## 一、系統定位

上傳會議影音 → 自動轉成逐字稿 → 用提示詞範本交給 LLM 整理成會議紀錄 → 待辦追蹤。

由通用 Blazor 腳手架（NET10-Blazor-Starter）演進而來，0.4.25 起轉為「AI 會議記錄小助手」。腳手架時期的通用能力（RBAC、稽核、快取、健康監控）仍在，並成為業務功能的底座。

## 二、端到端流程

核心流程與各階段的實作版本，見 [會議紀錄產生流程 PRD](../prd/會議紀錄產生流程-prd.md)：

```
音檔上傳 ─► 轉錄（STT）─► 逐字稿 ─► 歸屬專案 ─► 套用提示詞範本 ─► LLM ─► 會議紀錄 ─► 人工編修
└──────────── 0.4.27 ────────────┘└──────────────────── 0.4.31 ────────────────────┘
```

對應到使用者實際要點的地方：

| # | 動作 | 在哪一頁 | 產出 |
|---|------|---------|------|
| 0 | 建立分類、團隊、提示詞範本 | 資料定義 → 三個清單頁 | 後續各頁下拉的選項來源 |
| 1 | 建立專案 | 專案項目 | 會議紀錄與待辦的歸屬容器 |
| 2 | 新增會議、上傳影音檔 | 會議紀錄 | 存檔後**自動排入轉錄佇列**（0.4.65 起會先跳費用確認） |
| 3 | 等待背景轉錄（數分鐘～數十分鐘） | 會議紀錄（狀態欄） | 逐字稿 `.txt`（不落庫，只存路徑） |
| 4 | 選專案 → 選逐字稿 → 選提示詞 → 按「AI 轉會議紀錄」 | 專案項目 | （0.4.65 起會先跳費用確認）**排入生成佇列**，逐字稿同時歸屬到該專案 |
| 5 | 等待生成（約 30 秒～數分鐘） | 專案項目（歷史清單狀態欄） | 會議紀錄草稿（**落庫**，可編修） |
| 6 | 檢視／編修草稿 | 專案項目 → 歷史會議紀錄 | 最終會議紀錄 |
| 7 | 手動建立待辦 | 待辦事項 | 追蹤中的行動項目 |

**兩個必要前置條件**：步驟 4 需要「轉錄已完成的逐字稿」與「啟用中的提示詞範本」，缺一按鈕就沒東西可選。步驟 7 需要至少一個專案——待辦一定隸屬專案。

**步驟 3 與 5 都是背景工作**，畫面不會自動更新，要按「重新整理」才看得到狀態變化。

## 三、側邊選單逐項介紹

選單結構、id→權限鍵對照與過濾機制見 [首頁與導覽 PRD](../prd/首頁與導覽-prd.md)。0.4.33 起分為兩區塊，由 `Menu.json` 的 `section` 欄位宣告。

### 核心功能

#### 儀表板（`/dashboard`，權限鍵「儀表板」）

**用途**：整個系統的營運概況。純唯讀，不寫入任何資料。

**內容**：6 張數字卡（專案／會議／逐字稿／待辦／音檔容量／AI 問答次數）、3 張圓餅（專案狀態、轉錄狀態、生成狀態）、2 張長條（各專案會議份數 Top 8、提示詞使用次數）、1 張雙線折線（時間範圍可切換最近 7／14／30／90 天，預設 30 天），以及處理效能（平均轉錄／生成耗時、轉錄失敗率、**未歸屬逐字稿數**）。

**資料範圍沿用各頁既有規則**：會議套團隊過濾；專案（0.4.39）與待辦（0.4.66）都已無列級權控。這樣儀表板的數字才會與各頁實際看到的一致。

**圖表全部是手工 SVG／CSS**，沒有引任何圖表套件——顏色直接吃 `app.css` 的色票，零 JS、零新依賴。詳見 [儀表板](../changelog/2026-09-08-儀表板.md)。

#### 會議紀錄（`/meetings`，權限鍵「會議紀錄」）

**用途**：影音檔的入口。上傳、轉錄、看逐字稿都在這裡。

**主要操作**：新增會議（標題、日期、描述）→ 在同一個 Modal 內上傳影音檔（有百分比進度列）→ 存檔後自動排入轉錄佇列。清單上可看轉錄狀態、預覽逐字稿、重新轉錄。

**付費動作一律二次確認（0.4.65）**：上傳影音檔（會自動排入轉錄）與重新轉錄按下去都會先跳確認並說明會產生 Azure OpenAI 費用；服務層一併擋掉「待處理」狀態的重複請求（先前只擋「處理中」，連按兩下會跑兩趟並收兩份費用）。取消過的紀錄現在也會出現「重新轉錄」鈕——先前這個狀態沒有出口。

**0.4.35 的兩項調整**：

- 移除分類／團隊（清單欄位、工具列過濾、表單欄位）。本頁定位收斂為「上傳音檔 → 產出逐字稿」，歸屬與分類交給專案項目頁。**副作用是新建的會議一律公開**——`Teams` 是會議唯一的列權限來源，詳見「分類 vs 團隊」一節。
- **會議日期留空時，於上傳成功當下自動帶入上傳當天**；已填的不覆蓋，要更正可從畫面編輯。

**0.4.36 轉錄進度通知器**：右下角常駐面板顯示每筆轉錄的階段（排隊中／轉檔中／轉錄中第 N/M 段）與百分比，完成打勾、失敗顯示錯誤訊息；掛在 `MainLayout`，切到其他頁面也看得到。轉錄結束時清單自動重新載入。進度只存在記憶體（Singleton），沒有資料庫欄位，行程重啟即消失（重啟時殘留的「處理中」本來就會被標記為失敗）。

**限制**：一筆會議只搭配一個影音檔（替換即覆寫）。影音上限 1GB，16 種副檔名白名單。**逐字稿刻意沒有任何下載端點**——預覽走 Blazor 服務層讀檔後直接顯示在 Modal，少一個 HTTP 檔案輸出面就少一處要顧的授權。

**程式位置**：`Components/Views/Meetings/MeetingViewView.razor`、`MeetingService`、`TranscriptionJobRunner`。詳見 [會議紀錄 PRD](../prd/會議紀錄-prd.md)。

#### 專案項目（`/projects`，權限鍵「專案項目」）

**用途**：專案容器，也是 **AI 生成會議紀錄的唯一入口**。

0.4.31 全面改版：由分頁表格 CRUD 改為以專案為中心的工作區——頂端專案選擇器（可搜尋）＋ 新增／編輯／刪除／重新整理四顆按鈕，下方是專案摘要列、AI 生成區塊、歷史會議紀錄清單。

**主要操作**：

- 選專案 → 看摘要（負責人／期程／狀態／完成度／會議紀錄份數／**附件份數**）。附件份數可點開視窗檢視與下載（0.4.43）
- AI 區塊：選逐字稿 ＋ 選提示詞 → 「AI 轉會議紀錄」。逐字稿下拉列出**全部**轉錄完成的逐字稿，已被其他專案取用的呈現為不可選並標示「已屬：專案名」
- 歷史會議紀錄：檢視草稿、編修草稿、預覽來源逐字稿、**匯出 PDF**（0.4.40，需 `export` 動作權限；0.4.34–0.4.39 為 Markdown）
- **生成進度**（0.4.38）：按下「AI 轉會議紀錄」後，右下角常駐面板顯示階段與百分比，狀態欄同步附上即時百分比；生成結束時清單自動更新，不必手動按重新整理
- **AI 問答**（0.4.51）：工具列一顆「AI 問答」就整個專案提問（讀所有會議紀錄與**附件**），歷史清單每列一顆就單一會議提問（讀該會議的紀錄與逐字稿）。回答邊生成邊顯示，**對話歷史落庫**（`AiChatMessage`），同專案／會議底下所有人共用同一段對話

**關鍵規則**：**一份逐字稿只能歸屬一個專案，一個專案可有多份逐字稿**。屬於本專案的逐字稿可重選以更換提示詞重新產生，但**會覆蓋既有草稿**（畫面會先跳確認框，不保留版本歷程）。

**0.4.37→0.4.39 表單精簡與欄位移除**：新增／編輯專案的表單只留標題、開始／結束日期、狀態、完成百分比、負責人與附件。描述、優先級、分類、團隊四欄已於 **0.4.39 從資料庫中徹底刪除**，專案不再有列級可見性控管（見「分類 vs 團隊」一節）。專案附件刻意保留——日後要放合約之類的文件供 AI 查詢。

**改版的副作用**：原本的分頁、分類過濾、團隊過濾與關鍵字搜尋隨表格一併移除，改用專案下拉的搜尋。專案數量成長到數百筆時這個版面要重新檢討。

**程式位置**：`Components/Views/Projects/ProjectViewView.razor`、`ProjectService`、`MeetingService.RequestDraftAsync`。詳見 [專案項目 PRD](../prd/專案項目-prd.md)。

#### 待辦事項（`/todos`，權限鍵「待辦事項」）

**用途**：追蹤各專案的行動項目。

**主要操作**：雙欄版面——左邊是標準清單頁（工具列＋表格＋分頁），右邊是各負責人工作量面板（0.4.66，下拉切換人名，顯示完成度與該人的待辦清單；0.4.67 起可收合）。過濾器為專案與狀態兩個下拉（分類與團隊過濾已於 0.4.66 移除）。清單第一欄是完成勾選框，可直接勾；「待辦事項」欄只顯示標題的單行省略，描述改由旁邊的資訊 icon 開唯讀對話框檢視。

**設計決策**：**完成與否只有 `Status` 一個欄位**（待辦／進行中／已完成），刻意不另存 `IsCompleted` 布林——兩個欄位並存必然出現「勾了完成但狀態還是進行中」這種互相矛盾的資料。取消勾選會退回「進行中」而非「待辦」。

**關聯**：`ProjectId` 必填且為 **Cascade**（刪專案連帶刪待辦）；`MeetingId` 可空且為 **SetNull**，指向產生此待辦的來源會議紀錄——**但 AI 抽出待辦尚未實作**，目前所有待辦都是手動新增，來源顯示「— 手動新增」。

**程式位置**：`Components/Views/Todos/TodoViewView.razor`、`TodoService`。詳見 [待辦事項 PRD](../prd/待辦事項-prd.md)。

#### 系統管理 → 使用者管理（`/myusers`）

**誰能看**：**只有管理員**。頁面自己再檢查一次 `CheckIsAdmin()`，一般角色即使在權限矩陣勾了「使用者管理」也進不去。

**主要操作**：帳號、密碼（**編輯時留白＝沿用原密碼**）、名稱、Email、主要角色、**額外角色**（多選，權限取聯集）、**團隊**（直接綁定此使用者）、啟用、管理員。

**注意**：停用帳號會即時生效——該使用者下次載入任何頁面就被導向登出。**沒有「重設密碼」或「解鎖帳號」按鈕**（見第六節）。

#### 系統管理 → 角色管理（`/roleviews`，權限鍵「角色管理 」，**注意尾隨空白**）

**誰能看**：**只有管理員**。

**權限矩陣的操作方式**是這頁最需要理解的部分。矩陣是兩層＋動作欄：

```
☐ 資料定義管理功能                                        ← 群組（決定側邊選單那個分類是否出現）
   ☐ 提示詞清單（全部）  ☐檢視 ☐新增 ☐編輯 ☐刪除 ☐匯出   ← 葉節點
```

- 勾**葉節點的「（全部）」**＝該頁所有動作全開（舊制的裸頁面鍵），勾了之後右邊五個動作勾選框會整排灰掉
- 勾**任一個別動作**或「（全部）」，都會**自動把上層群組一併勾起來**（避免存了權限卻因群組沒開而看不到選單）
- 取消勾選群組會清掉底下所有葉節點的「（全部）」，但**不會清掉個別動作勾選**

**預設團隊**：角色層級的團隊授權，與使用者頁面的個人層級團隊**取聯集**（見第五節）。

#### 資料定義 → 分類清單（`/categories`）／團隊清單（`/teams`）／提示詞清單（`/prompttemplates`）

三頁都是標準清單頁（新增／重新整理／搜尋＋表格＋分頁）。頁大小取自 `MagicObjectHelper.PageSize`（8），但**目前只有提示詞清單真的分頁**——其餘七頁的 `GetAsync` 仍有 `Take` 只在 `dataRequest.Take != 0` 時才套用的缺陷，而呼叫端一律傳 0，所以第 1 頁會列出全部資料（0.4.64 只修了提示詞清單）。

- **分類清單**：名稱（不可重複）、描述、啟用狀態。
- **團隊清單**：名稱（不可重複）、代號（選填但需唯一）、描述、啟用狀態。
- **提示詞清單**：名稱、**提示詞內容**（長文字）、描述、啟用狀態。工具列多了「建立內建範本」與「選擇內建範本＋新增此範本」兩個入口（0.4.64），一鍵建立五個內建範本供新使用者起步；「啟用狀態」可直接點擊切換（附二次確認）。分類與團隊仍在編輯表單中，但已不在清單欄位與工具列過濾（0.4.64 移除）。
  - 內容可用三個變數：`{{transcript}}`、`{{meetingTitle}}`、`{{meetingDate}}`。大括號內允許空白、比對不分大小寫。
  - **變數驗證只提醒不阻擋**：寫了不認得的變數仍會存檔成功，只跳一則橘色警告；產生會議紀錄時**找不到對應值的佔位符會原樣保留**（不會悄悄變成空字串），方便一眼看出哪裡沒生效。
  - **這是目前唯一真的使用動作級權限的清單頁**——沒有 `create` 權限就看不到「新增」鈕。

**停用 vs 刪除**：停用只是讓它從其他頁面的下拉消失，**既有紀錄上的標籤不受影響**。刪除則有隱患，見第六節。

## 五、兩個必須先搞懂的觀念

### 分類 vs 團隊

兩者外觀一模一樣（都是多選標籤、都以換行包夾的分隔字串存在同一種欄位），**但作用完全不同**：

- **分類**＝純粹的分群／過濾標籤，**不控制任何權限**。只用在「工具列選了分類 A、B → 只顯示含 A 或 B 的紀錄」。
- **團隊**＝**唯一**的資料列可見性機制。

團隊的判斷規則（`TagStringHelper`）：

1. 管理員 → 一律看全部
2. 紀錄**沒有填任何團隊 → 視為公開，所有人都看得到**
3. 使用者沒有任何有效團隊 → 只看得到公開紀錄
4. 否則：紀錄的團隊與使用者的有效團隊**有任一名稱相同就放行**（交集，不是包含）

不只清單查詢，讀取單筆、更新、刪除、依專案連動查詢全都會再檢查一次，**猜網址、猜 Id 也繞不過去**。Web 與 API 走同一套判斷。

> 一句話：**分類幫你找資料，團隊決定誰看得到**。

**例外一：會議紀錄自 0.4.35 起不套用團隊控管。** 該頁的分類／團隊欄位已依需求整組移除，`Meeting.Teams` 因此不再被寫入；資料庫欄位與服務層 11 處判斷都還在，所以舊資料維持原可見範圍，但**新建的會議 `Teams` 恆為 `null`＝公開**。

**例外二：專案項目已完全退出團隊控管（0.4.39）。** `Project` 的 `Categories`／`Teams` 欄位已從資料庫刪除，6 處權限判斷（`ProjectService` 4 處、`MeetingService.RequestDraftAsync` 的專案守門、`TodoService.BeforeAddCheckAsync`）一併移除。設計理由：**角色權限只管功能，不管資料可見範圍**。 **0.4.66 起待辦事項也完全退出**：`Todo` 的 `Categories`／`Teams` 已隨 migration `RemoveTodoCategoriesTeams` 從資料庫刪除，`TodoService` 的 4 處判斷與 `DashboardService.BuildTodoQuery` 的團隊過濾一併移除。

會議紀錄（例外一）只需把表單的團隊 `Select` 加回去即可恢復，服務層完全沒動；專案項目則已無此欄位，要恢復得重下 migration。

### 有效團隊＝聯集

使用者的有效團隊 ＝ 直接綁在使用者身上的團隊（`UserTeam`）**∪** 其所有角色的預設團隊（`RoleView.DefaultTeamsJson`，含主要角色與額外角色）。

**畫面上的提示語「不設定則沿用其角色的預設團隊」容易誤導**——實際不是「有設就取代」，而是兩邊全部相加。使用者個人綁的團隊只會**擴大**可見範圍，不會縮小角色帶來的範圍。

比對的是團隊**名稱字串**而非 Id，也不檢查團隊是否啟用。這造成第六節的兩個隱患。

## 六、權限、背景工作與已知問題

### 權限機制

- **頁面級**：`AuthenticationStateHelper.CheckAccessPage(權限鍵)`
- **動作級**：`CheckAccessAction(權限鍵, view/create/edit/delete/export)`
- **管理員一律短路**，兩者對 `IsAdmin` 都直接回 true
- **選單過濾不是授權邊界**——選單看不到不代表打網址進不去，每頁必須自己檢查

新增受權限控管的頁面時，宣告式註冊有七處要同步，漏一處通常不會編譯失敗但功能會壞。清單見 [開發慣例與限制速查](開發慣例與限制速查.md)。

### 背景工作

轉錄與草稿生成是**兩條獨立的佇列與 worker**，刻意不共用——轉錄一筆可能跑數十分鐘，共用單一 worker 會讓草稿生成被長音檔堵住。

兩條都是行程內 `Channel<T>` ＋ 單一 worker，**佇列不持久化**（單一實例假設）。因此 `Program.cs` 啟動時會把殘留在「處理中」／「生成中」的紀錄改判為「失敗」，由使用者重新觸發。

**取消**（0.4.55）：兩條佇列共用 Singleton 的 `IJobCancellationRegistry`。排隊中的取消是一個只能消耗一次的標記（worker 取件時檢查後跳過）；執行中的取消直接對登記中的 CTS `Cancel()`。handle 上的 `IsCancelledByUser` 旗標是關鍵——**使用者取消與應用程式關機都只會拋 `OperationCanceledException`**，沒有它就分不出該標「已取消」還是留給啟動復原標「失敗」。上面那段啟動改判邏輯刻意維持不動：那些是真的沒人接手的孤兒。

**UI 舊複本不得覆寫背景寫入的狀態**：`MeetingService.UpdateAsync` 與 `MeetingRepository.UpdateAsync` 都一律沿用資料庫既有的媒體、轉錄與草稿欄位。日後再有背景工作寫回主表時請比照辦理。

### 已知問題與限制

以下都是實際查證過的現況，不是推測。接手前務必知道：

**功能面**

- ~~**首頁與專案項目是同一個畫面**~~：**已於 0.4.45 移除**，`HomeAuthed.razor` 已刪除，登入後降落點改為 `/meetings`。
- ~~**專案附件下載是壞的**~~：**已於 0.4.43 修復**。原因是 `/api/project-files/{id}/download` 端點從未存在（且 API 全為 JWT-only，`<a href>` 帶 Cookie 也會 401）。現改為呼叫 `ProjectService.GetFileDownloadAsync` 後走 `FileDownloadInterop` 的 JS interop 下載，不新增對外端點；同時在專案摘要列補了「附件 N 份」入口。
- **`/system-health` 沒有重新整理鈕**，只在載入時檢查一次，要重測得重新整理瀏覽器。

**資料完整性**

- **分類與團隊的刪除沒有使用中檢查**，且在紀錄上是以**名稱字串**儲存。刪除或改名會讓既有紀錄上的舊標籤變成孤兒。
- **改團隊名稱會讓可見性當場斷掉**——原本靠它取得存取權的使用者會突然看不到那些紀錄。
- **會議紀錄的列級權控對新資料已失效**（0.4.35，刻意）——表單不再能設定團隊，新建的會議一律公開，包含逐字稿預覽。
- **專案項目已無列級權控**（0.4.39，刻意）——欄位已從資料庫刪除，只要有頁面權限就看得到所有專案。
- **停用團隊不影響已授權的可見性**（判斷只比對名稱，不查是否啟用）。

**安全**

- **帳號鎖定沒有後台解鎖介面**。5 次失敗鎖 15 分鐘，**到期後計數器仍是 5**，再錯一次立刻又鎖，直到成功登入才歸零。管理者無法手動解鎖，清單上也看不到「已鎖定」狀態。
- **雙因素驗證只有資料表欄位（`TwoFactorEnabled`／`TwoFactorSecret`），完全未實作**，登入流程不讀取它們。
- **登入驗證碼是純文字四位數**（不是圖片），透過表單 hidden 欄位帶回比對，防機器人強度很低。
- **稽核日誌沒有任何查看介面**，只能直接查 SQLite 的 `AuditLog` 表。涵蓋範圍也窄：只記登入與使用者／角色管理，**Google 登入、業務資料 CRUD、變更密碼全都不記錄**。寫入失敗只記警告不阻斷原操作，**不能當成強保證**。
  - 注意別混淆：`/system-health` 頁尾顯示的是 NLog 文字日誌檔，與 `AuditLog` 資料表是兩回事。
- **動作級權限僅提示詞清單頁與專案項目的匯出鈕真的在用**，分類與團隊清單頁只做頁面層級檢查，進得去就能增刪改。
- **`export` 動作在 0.4.34 之前從未被任何程式使用**，因此既有角色都沒有勾過它。升級後一般角色看不到匯出鈕，需由管理員在角色管理勾選（管理員本身短路不受影響）。

**AI 與資料處理**

- **逐字稿會外送 Azure OpenAI**（轉錄與生成兩段都是）。使用組織自有租戶，但仍是資料離開本系統。 **0.4.51 起專案附件（含合約）的全文也會外送**——AI 問答會把附件文字放進脈絡，這是新的資料外送面。
- **逐字稿沒有保留期限與自動清理政策**。
- **AI 問答的對話存在檔案系統**（0.4.60 起，路徑 `SystemSettings.ExternalFileSystem.AiChatPath`），一段對話一個 `.jsonl`。**同一個專案／會議底下的對話是所有人共用**，不是每人一份。與逐字稿一樣沒有保留期限與自動清理政策。
- **完全不做成本控管**：不計 token、不設單次上限或每日配額。 0.4.51 的 AI 問答讓這件事更明顯——它是使用者主動觸發且可無限重複的成本面。
- 生成的會議紀錄**不保留版本歷程**，重新產生即覆蓋（含人工編修過的內容）。
- **逐字稿的人工編修同樣不保留版本歷程**（0.4.55）——儲存是就地覆寫，改掉的舊內容不留。另外讀取時會經 `TranscriptionNoiseFilter` 過濾，使用者存回去的是**過濾後**的內容，等於順手把供應商外漏的系統指令從檔案永久清掉；這是好事，但別誤判成「編輯把內容弄不見了」。
