# 資料模型與資料庫

- 文件版本：1.3
- 文件狀態：已實作
- 現行系統版本：0.4.27
- 首次實作版本：0.1.61
- 最後核對日期：2026/09/01

## 文件目的

說明本專案的資料庫採用方案、`BackendDBContext` 結構、各 Entity 與彼此關聯，以及 Migration 與啟動 Seed 的行為。

---

## 1. 資料庫採用方案

- **唯一支援**：SQLite，連線字串由 `MagicObjectHelper.GetSQLiteConnectionString(databasePath)` 動態組成；`databasePath` 來自 `appsettings.json` 之 `SystemSettings.ExternalFileSystem.DatabasePath`（預設 `C:\temp\MeetingRecord\DB`）。註冊處為 `ServiceCollectionExtensions.AddConfiguredDatabase`，固定呼叫 `UseSqlite`。
- 0.4.24 起**移除 SQL Server 支援**：`MeetingRecord.AccessDatas.SqlServerMigrations` 專案、`SystemSettings.DatabaseProvider` 設定與 `ConnectionStrings.DefaultConnection` 皆已刪除。
- **Collation**：`Chinese_Taiwan_Stroke_CI_AS`（於 `BackendDBContext.OnModelCreating` 統一指定）。此為 SQL Server 概念，SQLite 會忽略；保留以避免產生不必要的模型差異。

## 2. `BackendDBContext`

檔案：[`src/MeetingRecord/MeetingRecord.AccessDatas/BackendDBContext.cs`](../../src/MeetingRecord/MeetingRecord.AccessDatas/BackendDBContext.cs)

### 2.1 DbSet 一覽

| `DbSet` | Entity | 用途 |
|---------|--------|------|
| `MyUser` | `MyUser` | 使用者帳號 |
| `Project` | `Project` | 專案 |
| `ProjectFile` | `ProjectFile` | 專案附件 |
| `RoleView` | `RoleView` | 角色（含權限 JSON） |
| `AuditLog` | `AuditLog` | 稽核軌跡（誰/何時/對什麼/做了什麼/結果） |
| `Permission` | `Permission` | RBAC 權限鍵目錄 |
| `RolePermissionMap` | `RolePermissionMap` | 角色↔權限多對多 |
| `UserRole` | `UserRole` | 使用者↔角色多對多（支援多角色） |
| `UserTeam` | `UserTeam` | 使用者↔團隊多對多（團隊直接綁使用者） |
| `PromptTemplate` | `PromptTemplate` | 會議紀錄提示詞範本 |
| `Meeting` | `Meeting` | 會議紀錄（含影音檔中繼資料與轉錄狀態）|
| `Todo` | `Todo` | 待辦事項（隸屬專案項目，可回溯來源會議紀錄）|

> 註：另有 `Category`、`Team` 兩張標籤主檔（見 [開發慣例與限制速查](開發慣例與限制速查.md) 分類/團隊權控段落）。

### 2.2 全域刪除政策

`OnModelCreating` 預設將所有外鍵的 `DeleteBehavior` 設為 `Restrict`：父資料表若仍有子資料時不可被強制刪除。

### 2.3 Cascade 例外

下列「主表 → 附件表」改為 `DeleteBehavior.Cascade`，主表刪除時連動清除附件紀錄：

```csharp
Project    → Project.Files     → ProjectFile.ProjectId
Project    → Project.Todos     → Todo.ProjectId
```

> 注意：附件「資料表紀錄」會被 EF Core Cascade 處理；但**實體檔案**仍須由 Service 層在刪除前後手動移除。詳見 [檔案上傳機制](../features/檔案上傳機制.md)。
>
> `Meeting` **不在此列**：一筆會議只搭配一個影音檔，媒體與逐字稿路徑直接內嵌在主表，沒有附件子表。刪除時 `MeetingService.DeleteAsync` 與 `MeetingController.Delete` 都必須自行呼叫 `MeetingFileStore` 清實體檔案。
>
> 0.4.31 起 `Meeting` 有一個**可空**外鍵 `ProjectId`（`Project` → `Meeting` 一對多），但刪除行為刻意是 `DeleteBehavior.SetNull` 而非 `Cascade`：會議紀錄不是專案的附件，刪專案只解除歸屬、逐字稿與 AI 草稿保留。
>
> 0.4.32 起 `Todo` 有兩個外鍵，刪除行為刻意不同：`ProjectId`（必填）為 **Cascade**——沒有專案的待辦只會變成沒人管的垃圾資料；`MeetingId`（可空）為 **SetNull**——會議紀錄被刪除時待辦保留，只是失去來源。

## 3. 主要 Entity 概觀

| Entity | 主要欄位 | 備註 |
|--------|----------|------|
| `MyUser` | `Account`、`Name`、`Email`、`Password`、`Salt`、`IsAdmin`、`Status`、`RoleViewId`、`AccessFailedCount`、`LockoutEndUtc`、`TwoFactorEnabled`、`TwoFactorSecret` | 密碼以 `SecurePasswordHasher.HashPassword`（PBKDF2）雜湊，登入自動升級舊 SHA256（`Salt` 僅供舊資料相容）；含帳號鎖定與 TOTP 欄位。 |
| `RoleView` | `Name`、`TabViewJson`、`DefaultTeamsJson` | `TabViewJson` 為權限樹 JSON；`DefaultTeamsJson` 為角色預設團隊。**RBAC 重構後改由關聯表為準**（見 3.1）。 |
| `Project` | `Title`、`StartDate`、`EndDate`、`Status`、`CompletionPercentage`、`Owner`、`CreatedAt`、`UpdatedAt`、`Files` | 日期欄位可為 null。**0.4.39 移除 `Description`、`Priority`、`Categories`、`Teams` 四欄**（migration `RemoveProjectDescriptionPriorityCategoriesTeams`）——專案不再有列級可見性控管，權限只管功能不管資料範圍。 |
| `ProjectFile` | `FileName`、`StoredPath`、`Size`、`ProjectId` | 一筆紀錄對應一份實體檔案。 |
| `PromptTemplate` | `Name`、`Content`、`Description`、`IsEnabled`、`Categories`、`Teams`、`CreatedAt`、`UpdatedAt` | 產生會議紀錄用的提示詞範本；`Name` 唯一（不分大小寫，由 Service 檢查，非 DB 索引）。`Content` 為 SQLite `TEXT`，Entity 端不設長度上限。`Categories`／`Teams` 為換行包夾的多值標籤字串（`TagStringHelper`），`Teams` 決定列級可見性。無外鍵關聯。 |
| `Meeting` | `Title`、`MeetingDate`、`Description`、`Categories`、`Teams`、`MediaOriginalFileName`、`MediaStoredFileName`、`MediaRelativePath`、`MediaContentType`、`MediaFileSize`、`TranscriptRelativePath`、`TranscriptionStatus`、`TranscriptionError`、`TranscriptionStartedAt`、`TranscriptionCompletedAt`、`ProjectId`、`DraftContent`、`DraftStatus`、`DraftError`、`DraftPromptTemplateId`、`DraftPromptTemplateName`、`DraftStartedAt`、`DraftCompletedAt`、`CreatedAt`、`UpdatedAt` | 會議紀錄。**刻意命名為 `Meeting` 而非 `MeetingRecord`**——後者會與根命名空間衝突。一筆會議只搭配一個影音檔，媒體欄位內嵌、**不另開附件子表**；影音檔與逐字稿存於檔案系統，欄位只記相對路徑（媒體相對於 `MeetingMediaPath`、逐字稿相對於 `MeetingTranscriptPath`）。`TranscriptionStatus` 為 `TranscriptionStatus` 列舉存 int（0 未上傳／1 待處理／2 處理中／3 已完成／4 失敗）。`Categories`／`Teams` 為換行包夾的多值標籤字串（`TagStringHelper`），`Teams` 決定列級可見性。0.4.31 起新增可空外鍵 `ProjectId`（一份逐字稿只能屬一個專案，一個專案可有多份）與七個 AI 草稿欄位；`DraftStatus` 為 `DraftStatus` 列舉存 int（0 未產生／1 待處理／2 生成中／3 已完成／4 失敗），`DraftContent` 落庫且可人工編修、重新產生即覆蓋。 |
| `Todo` | `Title`、`Description`、`ProjectId`、`MeetingId`、`Owner`、`DueDate`、`Priority`、`Status`、`Categories`、`Teams`、`CreatedAt`、`UpdatedAt` | 待辦事項。**完成與否只看 `Status` 一個欄位**（待辦／進行中／已完成），刻意不另存 `IsCompleted` 布林——兩個欄位並存必然出現互相矛盾的資料。`ProjectId` 必填且為 Cascade；`MeetingId` 可空且為 SetNull，指向產生此待辦的來源會議紀錄（AI 抽出待辦尚未實作，目前一律為 null）。`Categories`／`Teams` 為換行包夾的多值標籤字串（`TagStringHelper`），`Teams` 決定列級可見性。 |

實際欄位請以 `src/MeetingRecord/MeetingRecord.AccessDatas/Models/` 內的程式碼為主。

### 3.1 RBAC 關聯資料模型（權限重構階段二）

資料驅動 RBAC 以四張關聯表取代原本寫在 `RoleView.TabViewJson` / `MyUser.RoleViewId` / `RoleView.DefaultTeamsJson` 的邏輯：

- `Permission`：權限鍵目錄（`Key` 唯一；階段四導入 `resource:action` 動作粒度）。
- `RolePermissionMap`：角色↔權限（取代 `TabViewJson`）。命名加 `Map` 以避開 UI 綁定模型 `MeetingRecord.Models.Admins.RolePermission`。
- `UserRole`：使用者↔角色（取代單一 `RoleViewId`，支援多角色）。
- `UserTeam`：使用者↔團隊（團隊改直接綁使用者，取代綁在角色）。

**回填**：啟動時由 `IRbacBackfillService`（`RbacBackfillService`）冪等地將既有資料填入上述表；失敗僅記錄、不中止啟動。

**雙寫**：角色編輯（`RoleViewService`）與使用者指派（`MyUserService`）時，另由 `IRbacWriteService`（`RbacWriteService`）協調式同步 `RolePermissionMap` / `UserRole`，使新表隨編輯即時保持一致（不必等下次啟動回填）。

> **現況（階段三／四已落地）**：執行期授權**已以 RBAC 關聯表為權威來源**——API 以 `HasPermission` + `IPermissionChecker` 強制動作級授權（無權限回 403），UI 亦於登入時經 `IPermissionChecker.GetEffectivePermissionKeysAsync` 載入有效權限鍵（多角色聯集）；`TabViewJson` 退為角色編輯回填用的相容欄位。（上句原為階段二當時狀態，現已切換。）

## 4. Migration 與啟動 Seed

### 4.1 Migration 檔案

SQLite migration 位於 `src/MeetingRecord/MeetingRecord.AccessDatas/Migrations/`，隨模型演進累積（`init` → `add-some` → `AddGoogleOAuth` → `AddCategoryAndTeam` → `AddRecordTagsAndRoleTeams` → `AddAccountLockout` → `AddAuditLog` → `AddTwoFactor` → `AddRbacTables` → `RemoveTaskAndMeeting` → `AddPromptTemplate` → `AddMeeting` → `AddMeetingProjectAndDraft` → `AddTodo`）。本專案只有這一組 migration。

> `AddPromptTemplate`（0.4.26）只 `CREATE` 一張 `PromptTemplate` 表，不影響任何既有資料表。

> `AddMeeting`（0.4.27）只 `CREATE` 一張 `Meeting` 表，不影響任何既有資料表。
>
> `AddMeetingProjectAndDraft`（0.4.31）在既有的 `Meeting` 表上新增八個欄位與一個指向 `Project` 的外鍵。這是本專案第一個「改既有表 + 加外鍵」的 migration —— SQLite 不支援用 `ALTER TABLE` 加外鍵約束，EF Core 會改以 **table-rebuild** 執行（建 `ef_temp_Meeting` → `INSERT...SELECT` 搬全部欄位 → `DROP` 舊表 → rename）。因此套用時會出現一則預期中的警告：`The migration operation 'PRAGMA foreign_keys = 0;' ... cannot be executed in a transaction`。這是 SQLite 重建資料表的固有限制，不是設定錯誤；既有資料會完整保留。

> `RemoveTaskAndMeeting`（0.4.24）會 `DROP` 掉 `MeetingFile`、`MyTasFile`、`Meeting`、`MyTas` 四張表。既有資料庫啟動時會自動套用，該四張表內的資料將一併消失；附件的**實體檔案**不會被自動刪除，需自行清理。

新增 Migration、移除 Migration、套用資料庫的指令請見 [EFCore.md](../guides/EFCore.md)。

### 4.2 啟動時自動處理

`Program.cs:175-258` 會在 `app.Build()` 後執行：

1. 若有任何 Migration → `dbContext.Database.Migrate()`。
2. 否則 → `dbContext.Database.EnsureCreated()`。
3. **Seed 預設角色**：`RoleView.Name == MagicObjectHelper.預設角色`（不存在則新增），其 `TabViewJson` 來自 `RolePermissionService.GetRolePermissionAllNameToJson()`。
4. **Seed 預設帳號**：`MyUser.Account == BootstrapSettings.SupportAccount`（不存在則新增），密碼以 `SecurePasswordHasher.HashPassword`（**PBKDF2**）雜湊、`IsAdmin=true`，並關聯到上一步的 `RoleView`；既有帳號密碼驗證失敗時自動升級為 PBKDF2。

5. **轉錄狀態修復**（0.4.27 起）：把殘留在 `TranscriptionStatus == Processing` 的 `Meeting` 一律改判為 `Failed`。轉錄佇列是行程內的、不持久化，重啟後沒有 worker 會接手這些工作，不修復就會永久卡在「處理中」。
6. **草稿生成狀態修復**（0.4.31 起）：同理，把殘留在 `DraftStatus == Processing` 的 `Meeting` 改判為 `Failed`。

> 啟動 Seed 為冪等行為：每次啟動會重新覆寫預設角色的 `TabViewJson`（RBAC 權威表 `RolePermissionMap` 由 `RbacBackfillService` 於啟動從 `TabViewJson` 回填），並重置預設帳號 `IsAdmin = true`，確保其永遠可登入。
