## 1. 資料庫採用方案

- **唯一支援**：SQLite，連線字串由 `MagicObjectHelper.GetSQLiteConnectionString(databasePath)` 動態組成；`databasePath` 來自 `appsettings.json` 之 `SystemSettings.ExternalFileSystem.DatabasePath`（預設 `C:\temp\MeetingRecord\DB`）。註冊處為 `ServiceCollectionExtensions.AddConfiguredDatabase`，固定呼叫 `UseSqlite`。
- 0.4.24 起**移除 SQL Server 支援**：`MeetingRecord.AccessDatas.SqlServerMigrations` 專案、`SystemSettings.DatabaseProvider` 設定與 `ConnectionStrings.DefaultConnection` 皆已刪除。
- **Collation**：`Chinese_Taiwan_Stroke_CI_AS`（於 `BackendDBContext.OnModelCreating` 統一指定）。此為 SQL Server 概念，SQLite 會忽略；保留以避免產生不必要的模型差異。

| `AiUsageLog` | `AiUsageLog` | AI 呼叫的用量帳本（0.4.80）——**一次 API 呼叫一列**，永久保留。0.4.88 加上 `ExchangeRate`／`ConvertedCurrency` 兩欄，存呼叫當下的匯率快照 |

> 註：另有 `Category`、`Team` 兩張主檔。`Team` 就是部門（畫面「團隊清單」，`/teams`；0.4.101 曾改叫「資料群組」，0.4.102 改回），透過 `UserTeam`／`ProjectTeam` 決定誰看得到哪些專案（見 [開發慣例與限制速查](開發慣例與限制速查.md) §4.0）。`Category` 只描述資料，以名稱字串存進 `Project.Categories`／`Meeting.Categories`，不影響可見性。0.4.99～0.4.100 的 `ProjectMember`（負責人／協作者）已移除：migration 刻意不刪表，由啟動時的 `TeamConversionService` 轉成同名團隊（設為主責）後 `DROP TABLE`。

> **`AiUsageLog`（0.4.80，0.4.88 補匯率）** 有幾個刻意的性質，改動前先讀一遍：
>
> - **`ExchangeRate`／`ConvertedCurrency`（0.4.88）** 與單價一樣是**寫入當下的快照**。匯率天天在動，讀取時才換算的話今天匯率一變、去年的帳就整批跟著變，而這張表最主要的用途正是「本月 vs 上月」。台幣金額 = 同一列的 `EstimatedCost × ExchangeRate`，**刻意不另存換算後金額**（兩份真相必然漂移，而且 SQLite 的 decimal 是 TEXT，預先算好也換不到效能）。
> - ⚠️ `ExchangeRate` 與 `EstimatedCost` 同樣**不可在 SQL 端 `ORDER BY`、比大小或 `SUM`**，只能 `IS NOT NULL` 篩選後撈進記憶體算。
> - ⚠️ 抓不到匯率時是 **null 而不是 1**——當成 1 會讓台幣金額少報三十幾倍，而畫面上完全看不出來。
>
> - **一次 API 呼叫一列**，不是一次使用者動作一列。一趟長會議的生成會寫下 N 筆分段摘要 ＋ 1 筆最終整理，
>   一個音檔會寫下 N 筆轉錄。
> - **沒有任何外鍵。** 帳本是既成事實的紀錄，不該因為會議或使用者被刪除而被連帶刪掉，
>   也不該讓刪除操作被 Restrict 擋住。`UserName` 是當下的名字快照。
> - **兩種計費單位共用一張表**：文字生成填 token、轉錄填秒數，另一組留 null。
>   單位由 `Feature` 唯一決定，刻意不另存單位欄位。
> - ⚠️ **`EstimatedCost` 等 decimal 欄位在 SQLite 是 TEXT**：`ORDER BY` 是字典序（`"10.0" < "9.0"`）、
>   比較大小同理。**只能撈進記憶體再加總**，絕不可在 SQL 端排序或比較。
> - 單價未設定時金額是 **null 而不是 0**——0 與「真的沒花錢」看起來一模一樣。
> - **不回填**：0.4.80 之前的呼叫沒有留下任何用量資料，事後補不回來。

### 2.2 全域刪除政策

`OnModelCreating` 預設將所有外鍵的 `DeleteBehavior` 設為 `Restrict`：父資料表若仍有子資料時不可被強制刪除。

### 2.3 Cascade 例外

下列「主表 → 附件表」改為 `DeleteBehavior.Cascade`，主表刪除時連動清除附件紀錄：

```csharp
Project    → Project.Files     → ProjectFile.ProjectId
Project    → Project.Todos     → Todo.ProjectId
Project    → Project.Teams     → ProjectTeam.ProjectId   （0.4.101）
Team       → ProjectTeam.TeamId、UserTeam.TeamId          （0.4.101；UserTeam 另對 MyUser Cascade）
Category   → CategoryTeam.CategoryId                      （0.4.102）
Team       → CategoryTeam.TeamId                          （0.4.102）
```

> ⚠️ 資料庫層刪除團隊（`Team`）會連帶刪掉它的 `ProjectTeam`，所以**非管理者刪除還是某專案主責團隊的團隊時由服務層擋下**（`TeamService.BeforeDeleteCheckAsync`／`DeleteAsync`、`TeamRepository.DeleteAsync`，API 回 409），否則專案會失去主責。管理者不受此限（0.4.104）：照刪，受影響的專案就沒有主責團隊，之後編輯專案時再補；下次啟動時 `TeamConversionService` 會替沒有主責的專案補上（取協作團隊中 Id 最小的，沒有就掛「待分配」）。只當協作團隊的可以刪，只會縮小可見範圍。

> 注意：附件「資料表紀錄」會被 EF Core Cascade 處理；但**實體檔案**仍須由 Service 層在刪除前後手動移除。詳見 [檔案上傳機制](../features/檔案上傳機制.md)。
>
> `Meeting` **不在此列**：一筆會議只搭配一個影音檔，媒體與逐字稿路徑直接內嵌在主表，沒有附件子表。刪除時 `MeetingService.DeleteAsync` 與 `MeetingController.Delete` 都必須自行呼叫 `MeetingFileStore` 清實體檔案。
>
> 0.4.31 起 `Meeting` 有一個**可空**外鍵 `ProjectId`（`Project` → `Meeting` 一對多），但刪除行為刻意是 `DeleteBehavior.SetNull` 而非 `Cascade`：會議紀錄不是專案的附件，刪專案只解除歸屬、逐字稿與 AI 草稿保留。
>
> 0.4.32 起 `Todo` 有兩個外鍵，刪除行為刻意不同：`ProjectId`（必填）為 **Cascade**——沒有專案的待辦只會變成沒人管的垃圾資料；`MeetingId`（可空）為 **SetNull**——會議紀錄被刪除時待辦保留，只是失去來源。

> 0.4.60 起 **AI 問答的對話不再進資料庫**：對話文字不需要被查詢或索引，只會整段讀出來顯示，放資料庫只是讓它膨脹。改存成檔案（一段對話一個 `.jsonl`，路徑由「範圍＋對象 Id」直接算出來，見 [檔案上傳機制](../features/檔案上傳機制.md)），`AiChatMessage` 資料表已由 `DropAiChatMessage` migration 移除。**代價：刪除專案／會議時不再有 Cascade 幫忙清理**，`MeetingService`／`ProjectService` 的 `DeleteAsync` 各自呼叫 `AiChatStore.TryDelete`。
>
> 0.4.79 讓一個對象底下可以有**多段對話**（路徑多一層對話 Id），標題與建立者放在對話檔的第一行（`role: "meta"`），**同樣沒有為此新增資料表**——清單直接從檔案系統列出來。

### 3.1 RBAC 關聯資料模型（權限重構階段二）

資料驅動 RBAC 以四張關聯表取代原本寫在 `RoleView.TabViewJson` / `MyUser.RoleViewId` / `RoleView.DefaultTeamsJson` 的邏輯：

- `Permission`：權限鍵目錄（`Key` 唯一；階段四導入 `resource:action` 動作粒度）。
- `RolePermissionMap`：角色↔權限（取代 `TabViewJson`）。命名加 `Map` 以避開 UI 綁定模型 `MeetingRecord.Models.Admins.RolePermission`。
- `UserRole`：使用者↔角色（取代單一 `RoleViewId`，支援多角色）。
- `UserTeam`：使用者↔團隊（團隊改直接綁使用者，取代綁在角色）。0.4.101 起 `DefaultTeamsJson` 已刪除，`UserTeam` 是唯一來源。

**回填**：啟動時由 `IRbacBackfillService`（`RbacBackfillService`）冪等地將既有資料填入上述表；失敗僅記錄、不中止啟動。0.4.101 起不再從角色預設團隊回填 `UserTeam`。0.4.101 曾把權限鍵「團隊清單」改名為「資料群組」，**0.4.102 起 `RenameLegacyPermissionKeysAsync` 把「資料群組」（含 `資料群組:edit` 等動作鍵）就地改回「團隊清單」**（`Permission.Key` 與 `RoleView.TabViewJson` 都改；`RolePermissionMap` 掛的是 `PermissionId`），原本有的角色照樣有。

**雙寫**：角色編輯（`RoleViewService`）與使用者指派（`MyUserService`）時，另由 `IRbacWriteService`（`RbacWriteService`）協調式同步 `RolePermissionMap` / `UserRole`，使新表隨編輯即時保持一致（不必等下次啟動回填）。

> **現況（階段三／四已落地）**：執行期授權**已以 RBAC 關聯表為權威來源**——API 以 `HasPermission` + `IPermissionChecker` 強制動作級授權（無權限回 403），UI 亦於登入時經 `IPermissionChecker.GetEffectivePermissionKeysAsync` 載入有效權限鍵（多角色聯集）；`TabViewJson` 退為角色編輯回填用的相容欄位。（上句原為階段二當時狀態，現已切換。）

## 4. Migration 與啟動 Seed

### 4.1 Migration 檔案

SQLite migration 位於 `src/MeetingRecord/MeetingRecord.AccessDatas/Migrations/`，隨模型演進累積（`init` → `add-some` → `AddGoogleOAuth` → `AddCategoryAndTeam` → `AddRecordTagsAndRoleTeams` → `AddAccountLockout` → `AddAuditLog` → `AddTwoFactor` → `AddRbacTables` → `RemoveTaskAndMeeting` → `AddPromptTemplate` → `AddMeeting` → `AddMeetingProjectAndDraft` → `AddTodo` → `RemoveProjectDescriptionPriorityCategoriesTeams` → `AddAiChatMessage` → `DropAiChatMessage` → `RemoveTodoCategoriesTeams` → `AddProjectGlossaryAndMeetingDraftAttendees` → `AddAiUsageLog` → `AddAiUsageExchangeRate` → `AddProjectMemberAndMeetingCreator` → `AddProjectTeamRemoveDefaultTeams` → `AddProjectPrimaryTeamAndCategories` → `RemoveLegacyTeamTags`）。本專案只有這一組 migration。

> `AddPromptTemplate`（0.4.26）只 `CREATE` 一張 `PromptTemplate` 表，不影響任何既有資料表。

> `AddMeeting`（0.4.27）只 `CREATE` 一張 `Meeting` 表，不影響任何既有資料表。
>
> `AddMeetingProjectAndDraft`（0.4.31）在既有的 `Meeting` 表上新增八個欄位與一個指向 `Project` 的外鍵。這是本專案第一個「改既有表 + 加外鍵」的 migration —— SQLite 不支援用 `ALTER TABLE` 加外鍵約束，EF Core 會改以 **table-rebuild** 執行（建 `ef_temp_Meeting` → `INSERT...SELECT` 搬全部欄位 → `DROP` 舊表 → rename）。因此套用時會出現一則預期中的警告：`The migration operation 'PRAGMA foreign_keys = 0;' ... cannot be executed in a transaction`。這是 SQLite 重建資料表的固有限制，不是設定錯誤；既有資料會完整保留。

> `AddProjectTeamRemoveDefaultTeams`（0.4.101）建立 `ProjectTeam` 表、刪除 `RoleView.DefaultTeamsJson`，**刻意不刪 `ProjectMember`**——舊的專案成員要留給啟動時的轉換服務（0.4.101 叫 `DataGroupConversionService`，0.4.102 改名 `TeamConversionService`）轉成團隊，轉完由它刪表。

> `AddProjectPrimaryTeamAndCategories`（0.4.102）新增 `ProjectTeam.IsPrimary`、`Project.Categories` 兩欄與 `CategoryTeam` 表（`(CategoryId, TeamId)` 唯一索引，兩邊 Cascade）。**既有 `ProjectTeam` 的 `IsPrimary` 一律是 false**，由啟動時的 `TeamConversionService` 補主責（見 4.2）。

> `RemoveLegacyTeamTags`（0.4.103）刪除 `Meeting.Teams`、`PromptTemplate.Teams` 兩欄——0.4.98 以前的團隊標籤字串，0.4.99 起已不影響可見性。**既有標籤資料一併刪除**（經使用者同意）；`Down` 只會加回空欄位，資料不會回來。

> `RemoveTaskAndMeeting`（0.4.24）會 `DROP` 掉 `MeetingFile`、`MyTasFile`、`Meeting`、`MyTas` 四張表。既有資料庫啟動時會自動套用，該四張表內的資料將一併消失；附件的**實體檔案**不會被自動刪除，需自行清理。

新增 Migration、移除 Migration、套用資料庫的指令請見 [EFCore.md](../guides/EFCore.md)。

### 4.2 啟動時自動處理

`Program.cs` 的 `#region 資料庫的 Migration` 會在 `app.Build()` 後執行：

1. 若有任何 Migration → `dbContext.Database.Migrate()`。
2. 否則 → `dbContext.Database.EnsureCreated()`。
3. **預設角色**（0.4.101，`DefaultRoleSeeder`，原 0.4.98 的 `RoleConsolidationService`）：確保 `RoleView.Name == MagicObjectHelper.預設角色`（「一般使用者」）存在——找不到時先把舊名「預設角色」那一列改名，都沒有才新增；權限只在剛建立或剛改名時以 `SyncRolePermissionsAsync` 同步成 `RolePermissionService.GetGeneralUserPermissionNames()`（**會移除多餘權限**）。**不動任何帳號的角色**（0.4.98～0.4.100 曾把所有帳號的 `RoleViewId`／`UserRole` 收斂成這個角色，已拿掉）。
4. **Seed 預設帳號**：`MyUser.Account == BootstrapSettings.SupportAccount`（不存在則新增），密碼以 `SecurePasswordHasher.HashPassword`（**PBKDF2**）雜湊、`IsAdmin=true`，並關聯到上一步的 `RoleView`；既有帳號若密碼驗證結果不是 `Success`（含與設定值不符，或仍為舊格式需升級）就以 `BootstrapSettings.SupportPassword` 重新雜湊為 PBKDF2，`RoleViewId` 只在為空時補上（0.4.101 起不覆寫）。
   - 其後另有 RBAC 回填（`RbacBackfillService`，見 3.1）與**團隊轉換**（`TeamConversionService`，0.4.101 叫 `DataGroupConversionService`；每次啟動、冪等、失敗不中止啟動）：
     1. `ProjectMember` 表還在時，每個有成員的專案建一個同名團隊（撞名依序改「X（專案）」「X（專案 2）」…）放入成員並設為該專案的**主責**；沒有成員的專案主責掛到空的「待分配」團隊（只有管理者看得到）；最後 `DROP TABLE ProjectMember`。
     2. 補主責（EnsurePrimaryTeams）：有 `ProjectTeam` 但沒有主責的專案，把 `TeamId` 最小的那列設為主責；完全沒有 `ProjectTeam` 的專案（0.4.101 的「公開」專案）主責掛「待分配」——升級後只有管理者看得到，待管理者改指定。
     3. 會議上傳者（`Meeting.CreatedByUserId`）仍取 `AiUsageLog` 最早一筆轉錄的使用者回填。

5. **轉錄狀態修復**（0.4.27 起，`#region 轉錄狀態修復`）：把殘留在 `TranscriptionStatus == Processing` **或 `Pending`** 的 `Meeting` 一律改判為 `Failed`。轉錄佇列是行程內的、不持久化，重啟後沒有 worker 會接手這些工作（已入列但尚未被撿走的 `Pending` 也一樣），不修復就會永久卡在「處理中」／「待處理」。
6. **草稿生成狀態修復**（0.4.31 起，`#region 草稿生成狀態修復`）：同理，把殘留在 `DraftStatus == Processing` 或 `Pending` 的 `Meeting` 改判為 `Failed`。

> 啟動 Seed 為冪等行為：不動帳號的角色（0.4.101 起）；一般使用者的權限只在新建或改名當下設定一次，之後以角色管理頁為準（0.4.97 以前是每次啟動把預設角色覆寫成**全部權限**），並重置預設帳號 `IsAdmin = true`，確保其永遠可登入。
