# 新增「會議紀錄」管理頁面與影音語音轉文字（0.4.27）

- 文件版本：1.0
- 文件狀態：已實作
- 現行系統版本：0.4.27
- 首次實作版本：0.4.27
- 最後核對日期：2026/08/21

## 一、變更摘要

補上 [會議紀錄產生流程 PRD](../prd/會議紀錄產生流程-prd.md) 的前半段：新增 `/meetings` 會議紀錄 CRUD、單一影音檔上傳（含進度列），並以 FFmpeg 轉檔後呼叫 Azure OpenAI 完成語音轉文字，逐字稿落在檔案系統並可在畫面預覽。

版本號 **0.4.26 → 0.4.27**。

本次**不含**「套用提示詞 → LLM 產生會議紀錄草稿」，該階段仍為規劃中。

完整能力說明見 [會議紀錄 PRD](../prd/會議紀錄-prd.md)。

## 二、主要決策

| 決策 | 理由 |
| --- | --- |
| 實體命名為 `Meeting` 而非 `MeetingRecord` | 後者會與根命名空間 `MeetingRecord` 衝突；`Meeting` 也與 0.4.24 移除前的舊表同名，schema 有前例可循 |
| 媒體欄位內嵌在主表，不開附件子表 | 需求是「一筆會議一個影音檔」，開子表要多維護 Cascade 與集合的整套機制 |
| 上傳一律先經 FFmpeg 轉 mp3 | Azure OpenAI 轉錄不吃 `.wma`，也讀不了視訊容器；先轉檔才能同時滿足「支援常用格式」與「送得進 API」 |
| **一律切成 15 分鐘分段**，不做「夠小就不切」的分支 | 轉錄 API 單檔上限 25MB、上傳端允許 1GB。固定切段讓長會議與短錄音走同一條路徑，順帶解決長會議的時長問題；15 分鐘 @32kbps 約 3.6MB |
| 行程內 `Channel<int>` 佇列 + 單一 worker，不持久化 | 符合單一實例假設（SQLite 檔案資料庫 + 本機磁碟）。併發只會被 API 速率與 FFmpeg 的 CPU 佔用互相拖慢 |
| 啟動時把殘留「處理中」改為「失敗」 | 佇列不持久化，重啟後沒人會接手這些工作，不修復就會永久卡住 |
| 逐字稿預覽由服務層讀檔進 Modal，不開下載端點 | 逐字稿是高敏感內容；少一個 HTTP 檔案輸出面就少一處要顧的授權 |
| `LlmSettings` 加三個選填欄位，不另開設定區段 | 沿用既有 provider-aware 結構，AI 的 provider／endpoint／key／model 仍集中在同一處 |
| 轉錄檢查只在「明確啟用」時強制 | 只用 LLM、不用轉錄的部署不該被 `TranscriptionModel`／`FfmpegPath` 的檢查擋住上線 |

## 四、部署注意事項

1. **必須安裝 FFmpeg**，並在 `MediaSettings:FfmpegPath` 指向執行檔。這是本專案第一個外部執行檔相依。
2. Azure OpenAI 需另外部署一個轉錄模型（例如 `gpt-4o-transcribe`），deployment 名稱填在 `TranscriptionModel`。
3. `TranscriptionApiVersion` 需比文字生成的 `ApiVersion` 新；實際可用版本以目標 Azure 資源為準。
4. 新增權限鍵後，掛「預設角色」的使用者需重啟一次應用程式才會生效；掛自訂角色者須由管理員到 `/roleviews` 手動勾選。
5. `MeetingMediaPath` 會累積原始影音檔，容量規劃須另行評估（本版沒有自動清理政策）。
6. 會議逐字稿會外送第三方 LLM 供應商，導入前應確認資料處理、留存與跨境政策。
