## 變更目的

0.4.27 完成了「上傳 → 轉錄 → 逐字稿」，但整條流程真正的價值在後半段——把逐字稿交給 LLM 整理成會議紀錄——一行都還沒寫：全 repo 找不到 `chat/completions` 的呼叫端，`LlmSettings.DefaultProvider` 與 `Model` 兩個設定沒有任何消費者，`PromptVariableHelper` 也只會偵測未知變數、沒有代入方法。

本次補上後半段，並依 [會議記錄流程 Wireframe 設計規格](../superpowers/specs/2026-08-31-meeting-flow-wireframe-design.md) 把 `/projects` 改成以專案為中心的操作介面。

## 變更內容

### 一、逐字稿歸屬專案（推翻既有決議）

`Meeting` 原本**刻意沒有任何外鍵**，[會議紀錄產生流程 PRD](../prd/會議紀錄產生流程-prd.md) 明文寫「產出物歸屬＝獨立實體」。本次推翻該決議：

- `Meeting` 新增 `ProjectId` 可空外鍵；`Project` 新增 `Meetings` 導覽屬性。
- 關聯為一對多：**一份逐字稿只能屬於一個專案，一個專案可以有多份逐字稿**。
- `OnDelete(DeleteBehavior.SetNull)` —— 刪除專案只解除歸屬，逐字稿與會議紀錄保留。與 `Project → ProjectFile` 的 `Cascade` 不同，因為會議紀錄不是專案的附件。

Migration `AddMeetingProjectAndDraft` 是本 repo 第一個「改既有表 + 加外鍵」的 migration。SQLite 不支援用 `ALTER TABLE` 加外鍵約束，EF Core 會改以 table-rebuild 執行（`ef_temp_Meeting` 建新表 → `INSERT...SELECT` 搬資料 → drop → rename）。因此啟動時會看到一則預期中的警告：

```
The migration operation 'PRAGMA foreign_keys = 0;' from migration 'AddMeetingProjectAndDraft'
cannot be executed in a transaction.
```

這是 SQLite 重建資料表的固有限制，非設定錯誤。

### 二、文字生成軌道

在 `Business/Services/TextGeneration/` 新增一組與轉錄軌道對稱的元件：

| 轉錄軌道 | 生成軌道 |
| --- | --- |
| `ITranscriptionProvider` | `ITextGenerationProvider` |
| `AzureOpenAiTranscriptionProvider` | `AzureOpenAiTextGenerationProvider`（改打 `chat/completions`，收送 JSON） |
| `ITranscriptionQueue` | `IMeetingDraftQueue` |
| `TranscriptionBackgroundService` | `MeetingDraftBackgroundService` |
| `TranscriptionJobRunner` | `MeetingDraftJobRunner` |
| `AddTranscriptionServices()` | `AddTextGenerationServices()` |

**佇列刻意獨立而非共用**：轉錄一筆可能跑數十分鐘，若共用單一 worker，只要有一筆長音檔在轉錄，所有草稿生成都會被堵在後面。獨立軌道也讓既有的轉錄路徑完全不受影響。

`Meeting` 新增七個草稿欄位（`DraftContent`／`DraftStatus`／`DraftError`／`DraftPromptTemplateId`／`DraftPromptTemplateName`／`DraftStartedAt`／`DraftCompletedAt`）與 `DraftStatus` 列舉。

### 三、map-reduce 分段

`TranscriptChunker` 以 12000 字元為界切段，優先沿用轉錄本來的 `\n\n` 分段邊界，單一分段就超長時才硬切。

- **只有一段時直接送原文**，不做「摘要後再整理」——對短會議而言那等於資訊被壓縮兩次，反而讓品質下降。多數會議都落在這條路徑。
- 多段時逐段摘要（map）後以 `【第 N 段】` 標記合併，再套使用者選的提示詞產出最終會議紀錄（reduce）。

`PromptVariableHelper` 新增 `Render`，是 `{{transcript}}`／`{{meetingTitle}}`／`{{meetingDate}}` 自 0.4.26 定義以來的第一個代入端。**找不到對應值的佔位符原樣保留**，與既有「未知變數只提醒、不阻擋」的立場一致——悄悄代入空字串會讓範本作者看不出哪裡沒生效。

輸出語言在共用的 system prompt 中強制為繁體中文（台灣用語）。

### 四、`/projects` 頁面改版

由標準的分頁表格 CRUD 改為以專案為中心的操作介面：

- 頂端專案選擇器（可搜尋）＋ 新增／編輯／刪除三顆 icon 按鈕。
- 專案摘要列：負責人／期程／狀態／完成度／會議紀錄份數。
- AI 區塊：逐字稿下拉（已被其他專案取用的不可選並標示歸屬）＋ 提示詞下拉 ＋「AI 轉會議紀錄」。
- 歷史會議紀錄清單，可檢視、編修草稿與預覽逐字稿。

**副作用**：原本的分頁、分類過濾、團隊過濾與關鍵字搜尋隨表格一起移除，改以下拉的搜尋替代。專案數量成長到數百筆時這個版面要重新檢討。

Icon 一律改用 Material Icons Outlined，不再使用 emoji（➕🔄❌🔍）。

### 五、背景寫入的保護

`MeetingService.UpdateAsync` 與 `MeetingRepository.UpdateAsync` 的「沿用資料庫既有值」清單加入七個 `Draft*` 欄位，比照既有的媒體與轉錄欄位——否則畫面上的舊複本存檔時會把背景生成寫入的草稿清空。`ProjectId` 刻意不列入保護，歸屬本來就要能從畫面改。

`Program.cs` 啟動時比照轉錄，把殘留的 `DraftStatus == Processing` 改判為「失敗」。

## 已知限制

- **提示詞的團隊權控落差**：既有的 `GetAllEnabledNamesAsync()` 只回名稱且沒有團隊過濾。本次另外新增 `GetEnabledSelectableAsync()` 帶 Id 並套用 `BuildTeamAccessPredicate`，舊方法維持原狀給既有呼叫端使用。
- **不做成本控管**：不計 token、不設每日配額。日後要加需新增設定欄位並同步 [日誌與設定檔說明](../operations/日誌與設定檔說明.md)。
- **不保留草稿版本歷程**：重新產生即覆蓋，畫面上會先跳確認對話框。
- **待辦事項抽取尚未實作**：Wireframe 規劃的「AI 同時抽出待辦」需等 TodoList 頁面上線後再接。
