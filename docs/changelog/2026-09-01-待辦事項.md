## 變更目的

[會議記錄流程 Wireframe 設計規格](../superpowers/specs/2026-08-31-meeting-flow-wireframe-design.md) 規劃的四個畫面中，TodoList 是唯一完全不存在的一塊，也是使用者最初點名的三個核心功能之一。

0.4.24 曾有結構高度相似的 `MyTask`（表名 `MyTas`）被移除（migration `RemoveTaskAndMeeting`），理由是「與專案項目高度雷同，留著只是三份幾乎相同的樣板」。本次重新引入，但**定位不同**：待辦不是專案的縮小版，而是「會議紀錄產生的行動項目」的落腳處——`MeetingId` 外鍵就是為此預留。

## 變更內容

### 一、資料模型

新增 `Todo` 實體與 migration `AddTodo`（純 `CreateTable`，不影響既有資料表）。

| 關聯 | 刪除行為 | 理由 |
|------|----------|------|
| `Project` → `Todo`（必填） | **Cascade** | 沒有專案的待辦只會變成沒人管的垃圾資料 |
| `Meeting` → `Todo`（可空） | **SetNull** | 會議紀錄被刪除時待辦保留，只是失去來源 |

兩者都在 `BackendDBContext` 明寫 `OnDelete`——全域迴圈已把所有外部索引鍵預設為 `Restrict`，不明寫就會變成擋住刪除。

**完成狀態只有 `Status` 一個欄位**（待辦／進行中／已完成）。Wireframe 同時畫了「完成勾選框」與「狀態 pill」，但實作上刻意不另存 `IsCompleted` 布林：兩個欄位並存必然會出現「勾了完成但狀態還是進行中」這種互相矛盾的資料。勾選框只是把 `Status` 設為「已完成」的快捷鍵；取消勾選則退回「進行中」而非「待辦」——已經動過的事情退回未開始並不合理。

### 二、分層與註冊

比照 `PromptTemplate`（0.4.26）建立完整分層：Entity、AdapterModel、三支 DTO、Service、Repository、Controller、Page 與 View。

宣告式註冊七處（漏任何一處都不會編譯失敗，但功能會壞）：
`MagicObjectHelper.角色_待辦事項`、`RolePermissionService` 權限矩陣、`SidebarMenuService.MenuPermissionMap[22]`、`Menu.json`（icon `checklist`）、`MenuIconTests.AllowedIcons`、`_Imports.razor`、`ServiceCollectionExtensions`。

`DataRequest` 新增 `ProjectFilter` 與 `StatusFilter` 兩個欄位供清單過濾使用。

### 三、需要注意的實作細節

- `TodoAdapterModel.Clone()` **深拷貝** `Categories`／`Teams` 清單。被刪除的 `MyTask` 當年是淺拷貝，編輯中的修改會回寫到清單資料列——這是已知的 bug，不再重蹈。
- `MeetingId` 不開放從畫面或 API 覆寫，`TodoService.UpdateAsync` 與 `TodoRepository.UpdateAsync` 都沿用資料庫既有值。
- API 新增後會重新載入實體才回傳，否則回應的 `ProjectTitle`／`MeetingTitle` 會是空的（實跑時發現並修正）。
- Icon 一律 Material Icons Outlined，不使用 emoji。

## 已知限制

- **AI 抽出待辦尚未實作**。`MeetingId` 欄位已備妥，但目前所有待辦都是手動新增，來源顯示「— 手動新增」。
- **團隊標籤不會跟著專案改**。Todo 自己帶 `Categories`／`Teams`（與其他模組一致），專案改了團隊，底下的待辦不會自動跟著改。
- **不連動專案完成度**。待辦數量與專案進度未必成正比，自動換算反而變成假資訊。
