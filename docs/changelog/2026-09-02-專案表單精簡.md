## 變更目的

使用者要求新增專案的表單不要「專案描述、優先級、分類、團隊」四個欄位——這些對他的實際流程沒有用處。

原本同一批需求還包含「不用有專案附件」，但討論後**使用者改變主意要保留附件**：他想把合約之類的文件放在專案附件，日後讓 AI 查詢。因此**附件功能完全沒有動**。

## 變更內容

`Components/Views/Projects/ProjectViewView.razor` 移除四個 `FormItem`。表單剩下：標題、開始日期、結束日期、狀態、完成百分比、負責人、專案附件。

`ProjectViewView.razor.cs` 一併清掉**因此變成孤兒**的成員：`availableCategories`／`availableTeams` 兩個欄位、建構式注入的 `CategoryService`／`TeamService`、`OnInitializedAsync` 載入選項的兩行、`PriorityOptions` 屬性，以及 `OnRecordCategoriesChanged`／`OnRecordTeamsChanged` 兩個 handler。

**刻意不動**：`Project` 實體與 `ProjectAdapterModel` 的欄位與預設值、`ProjectService` 全部邏輯、`TagStringHelper`、AutoMapper、`ProjectCreateUpdateDto`（API 路徑仍可寫入這四個欄位）、`DataRequest`、**專案附件全部程式碼**。沒有 migration。

`ProjectAdapterModel.CategoriesText`／`TeamsText` 在 0.4.31 表格移除後就已是死碼，不是本次造成的孤兒，依慣例未刪。

## ⚠️ 優先級的陷阱

`Priority` **雖然從表單移除，但仍是 `[Required]`**，而且 `ProjectService.ValidateBusinessRulesAsync` 會驗證它必須是 `低/中/高` 之一。所以 `OnAddAsync` 保留了帶入預設「中」的那行：

```csharp
// 優先級已從表單移除，但仍是必填且服務層會驗證合法值，因此在此帶入預設「中」。
Priority = ProjectAdapterModel.PriorityOptions[1],
```

**動這段程式碼時不能把預設值拿掉**，否則所有新增／修改都會被擋下並回「專案優先順序不合法。」編輯既有專案時 `Priority` 從資料庫讀回原值，不受影響。

## ⚠️ 已知的權限副作用（刻意為之，非 bug）

`Project.Teams` 是專案唯一的列權限來源，共 **6 處**在用：`ProjectService` 4 處（清單、單筆、附件下載守門、`GetSelectableAsync`）、`MeetingService.RequestDraftAsync`、`TodoService.BeforeAddCheckAsync`。

移除表單欄位後：

- **新建的專案一律公開**，任何有「專案項目」頁權限的人都看得到。
- **既有已設團隊的專案，只要被編輯一次就會被清成公開。** `ProjectService.UpdateAsync` 用表單值覆寫 `Teams`，而表單移除後傳入的是空 List，`TagStringHelper.ToStored([])` 回傳 `null`，而 predicate 視 `null` 為公開。
- 連帶影響：選到專案就能看該專案下的歷史會議紀錄、預覽逐字稿、匯出 Markdown；`RequestDraftAsync` 與 `TodoService` 的專案守門對公開專案永遠通過。

**第二點與 0.4.35 會議紀錄那次不同**——那次舊資料完全不受影響，這次會回溯。動工前已明確告知使用者這個差異，使用者仍選擇整組移除（「不太需要用到團隊這個欄位」）。

服務層 6 處判斷與資料庫欄位全部保留未動。要恢復控管只需把表單的團隊 `Select` 加回去，服務層一行都不必改。

## 實作備註（給後續維護）

- 用 `perl -0pi` 做多行取代時，本 repo 的 `.cs` 檔是 **CRLF**，`\n` 匹配不到，要寫 `\r?\n`。
- 用 `sed -i '起,迄d'` 連續刪多段時，**每刪一次行號就位移**。本次因此誤刪過建構式的 `ModalService` 參數（先刪了前面的行導致後面行號位移）。多段刪除一律改用字面內容取代，或由**檔尾往檔頭**刪。
