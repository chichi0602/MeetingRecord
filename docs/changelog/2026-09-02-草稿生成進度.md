- 文件版本：1.0
- 文件狀態：已實作

- 首次實作版本：0.4.38
- 最後核對日期：2026/09/02

## 變更目的

使用者要求「選逐字稿後的生成狀態也要有進度百分比，如會議記錄那邊一般」——把 0.4.36 為語音轉錄做的進度通知器，同樣套到 AI 產生會議紀錄的流程上。

原本專案頁完全沒有自動更新：生成成功的提示語直接寫著「請稍後重新整理查看結果」。

## 為什麼進度同樣不進資料庫

理由與 0.4.36 完全相同：進度只在工作進行中有意義；通知器是 Singleton，跨 circuit 與頁面重新整理都還在；`Program.cs` 啟動時已會把殘留的 `DraftStatus.Processing` 標記為失敗，不會留下卡住的百分比；最終狀態本來就存在 `Meeting.DraftStatus`。

**因此沒有 migration，也不必動 `MeetingService.UpdateAsync` 的「沿用資料庫既有值」清單。**

## ⚠️ 進度粒度天生很粗，這是誠實的

- `TranscriptChunker.DefaultMaxChars = 12000`——逐字稿要**超過 12000 字元（約一小時以上的會議）才會分段**做 map-reduce。
- `AzureOpenAiTextGenerationProvider` **沒有串流**（一次 POST 讀完整個 body），拿不到 token 級進度。

所以**多數會議根本不會經過分段階段**，實際路徑是 `0 → 5 → 70 → 100`，會在 70% 停留到完成。

這點在動工前已明確告知使用者，使用者選擇「照做，與轉錄一致的誠實粗粒度」。**沒有拿經過時間去內插假進度**——那會出現「跑到 95% 卡很久」或「還沒到 100% 就完成」。面板改以階段文字（讀取逐字稿與提示詞／分段摘要中（第 N/M 段）／產生會議紀錄中）讓使用者知道目前在做什麼，而不是靠數字。

## 一、通知器

新增 `Business/Services/TextGeneration/MeetingDraftProgressNotifier.cs`，形狀比照 `TranscriptionProgressNotifier`（Singleton、`ConcurrentDictionary`、`event Action? Changed`、`Report*` 對不存在的 Id 直接忽略）。

```csharp
public enum MeetingDraftPhase
{
    Queued = 0,       // 已排入佇列
    Preparing = 1,    // 讀取提示詞範本與逐字稿
    Summarizing = 2,  // 逐段摘要（map，只有長逐字稿會走）
    Generating = 3,   // 產生會議紀錄（reduce 的單次 LLM 呼叫）
    Completed = 4,
    Failed = 5,
}
```

`CalculatePercent` 純函式：

```
Queued       → 0
Preparing    → 5
Summarizing  → 5 + 65 × 已完成段 / 總段數   （分段摘要佔 5~70，剛好接上 Generating）
Generating   → 70
Completed    → 100
Failed       → 停在中斷當下
```

## 二、回報點

| 位置 | 呼叫 |
|------|------|
| `MeetingService.RequestDraftAsync` | `Enqueued`（在 `EnqueueAsync` **之前**——背景工作要等輪到才知道，先登錄畫面才立刻看得到「排隊中」） |
| `MeetingDraftJobRunner` 標記 Processing 後 | `ReportPreparing` |
| `CondenseAsync` 取得總段數時 | `ReportSummarizing(meetingId, 0, chunks.Count)` |
| 段迴圈內 | `ReportSummarizing(meetingId, index + 1, chunks.Count)` |
| 最終 `GenerateAsync` 之前 | `ReportGenerating` |
| 寫回完成後 | `ReportCompleted` |
| `MarkFailedAsync` | `ReportFailed` |

⚠️ 段迴圈的回報必須放在 `GenerateAsync` 回傳之後、**`continue` 之前**。空白摘要會 `continue` 跳過，寫在迴圈尾端會漏計——與 0.4.36 轉錄那次是同一個陷阱。

## 三、面板合併（不是新做第二個）

轉錄面板與生成面板都固定在右下角，各做一個會**直接重疊**。因此把 0.4.36 的 `TranscriptionProgressPanel` 泛化為 **`BackgroundJobProgressPanel`**（以 `git mv` 改名，保留歷史）：

- 同時注入兩個通知器，各自取快照後轉成面板內部的 `private sealed record JobRow`，合併顯示
- 每列以圖示區分工作類型：轉錄 `graphic_eq`、生成會議紀錄 `auto_awesome`；階段文字前面也標明類型
- 標題改為「處理中（N）」
- **進行中的排在前面**，避免仍在跑的工作被一堆已完成項目擠下去
- 同一筆會議可能同時有轉錄與生成兩種工作，所以 `@key` 用 `{Kind}-{MeetingId}` 而非單純 Id
- CSS class 前綴 `transcription-panel-` → `job-progress-panel-`
- 仍以 `TagStringHelper.IsTeamAccessible` 過濾兩邊的項目

`JobRow` 刻意做在 Web 層的面板裡：這樣兩個 Business 層通知器可以維持各自獨立的語意型別，不必為了共用畫面去抽共同介面。

## 四、專案頁的即時百分比與自動翻狀態

`ProjectViewView` **新增 `IDisposable` 實作**（原本沒有），訂閱 `Changed`、`Dispose` 解除。

- 進行中只 `StateHasChanged`，百分比直接讀記憶體
- 工作結束才 `ReloadProjectContextAsync()`，讓「狀態」欄翻成已完成／失敗
- 用 `HashSet<int>` 記住已處理的 Id，否則之後每次進度變動都會再重載一次；判斷用 `Count` 而非 `Any`（`Any` 會短路，漏掉同時完成的其他筆）

歷史會議紀錄的狀態欄在生成中時，於徽章旁附上百分比，Tooltip 顯示目前階段。生成成功的提示語也從「請稍後重新整理查看結果」改成「可在右下角看到進度，完成後清單會自動更新」。

## 實作備註（給後續維護）

- 兩個通知器都是 Singleton 且不注入任何 Scoped 服務，沒有 captive dependency 問題。
- `ProjectViewView` 從此有 `IDisposable`——日後若再加事件訂閱，記得一起在 `Dispose` 解除。
- `Program.cs` 的啟動復原只處理 `DraftStatus.Processing`，**`Pending` 沒有被處理**。重啟時停在「待處理」（已入列但 worker 還沒取走）的紀錄會永遠卡著，只能靠使用者重新按一次「AI 轉會議紀錄」。這是 0.4.31 就存在的既有問題，本次未處理。
