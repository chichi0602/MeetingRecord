## 變更目的

使用者要「轉錄狀態除了待處理，還要看得到處理進度百分比」，並指定形式：**類似雲端硬碟右下角的上傳進度**——常駐顯示百分比、完成後打勾，且清單的轉錄狀態自動翻成已完成。

原本清單頁**完全沒有自動更新**：`ReloadAsync` 只由初始化、🔄 按鈕、搜尋/分頁/排序與增刪改觸發，所以轉錄跑完要自己按重新整理才看得到。

## 為什麼進度不進資料庫

一開始的直覺是在 `Meeting` 上加 `TranscriptionProgressPercent` 欄位，但那是不必要的：

- 進度**只在工作進行中有意義**，跑完就只剩最終狀態，而最終狀態本來就存在 `TranscriptionStatus`。
- 通知器是 Singleton，**跨 circuit、跨頁面重新整理都還在**，行為和雲端硬碟一致。
- 行程重啟時 `Program.cs` 的啟動復原**已經**會把殘留的「處理中」標記為失敗，所以不會留下卡住的百分比。

結論：**不需要 migration、不需要動 `MeetingService`／`MeetingRepository` 的「沿用資料庫既有值」清單**，改動面小很多。

## 一、通知器

新增 `Business/Services/Transcription/TranscriptionProgressNotifier.cs`，形狀比照既有的 `TranscriptionQueue`（Business 層、Singleton、行程內）。

```csharp
public interface ITranscriptionProgressNotifier
{
    event Action? Changed;
    IReadOnlyList<TranscriptionProgressItem> GetSnapshot();
    TranscriptionProgressItem? Find(int meetingId);
    void Enqueued(int meetingId, string title, string? teams);
    void ReportConverting(int meetingId);
    void ReportSegment(int meetingId, int completedSegments, int totalSegments);
    void ReportCompleted(int meetingId);
    void ReportFailed(int meetingId, string message);
    void Dismiss(int meetingId);
}
```

內部是 `ConcurrentDictionary<int, TranscriptionProgressItem>`。項目一併存 `Teams`，讓面板不必回資料庫就能做可見性過濾。

### 百分比怎麼算

轉錄固定切 **15 分鐘一段**（`FfmpegMediaConverter.SegmentSeconds = 900`），而 `AzureOpenAiTranscriptionProvider` 一段一個 HTTP POST、沒有串流，所以**「段」是進度的最細粒度**。

ffmpeg 轉檔本身是一次阻塞呼叫、沒有進度回呼，長檔在這階段可能跑很久。若不特別處理，畫面會一直停在 0%。因此轉檔獨立佔 `ConvertingPercent = 5`，其餘按段數分配：

```
排隊中     → 0
轉檔中     → 5
轉錄中     → 5 + 95 × 已完成段 / 總段數
完成       → 100
失敗       → 停在中斷當下的進度
```

換算抽成 `public static int CalculatePercent(...)` 純函式，比照 `TranscriptChunker`／`MeetingMarkdownExporter` 的可測慣例。

**短音檔（15 分鐘以下）只有一段，進度必然是 5% → 100%**，中間沒有東西可報。這是誠實的粗粒度，沒有拿經過時間去內插假進度。畫面另外顯示「第 N/M 段」，讓使用者看得出粒度從何而來。

## 二、回報點

| 位置 | 呼叫 |
|------|------|
| `MeetingService.SaveMediaAsync` | `Enqueued`（在 `EnqueueAsync` **之前**——背景工作要等輪到才知道，先登錄畫面才立刻看得到「排隊中」） |
| `MeetingService.RequeueTranscriptionAsync` | `Enqueued` |
| `TranscriptionJobRunner` 轉檔前 | `ReportConverting` |
| 段迴圈內 | `ReportSegment` |
| 完成處 | `ReportCompleted` |
| `MarkFailedAsync` | `ReportFailed` |

⚠️ `ReportSegment` 必須放在 `TranscribeAsync` 回傳之後、**`continue` 之前**。整段空白（無人說話）的段落會 `continue` 跳過，寫在迴圈尾端會漏計。

## 三、常駐通知面板

新增 `Components/Commons/TranscriptionProgressPanel.razor(.cs/.css)`，掛在 `MainLayout`——轉錄是背景工作，離開會議紀錄頁也要看得到。

- 右下角固定卡片，可收合、可逐筆關閉或全部關閉
- 每列：標題 + `<Progress Type="Line" Size="Small">` + 百分比 + 階段文字（排隊中／轉檔中／轉錄中（第 N/M 段）／已完成／失敗）
- 完成顯示 ✓（`check_circle`），失敗顯示紅色 `error` 並以 Tooltip 帶出訊息
- 沒有任何項目時整個面板不渲染
- 訂閱 `Changed`、實作 `IDisposable` 解除訂閱，照 `MainLayout` 既有的訂閱/解除慣例

**面板會以 `TagStringHelper.IsTeamAccessible` 過濾**：通知器是全行程共用的，不過濾會把受團隊限制的會議標題顯示給看不到那筆資料的人。0.4.35 之後新建的會議沒有團隊（視為公開），這道過濾主要是保護既有舊資料。

## 四、清單頁的即時百分比與自動翻狀態

`MeetingViewView` 訂閱同一個通知器：

- **進行中**：只 `StateHasChanged`，百分比直接讀記憶體，不查資料庫
- **工作結束**：才 `ReloadAsync()`，讓「轉錄狀態」翻成資料庫裡的已完成／失敗

已完成的項目會留在通知器裡直到使用者關閉，所以用 `HashSet<int>` 記住已處理過的 Id，否則之後**每一次**進度變動都會再重新載入一次。判斷用 `Count` 而非 `Any`——`Any` 會短路，同時完成的其他筆會被漏掉。

轉錄狀態欄在進行中時，於徽章旁附上百分比，Tooltip 顯示目前段數。

## 實作備註（給後續維護）

- `Changed` 由**背景執行緒**引發。訂閱端一律要 `InvokeAsync(StateHasChanged)` 切回 UI 執行緒，並在 `Dispose` 解除訂閱，否則元件被回收後事件仍握著參考。
- 沒有 captive dependency 問題：Singleton 的通知器不注入任何 Scoped 服務，方向是 Scoped（`MeetingService`、`TranscriptionJobRunner`、元件）注入 Singleton。
- `.razor.css` 是 scoped，AntDesign `Progress` 由子元件渲染拿不到 scope 屬性，樣式要用 `::deep`。
- 應用程式重啟後才輪到的殘留工作沒有經過 `Enqueued`，`Report*` 對不存在的 Id 會直接忽略，不會憑空生出沒有標題的項目。
