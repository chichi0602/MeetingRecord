# 生成進度串流、逐字稿雜訊過濾、完成度滑桿（0.4.42）

- 文件版本：1.0

- 首次實作版本：0.4.42

## 變更目的

實機測試時回報三件事：

1. 會議紀錄的處理進度不夠即時——「5% 之後不會動，馬上就跳 70，然後突然又完成」。
2. 專案項目的逐字稿預覽裡出現一大段英文提示詞。
3. 編輯專案的「完成百分比」希望能用拉的。

---

## 一、生成進度改用串流

### 5 → 70 → 100 不是 bug，是既有設計的必然結果

[0.4.38 的 changelog](2026-09-02-草稿生成進度.md) 就已載明實際路徑是 `0 → 5 → 70 → 100`，並把原因歸給「供應商沒有串流」。

**這個歸因是錯的。** Azure OpenAI 的 chat completions 一直支援 `stream: true`；真正的情況是 `AzureOpenAiTextGenerationProvider` 沒有開它，一次 POST 讀完整個 body，所以那次動輒數分鐘的呼叫中途沒有任何可回報的訊號。

### 為什麼是串流，不是用時間內插

0.4.38 明確拒絕過「拿經過時間去內插假進度」，理由是會出現「跑到 95% 卡很久」或「還沒到 100% 就完成」。這個判斷仍然成立，所以這次沒有改用時間曲線，而是去把**真訊號**拿出來：串流之後「目前已產生多少字」是實際觀測到的量，不是猜的。

### 實作

| 檔案 | 變更 |
|------|------|
| `Services/TextGeneration/ITextGenerationProvider.cs` | `GenerateAsync` 多收一個 `Action<int>? onCharactersGenerated` |
| `Services/TextGeneration/AzureOpenAiTextGenerationProvider.cs` | payload 加 `stream: true`；改 `HttpCompletionOption.ResponseHeadersRead` + 逐行讀 SSE；`ExtractContent` 換成 `ExtractDelta` |
| `Services/TextGeneration/MeetingDraftProgressNotifier.cs` | `MeetingDraftProgressItem` 加 `GeneratedCharacters`；新增 `ReportGeneratedCharacters`；生成階段改漸近曲線 |
| `Services/TextGeneration/MeetingDraftJobRunner.cs` | 最終生成呼叫接上回呼；分段摘要傳 `null` |
| `Components/Commons/BackgroundJobProgressPanel.razor.cs`、`Components/Views/Projects/ProjectViewView.razor.cs` | 階段文字改為「產生會議紀錄中（已產生 N 字）」 |

**用 `Action<int>` 而不是 `IProgress<int>`**：`Progress<T>` 會捕捉 SynchronizationContext 改用非同步派送；這裡呼叫端在背景執行緒、接收端（通知器）本身 thread-safe，同步呼叫即可，不必多繞一層。

### 進度曲線

```
百分比 = 70 + 29 × 字數 ÷ (字數 + 900)
```

| 已產生字數 | 百分比 |
|---|---|
| 0 | 70% |
| 300 | 77% |
| 900 | 84% |
| 2000 | 90% |
| 5000 | 95% |

用**漸近**而非線性，是因為沒有人知道模型最後會產出多少字，**沒有分母可以做線性內插**。漸近曲線只需要「已產生字數」這一個已知量，就能保證單調遞增、一開始爬得快、而且永遠到不了 100%——`100%` 只有 `Completed` 給得出來，避免出現「先衝到 100 再乾等」的失信畫面。

半衰值取 900 是因為一般會議紀錄約落在 800～2500 字。

### 節流靠百分比本身

每個 SSE 片段只有幾個字，逐片引發 `Changed` 會用上百次重繪轟炸 Blazor circuit。

`ReportGeneratedCharacters` 因此**一律更新字典**（畫面下次讀到的就是最新值），但**只有換算出的整數百分比真的變了才通知**。生成階段只有 70～99 這 30 個值，整段生成最多引發 29 次事件。這比「每 N 毫秒通知一次」乾淨——不必挑一個沒有依據的時間閾值，而且天生保證「畫面看得到的變化」與「事件」一對一。

### ⚠️ 逾時的取捨（給後續維護）

`ResponseHeadersRead` 是串流的前提——預設模式會等整個 body 收完才回來，那就沒有「邊收邊回報」可言。

代價是 **`HttpClient.Timeout` 只涵蓋到收到 response headers 為止，讀取串流的階段不再受逾時保護**。掛住的連線只能靠 `CancellationToken` 收掉（背景服務停止時會取消）。這是刻意接受的：原本把逾時拉長本來就是為了「長逐字稿的生成可能耗時數分鐘」，而串流本來就會持續有資料進來。

### `ExtractContent` 是本次變更造成的孤兒

改成串流後沒有任何呼叫端，一併移除，`TextGenerationRequestTests` 的「回應內容取值」區塊改寫成測 `ExtractDelta`。

`ExtractDelta` 對「這一片沒有文字」回傳 `null` 而**不是拋例外**——沒有文字是常態而非異常：Azure 的第一片通常只帶內容過濾註記、最後一片只帶 `finish_reason`。「整段串流下來一個字都沒有」才是失敗，那個判斷留在 `GenerateAsync` 收尾處，維持 0.4.34 以來「沒內容就失敗、不靜靜寫入空草稿」的行為。

## 二、逐字稿裡的英文提示詞

### 那不是我們送出去的

`AzureOpenAiTranscriptionProvider.TranscribeAsync` 只送 `file` 與 `response_format`，**沒有任何 prompt 參數**。

外漏內容裡提到 language list、keyword list、conversation 中的多個 message——這些都是本系統根本沒送的東西，足以佐證：那是 **`gpt-4o-transcribe` 在音檔沒有可辨識語音時，把自己的系統指令當成轉錄結果吐回來**。

這段文字已經寫進逐字稿檔案，所以**不只預覽看得到，產生會議紀錄時也會被當成逐字稿餵給 LLM**，污染輸出品質。這是比畫面難看更嚴重的一半。

### 實作

新增 `Services/Transcription/TranscriptionNoiseFilter.cs`，比照 `TranscriptChunker` 的純函式慣例：

- `IsProviderInstructionLeak(text)`——命中任一標記即成立
- `Strip(transcript)`——以空行切段，**逐段落**過濾後重組

標記共 9 條，全部取自實際觀察到的外漏內容。**刻意讓每個段落各有至少一個標記**：外漏內容本身是多個段落，`Strip` 是逐段落過濾的，只押其中一句會讓其他段落漏網。單元測試以 `[Theory]` 逐段落驗證這件事。

真實的會議逐字稿不會出現這些談論「如何轉錄」的英文句子，誤判機率實質為零。

套用兩處：

1. **寫入端**（源頭）——`TranscriptionJobRunner`：`TranscribeAsync` 回來後，在既有的空白判斷之前擋掉，視同空白段落跳過，並記一筆 Warning（日後才知道模型在漏指令，而不是默默吃掉）。
2. **讀取端**（既有髒資料）——`MeetingFileStore.ReadTranscriptAsync` 回傳前套 `Strip`。這條同時涵蓋逐字稿預覽（專案頁與會議紀錄頁都走 `MeetingService.ReadTranscriptAsync`）與草稿生成的輸入，所以升級前存下來的逐字稿**不必重新轉錄**就會乾淨。

**逐段落而非整份判斷**是關鍵：一份逐字稿是多個轉錄分段接起來的，其中只有沒有語音的那幾段會外漏，其他段落是真實內容，不能一起丟掉。

### ⚠️ 已知副作用

若某筆逐字稿**整份**都是外漏內容（例如純靜音的測試音檔），過濾後會變成空字串：預覽顯示「沒有逐字稿內容」，生成會以「逐字稿為空白」失敗。

**這是正確行為**——那筆音檔本來就沒有語音，先前之所以「有內容」只是因為模型吐了垃圾。

## 三、完成百分比改用滑桿

`ProjectViewView.razor` 的 `AntDesign.InputNumber` 換成 `Slider`，加上 0／25／50／75／100 的刻度標記。

AntDesign 的 `Slider<TValue>` 只支援 `double`，而 `ProjectAdapterModel.CompletionPercentage` 是 `int`，所以 code-behind 放一個 `CompletionPercentageValue` 轉接屬性。`[Range(0, 100)]` 驗證與 `ValidationMessage` 都不動。

刻度文字會掛在滑軌下方，因此外層包一個 `.project-view-completion-slider` 補下方間距，否則會壓到下一個 `FormItem` 的標籤。

## 實作備註（給後續維護）

- 進度百分比的漸近曲線用 `long` 運算。字數逼近 `int.MaxValue` 時，`span * characters` 與 `characters + 半衰值` **兩者都會溢位成負數**，讓百分比變成垃圾值。
- 用 `-p:BaseOutputPath=<暫存>/` 繞開 DLL 鎖定時，**暫存目錄要放在 repo 樹內**。`MeetingRegistrationTests` 與 `MenuIconTests` 會從組件位置往上走去找 `MeetingRecord.Web/Datas/Menu.json`，輸出丟到 `%TEMP%` 會讓這 6 個測試以 `FileNotFoundException` 失敗——那是路徑問題，不是真的壞掉。
