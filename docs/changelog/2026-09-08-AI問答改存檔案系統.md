## 變更目的

`AiChatMessage.Content` 把**每一則提問與每一段 AI 回答的完整文字**寫進 SQLite。
AI 回答動輒數百到數千字，累積下去會讓資料庫膨脹——而這些文字從來不需要被查詢或索引，
只會「整段對話一次讀出來顯示」。

使用者要求把它移到檔案系統，路徑在 `appsettings.json` 指定。
本專案已有現成的對照組：逐字稿走 `MeetingFileStore`，資料庫只留相對路徑，
根目錄取自 `SystemSettings.ExternalFileSystem`。

## 一、為什麼是「移除資料表」而不是「換一個欄位」

使用者選擇**一段對話一個檔**（而不是一則訊息一個檔）。這個決定的連鎖效果很大：

檔案路徑可以由「範圍＋對象 Id」**直接算出來**（`project/3.jsonl`、`meeting/12.jsonl`），
**資料庫連相對路徑都不必存**。而路徑一旦不必存，`AiChatMessage` 剩下的欄位
（`Role`／`AskedBy`／`CreatedAt`）本來就該跟內容放在一起——留一張表只是把一段對話
拆成兩個地方維護。

所以這一版是 `DropTable("AiChatMessage")`，不是加一個 `ContentRelativePath` 欄位。

**既有的對話紀錄直接捨棄，不做搬移**（使用者已確認）。migration 是破壞性的。

## 二、檔案格式

新增設定 `SystemSettings.ExternalFileSystem.AiChatPath`，預設
`C:\temp\MeetingRecord\AiChat`，底下分 `project/` 與 `meeting/`。

**JSONL（一行一則訊息）**，不是單一 JSON 陣列：新增一輪對話只要 append 兩行，
不必把整個檔案讀出來、反序列化、再整個寫回去。

```jsonl
{"role":"user","content":"這次會議結論是什麼","askedBy":"王小明","createdAt":"2026-09-08T14:02:11"}
{"role":"assistant","content":"依據會議紀錄…","createdAt":"2026-09-08T14:02:19"}
```

編碼 **UTF-8 含 BOM**（與逐字稿一致，使用者可能直接用記事本開來看），
中文不做 `\uXXXX` 逃脫（`UnsafeRelaxedJsonEscaping`），否則記事本裡完全看不懂。

### ⚠️ BOM 是這個格式唯一的陷阱

`File.AppendAllTextAsync` 只在檔案位置為 0 時寫前置碼，所以 append 不會重複寫 BOM。
但**讀取時第一行帶著 BOM**，不 `TrimStart('\uFEFF')` 的話第一則訊息會被當成壞行而
**默默消失**——不會拋例外，只是歷史少一則。兩條測試專門守這件事。

## 三、`AiChatStore`

`Business/Services/AiChat/AiChatStore.cs`，形狀比照 `MeetingFileStore`
（`IOptions<SystemSettings>` 取根目錄，禁止直接讀 `IConfiguration`）。

| 方法 | 用途 |
|------|------|
| `AppendTurnAsync` | 把一輪問答接到對話尾端 |
| `ReadHistoryAsync` | 讀出整段對話；不存在回空清單 |
| `TryDelete` | 刪掉整段對話 |
| `CountQuestions` | 儀表板的「AI 問答次數」 |

**註冊為 Singleton**：它沒有 DbContext 相依，而且要持有寫入鎖——同一段對話可能有
兩個人同時提問，併發 append 會讓兩輪對話的行交錯。用
`ConcurrentDictionary<string, SemaphoreSlim>` 依路徑序列化寫入。

磁碟格式用**獨立的 private record**，不直接序列化 `AiChatMessageItem`——
UI 的 DTO 日後若改欄位，不該讓既有檔案讀不出來。

壞掉的行（手動編輯過、寫到一半斷電）**跳過並記 Warning**，不讓整段歷史讀不出來。

## 四、⚠️ Cascade 刪除不再幫我們清理

資料表移除後，刪專案／會議時**資料庫不會再自動帶走對話**。
所以兩個服務要自己刪檔，漏掉就會留下永遠沒人讀的孤兒檔案：

- `MeetingService.DeleteAsync` → `chatStore.TryDelete(AiChatScope.Meeting, id)`
- `ProjectService.DeleteAsync` → `chatStore.TryDelete(AiChatScope.Project, id)`

這與本專案既有的慣例一致（`MeetingService` 刪逐字稿、`ProjectService` 刪附件實體檔）。

## 六、測試

新增 `AiChatStoreTests` 12 筆（既有 485 → **497 全綠**）：

- 一輪問答往返，`Role`／`AskedBy`／順序都正確；回答的 `AskedBy` 必須是 null
- **第一行帶 BOM 也要讀得出來**
- **append 兩輪後 BOM 只出現一次**（要看原始位元組——`File.ReadAllText` 會自動吃掉
  開頭的 BOM，用字串去數永遠是 0，那樣的斷言驗不到任何東西。第一次寫錯就是這樣）
- 含換行、引號、反斜線的回答往返不失真
- 提問會 trim、回答保持原樣
- **專案 12 與會議 12 是不同檔案**，不會互相污染
- 讀不存在的對話回空清單、`TryDelete` 不存在的檔案不拋例外
- 壞掉的行被跳過，其餘仍讀得出來
- `CountQuestions` 只算 `user`；根目錄還不存在時回 0（不能拋例外把儀表板弄掛）

## 七、待實跑驗證

1. 問一題 → `C:\temp\MeetingRecord\AiChat\meeting\<id>.jsonl` 出現兩行
2. 關掉再開問答視窗，歷史還在
3. 再問一題 → 變成四行（append 沒覆蓋、沒重複 BOM）
4. 「清空這段對話」→ 檔案消失
5. 刪掉那個會議／專案 → 對應的 `.jsonl` 也不見了
6. 儀表板的「AI 問答次數」數字正確
7. 用記事本打開 `.jsonl` 不是亂碼
