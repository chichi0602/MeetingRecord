# 逐字稿人工編修與背景工作取消（0.4.55）

- 文件版本：1.0
- 文件狀態：已實作
- 現行系統版本：0.4.55
- 首次實作版本：0.4.55
- 最後核對日期：2026/09/08

## 變更目的

盤點使用體驗時找出兩個**流程斷點**——不是不好看，是使用者走到那裡就沒有路了：

1. **逐字稿完全無法編輯。** 全專案沒有任何更新逐字稿的路徑（只有轉錄時寫入的
   `SaveTranscriptAsync` 與預覽用的 `ReadTranscriptAsync`）。STT 聽錯人名或專有名詞時
   **沒有任何人工介入點**，錯誤會原封不動被 AI 帶進會議紀錄、再帶進匯出的 PDF。
2. **背景工作無法取消，而且進度面板的「關閉」會誤導。** 原本的關閉鈕只是把該筆
   從通知器字典移除，**轉錄照跑**。誤傳一小時的音檔只能等它跑完，並付掉那筆 API 費用。

## 一、逐字稿可編修

### 資料層

`MeetingFileStore` 新增 `OverwriteTranscriptAsync(relativePath, content, ct)`——**就地覆寫**。

刻意不沿用既有的 `SaveTranscriptAsync`：那個方法每次都產生新的 GUID 檔名並回傳新路徑，
是「重新轉錄」的語意；拿來存編輯結果會留下一堆孤兒檔，而且要同步改
`Meeting.TranscriptRelativePath`。

### 服務層

`MeetingService.UpdateTranscriptAsync(meetingId, content, ct)` 回傳 `VerifyRecordResult`，
依序做三道檢查：

| 檢查 | 不通過時 |
|------|---------|
| 會議存在 | 「找不到這筆會議紀錄，可能已被刪除。」 |
| 團隊權控（`TagStringHelper.IsTeamAccessible`）| 「沒有權限編修這筆逐字稿。」 |
| `TranscriptionStatus == Completed` 且路徑非空 | 「目前的轉錄狀態無法編修逐字稿……」 |

第三道是**與重新轉錄的競爭防護**：若使用者開著編修視窗、期間有人按了重新轉錄，
存回去的內容馬上會被新逐字稿蓋掉，等於白改一場。當場擋下並說清楚原因，比事後才發現好。

通過後就地覆寫檔案、更新 `Meeting.UpdatedAt`。

### 介面

**會議紀錄頁與專案項目頁兩邊都能編修**，呼叫同一個服務方法。會議紀錄頁是逐字稿的家，
但「正要產生會議紀錄時才發現錯字」才是最該修的時機，逼使用者換頁是沒必要的摩擦。

原本唯讀的 `<pre>` 改為 `TextArea` ＋「儲存」。`TextArea` 加了 `BindOnInput="true"`
（AntDesign 預設只在失焦時更新值，0.4.52 踩過這個坑）。

### ⚠️ 一個要先講明的副作用

讀取逐字稿時會經過 0.4.42 的 `TranscriptionNoiseFilter`，濾掉供應商外漏的系統指令。
使用者看到並存回的是**過濾後**的內容——等於順手把那段垃圾從檔案裡永久清掉。

這是好事，但不講明的話，日後有人比對檔案大小會誤以為「編輯把內容弄不見了」。

## 二、背景工作可取消

### `JobCancellationRegistry`（Singleton，轉錄與草稿生成共用）

```csharp
public interface IJobCancellationRegistry
{
    void RequestCancel(BackgroundJobKind kind, int meetingId);
    bool TryConsumePendingCancel(BackgroundJobKind kind, int meetingId);   // 還在排隊
    JobCancellationHandle BeginJob(BackgroundJobKind kind, int meetingId, CancellationToken serviceToken);
}
```

`BeginJob` 回傳的 handle 帶著**與服務停止權杖連動**的 `Token`，以及 `IsCancelledByUser` 旗標，
`Dispose` 時解除註冊。

**那個旗標是整個設計的關鍵**：使用者取消與應用程式關機都只會拋 `OperationCanceledException`，
沒有旗標就分不出來，前者該標成「已取消」，後者該留給啟動復原標成失敗。

兩條路徑：

- **還在排隊**：背景服務取出工作後先問 `TryConsumePendingCancel`，是就跳過並標記為已取消。
  標記只能被消耗一次，否則同一筆重新入列還會再被上一輪的標記誤殺。
- **執行中**：`RequestCancel` 直接對已註冊的 CTS `Cancel()`，runner 的 catch 依
  `IsCancelledByUser` 決定標成「已取消」還是「失敗」。

### 新增 `Cancelled` 狀態，不沿用 `Failed`

`TranscriptionStatus` 與 `DraftStatus` 各加 `Cancelled = 5`。
**列舉以 int 儲存，不需要 migration。**

沿用 `Failed` 會把使用者主動取消顯示成紅色的「失敗」，那是說謊。各頁的狀態樣式
**刻意用中性灰**（`-status-none`），不是紅色——取消是中性結果，不是錯誤。

`Program.cs` 啟動時把殘留 Processing／Pending 標記為失敗的邏輯**維持不動**：
那些是真的沒人接手的孤兒，不是使用者取消的。

### 介面

`BackgroundJobProgressPanel` 進行中的項目多一顆「取消」。**同時修正既有的誤導**——
關閉鈕的文案依狀態而定：

```csharp
private static string CloseButtonLabel(JobRow job)
    => job.IsRunning ? "關閉通知（工作會繼續執行）" : "關閉這一筆";
```

## 三、測試

新增 19 個測試（既有 466 → 485 全綠）：

- `JobCancellationRegistryTests` × 7——排隊標記只能消耗一次、不跨工作種類外洩、
  `BeginJob` 會清掉殘留標記、執行中取消會讓 `IsCancelledByUser` 為真、
  **關機取消不會讓它為真**、`Dispose` 後解除註冊、取消不存在的工作不拋例外
- `MeetingServiceTests` 逐字稿人工編修 × 7——就地覆寫且路徑不變、`UpdatedAt` 有更新、
  三種非 `Completed` 狀態都拒絕且檔案未被動、跨團隊拒絕、會議不存在時不拋例外
- `StatusTextTests` × 5——兩個列舉的「已取消」文字，以及
  **每個已定義成員都不能落到 `_ => "未知"`**（漏補顯示文字時不會有編譯警告，只會默默顯示「未知」）
