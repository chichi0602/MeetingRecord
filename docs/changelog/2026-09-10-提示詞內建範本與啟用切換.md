# 提示詞內建範本、啟用狀態就地切換、移除分類與團隊過濾（0.4.64）

- 文件版本：1.0
- 文件狀態：已實作
- 現行系統版本：0.4.64
- 首次實作版本：0.4.64
- 最後核對日期：2026/09/10

## 變更目的

使用者指出：**新使用者拿到的提示詞清單是完全空白的**。而提示詞是「AI 轉會議紀錄」的
必要輸入（`MeetingService.RequestDraftAsync` 沒有提示詞就直接拒絕），所以空清單等於
核心功能不能用——使用者得自己從零寫一份提示詞才能開始用這套系統。

一併提出的三件介面調整：分類與團隊過濾用不到、啟用狀態要能直接點擊切換。

盤點時另外發現一個**現存的分頁缺陷**，與本次一併處理（範圍見第五節）。

## 一、內建範本目錄

新檔 `MeetingRecord.Business/Helpers/PromptTemplatePresets.cs`，五份範本：

| 名稱 | 用途 |
| --- | --- |
| 標準會議紀錄 | 會議資訊、摘要、討論事項、決議、待辦表格、待釐清事項 |
| 逐字稿重點條列 | 只做重點摘要，不拆解決議與待辦（演講、教育訓練） |
| 決議與待辦事項 | 只抽決議與待辦，含負責人／期限／優先序 |
| 客戶訪談紀要 | 訪談對象、現況、痛點、需求與期待、顧慮、後續行動 |
| 一頁摘要 | 500 字以內，供沒參加會議的主管快速掌握 |

放 `Helpers/` 而不是 `Services/DataAccess/`——後者清一色是持有 `BackendDBContext` 的
`*Service`，而同領域的 `PromptVariableHelper` 就在 `Helpers/`。

**純靜態內容**：不進資料庫、entity 也沒有 `IsBuiltIn` 之類的欄位。建進去之後就是一般的
提示詞資料，使用者可自由修改或刪除。倉庫原本**沒有任何現成的提示詞內容**可用（0.4.26
建了這個功能，但範本一直是要使用者自己寫的），所以五份內容都是這一版新寫的。

### 內容的硬性約束

`PromptTemplatePresetsTests` 守著四條，其中第一條是這次最重要的防線：

1. **每份都必須含 `{{transcript}}`**。`MeetingDraftJobRunner` 只做
   `PromptVariableHelper.Render`，逐字稿**只有**在範本含這個變數時才會被代入——漏了它
   模型會拿到一份沒有逐字稿的指令然後憑空生出一份會議紀錄，**不會報任何錯**。
2. 只用 `PromptVariableHelper.KnownVariables` 裡的變數，否則使用者每次儲存都被彈警告。
3. 長度用 `Validator.TryValidateObject` 跑 `PromptTemplateAdapterModel` 驗證，而不是
   在測試裡硬寫 100／20000／2000——上限改動時只有一個地方要動。
4. 名稱不分大小寫唯一（資料庫的名稱唯一性也是不分大小寫的）。

另外兩條寫在程式註解裡：**不交代輸出語言**（共用 system prompt 已強制繁體中文台灣用語
與「只依逐字稿作答」），以及 `{{meetingDate}}` **可能被代入空字串**（會議沒填日期時），
所以範本要附一句空值時該怎麼寫的指示，不能裸寫「會議日期：{{meetingDate}}」。

## 二、兩個新增入口

工具列左側新增三個控制項，都需要 `PermissionActions.Create`：

- **建立內建範本**：`PromptTemplateService.AddPresetsAsync()`，一次建立全部。
  **冪等**——已存在同名者略過，可以重複按。一次 `AddRange` ＋ 一次 `SaveChanges`。
- **選擇內建範本 ＋ 新增此範本**：只建選取的那一個，走與 Modal 送出相同的
  `BeforeAddCheckAsync` ＋ `AddAsync`，不需要新的服務方法。

### 為什麼一鍵生成放服務層而不是頁面端迴圈

`TodoExtractionModal` 有現成的「頁面端逐筆 BeforeAddCheck ＋ Add」寫法，但那裡的迴圈
是因為候選待辦由 LLM 產出、使用者可先勾選編輯，逐筆結果要各自回報。內建範本是靜態資料，
沒有這個需求。決定性的理由是**測試**：專案沒有 bUnit，放在頁面就是零覆蓋率，而
「重複按不能重複建」正是最需要被守住的行為。

### 為什麼下拉是「選單＋按鈕」兩步式

使用者原本描述的是「一個可以新增指定提示詞的下拉選單」。做成「選了就直接新增」有兩個
實際問題：誤觸就多一筆而且沒有取消機會（WCAG 3.2.2 也不建議改變下拉直接造成寫入），
以及 `AllowClear` 會把 `null` 送進 handler。全站既有的「挑一個再動作」也都是選單配獨立
按鈕的形狀（`ProjectViewView` 的 AI 區塊）。

### 「略過」的訊息刻意講得比較長

**名稱唯一性是全域的、可見性卻是團隊範圍**，所以非管理員有可能拿到「5 筆全部略過」但
清單仍然是空的——撞名的那幾筆屬於別的團隊而看不到。訊息因此寫成「已有同名提示詞；
同名範本可能屬於其他團隊而未顯示在清單上」，只寫「名稱已存在」會被當成系統壞了。

## 三、啟用狀態就地切換

「啟用狀態」欄的膠囊在有 `PermissionActions.Edit` 時變成一顆按鈕，點下去經
`ConfirmAsync` 二次確認後呼叫新的 `PromptTemplateService.SetEnabledAsync(id, isEnabled)`
（照抄 `TodoService.SetCompletedAsync` 的形狀，含團隊權控守門）。

四個刻意的決定：

- **啟用不套 `Danger`、停用才套**。啟用不是破壞性動作；非破壞性確認框不套紅色已有先例
  （`ProjectViewView` 的「確認重新產生」）。
- **沒有 Edit 權限時渲染回純 `<span>`**，不是 `<button disabled>`。disabled 的按鈕
  不可 focus，掛在上面的 `aria-label` 狀態說明就讀不到了。
- **可見文字講狀態、`aria-label` 與 `title` 講動作**。把「啟用」直接當按鈕的可及名稱
  會被讀成命令（「啟用這個」），語意與實際狀態相反。
- **`SetEnabledAsync` 刻意不用 `AsNoTracking()`**。本類其他讀取一律用，但這裡要靠變更
  追蹤把欄位寫回去；順手加上去會變成「什麼都沒寫、卻回傳成功」。註解與測試都守著這點
  （`SetEnabledAsync_NonAdminOutsideTeamScope_ShouldDenyAndKeepOriginalValue` 斷言的是
  資料庫的值沒變，不是只看 `Success`）。

原生 `<button>` 不繼承字型，所以 CSS 補了 `font: inherit` 與 `cursor: pointer`。
這裡不需要 `::deep`——button 是本元件自己寫的元素，scope 屬性選得到。

**已知副作用**：使用者若正以「啟用狀態」欄排序，切換後重載會讓那一列跳到別頁而從眼前
消失。這是排序與資料變更的必然結果，不是缺陷，寫進 PRD 以免被當 bug 回報。

## 四、移除分類與團隊過濾

移除工具列的兩個多選過濾 `Select`（`Values` ＋ `OnSelectedItemsChanged`）、對應的兩個
欄位與兩個事件處理、`DataRequest` 的 `CategoryFilters`／`TeamFilters` 傳值，以及表格的
分類、團隊兩個 `Column`。

**保留**（三者都還被需要，刪了會壞）：

- `availableCategories`／`availableTeams` 與 `CategoryService`／`TeamService` 依賴
  → **編輯 Modal 的分類／團隊 Select 還要用**
- `PromptTemplateService` 內的 `CategoryFilters`／`TeamFilters` 過濾邏輯
  → `DataRequest` 是全站共用型別，待辦清單還在傳，且有測試守著
- `PromptTemplateAdapterModel.CategoriesText`／`TeamsText` → 既有測試在斷言它們

編輯表單的兩個欄位一律保留：**團隊決定這筆提示詞誰看得到**（列級權控），拆不掉。

## 五、順修分頁缺陷（只修這一頁）

`PromptTemplateService.GetAsync` 的 `Take` 原本綁 `if (dataRequest.Take != 0)`，而畫面
傳的是 `Take = 0`——等於**從來沒有分頁**，第 1 頁會列出全部資料。`result.Count` 是在
`Skip`／`Take` 之前算的，所以分頁器的總數與頁數一直是對的，只有內容沒被切，因此一直
沒被發現。

盤點確認**這是全站八支 `*Service.GetAsync(DataRequest)` 共同的寫法，八個呼叫端也全部
傳 0**。與使用者確認後**本次只修提示詞清單這一頁**，其餘七支維持原樣，缺陷與修法記在
`docs/architecture/開發慣例與限制速查.md` §6.2，避免下一個人誤以為是本頁特例。

修好之後浮出一個原本被掩蓋的問題：`_pageIndex` 從來不會被夾回範圍內，停在第 2 頁時把
該頁唯一一筆刪掉就會 `Skip` 掉全部資料而顯示**空白表格**。所以 `ReloadAsync` 尾端補了
夾回最後一頁並重載一次的邏輯。
