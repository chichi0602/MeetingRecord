## 變更目的

使用者對待辦事項頁提出三件事：

1. 右側加一個區塊，可用下拉切換負責人，顯示該人的工作項目與完成度。
2. 移除所有分類、團隊相關欄位與過濾。
3. 「待辦事項」欄不要顯示過長，只顯示大綱，旁邊加資訊小 icon 點開看詳細內容。

第 2 點使用者已確認接受後果：**所有待辦事項將對所有使用者可見**。這與現況一致——待辦必定隸屬於專案，而專案在 0.4.39 就已退出團隊控管；AI 抽出的待辦也從來不填團隊（`TodoExtractionService.ToAdapterModel` 不設標籤），等於一直是公開的。

### migration 的驗證（測試抓不到，只能實跑）

**SQLite 的 `DropColumn` 是 table rebuild，不是 `ALTER TABLE DROP COLUMN`**：EF 會建 `ef_temp_Todo`、只搬保留欄位、`DROP TABLE Todo`、rename、重建索引。而 `CREATE TABLE` 是從**當前 model snapshot** 重新產生的，`Todo` 又有兩條語意不同的 FK，所以必須核對它們在 rebuild 後存活。

用 `dotnet ef migrations script` 讀出實際 DDL 確認（不需要 sqlite3 CLI）：

```sql
CREATE TABLE "ef_temp_Todo" (
    "Id" INTEGER NOT NULL CONSTRAINT "PK_Todo" PRIMARY KEY AUTOINCREMENT,
    ... 共 11 欄，已無 Categories／Teams ...
    CONSTRAINT "FK_Todo_Meeting_MeetingId" FOREIGN KEY ("MeetingId") REFERENCES "Meeting" ("Id") ON DELETE SET NULL,
    CONSTRAINT "FK_Todo_Project_ProjectId" FOREIGN KEY ("ProjectId") REFERENCES "Project" ("Id") ON DELETE CASCADE
);
```

`ON DELETE SET NULL`（Meeting）與 `ON DELETE CASCADE`（Project）都在，兩個索引也重建。套用前已備份 `BackendDB.db` → `BackendDB.db.bak-before-0.4.66`。

⚠️ **`TodoServiceFixture` 用 `EnsureCreatedAsync()` 照 model 直接建表，根本不跑 migration**，所以 migration 寫壞了測試不會變紅。這類驗證只能實跑。

⚠️ 兩則預期中的訊息，不要去「修」：`dotnet ef migrations add` 的 data-loss 警告、以及套用時 `PRAGMA foreign_keys = 0` 無法在交易中執行的警告（rebuild 必然出現）。

## 二、右側各負責人工作量面板

版面改雙欄（左清單、右 320px 面板），內容與設計決策見 [待辦事項 PRD](../prd/待辦事項-prd.md)。這裡只記幾個實作上會踩到的點。

### 服務層拆成兩支，不要合成一支

`GetOwnerSummariesAsync(projectFilter)` 只投影 `Owner`／`Status`／`DueDate` 三個純量欄位算統計；選中某人之後才用 `GetByOwnerAsync(owner, projectFilter)` 撈他那一份。合成一支（讓 summary 直接帶 `IReadOnlyList<TodoAdapterModel>`）會為了顯示一個人而把全表 `Include(Project)` 撈出來、全部映射 AdapterModel，比左邊的清單本身更貴——而左邊那支還有 §6.2 的分頁缺陷會撈全表，等於同一份資料撈兩次。

### 分組鍵一定要 Trim

`Owner` 是自由文字、沒有任何正規化（表單是裸的 `<Input>`）。交給 SQLite 的 `GROUP BY x.Owner` 會把「陳大文」與「陳大文 」算成兩個人，`null` 與空字串也會變成兩組。所以撈回記憶體後才分組，鍵一律 `Trim()`，空白與 null 歸到 `TodoService.UnassignedOwner`（「未指定」）。這是這個功能最可能默默出錯的地方，有三支測試守著。

### 完成度用整數截斷

系統沒有「完成度」欄位（`Status` 是唯一的完成依據），所以只能算「已完成筆數 ÷ 總筆數」。**刻意不四捨五入**：199/200 四捨五入會顯示 100%，看起來像全做完了，是假資訊。`Total == 0` 回 0（有測試守除零）。

### 面板掛在 ReloadAsync 尾端

`OnCompletedChangedAsync`／`OnDeleteAsync`／`OnModalOKHandleAsync` 全都只呼叫 `ReloadAsync()`，所以面板的重載掛在它尾端，與清單同進同出。這樣才不會出現「勾了完成、左邊變了、右邊完成度不動」——那是這個功能最容易被抓包的 bug。

### 面板只跟專案過濾連動

理由見 PRD 的決策表。重點是：套上狀態過濾會讓每個人都 100% 或都 0%，那不是空資料而是**看起來合理的錯誤數字**；而關鍵字搜尋會比對 `Owner` 欄位本身，搜一個人名會讓那個人的完成度變成 100%。面板標題旁顯示目前範圍，免得被當成 bug。

## 三、待辦事項欄改大綱 ＋ 資訊 icon

清單只顯示標題的單行省略（`title` 屬性帶完整標題），描述副標移除；描述非空時右邊多一顆 `CrudActionButton`（`Icon="info"`）開唯讀對話框。

三個實作細節：

- **`text-overflow: ellipsis` 對純 inline `<span>` 無效**。原本的 `.todo-view-title` 沒有 `display`，直接加 ellipsis 不會生效，所以外面包了一層 flex 容器並讓文字成為 `min-width: 0` 的 flex item（`flex item` 預設 `min-width: auto`，長標題會把整欄撐開而不是省略）。
- **對話框放在元件根層、不能放進 `<Column>` 裡**——放欄位內會讓每一列都渲染一個視窗。
- 描述來自 `TextArea`、換行有意義，所以用 `<pre>` 搭 `white-space: pre-wrap` 保留（比照檢視會議紀錄）。

## 四、版面：雙欄 ＋ ScrollX

先算過寬度：1440px 視窗、側邊欄展開時，`1440 − 300（側邊欄）− 48（article margin）− 64（article padding 2rem×2 !important）= 1028`，再扣 320px 面板與 gap 只剩約 692px 給表格。移除兩欄後表格仍有 8 欄 ＋ ActionColumn，扣掉固定寬的「完成」與操作欄，平均每欄只有 77px——「來源會議紀錄」那格會爛掉。

所以表格加了 **`ScrollX="900px"`**，窄容器下橫向捲動而不是把欄位擠爛。

**附帶效果（刻意的）**：`Fixed="ColumnFixPlacement.Right"` 在沒有 `ScrollX` 時本來就是 no-op，全站 9 個清單頁都這樣寫、一直沒生效。加上 `ScrollX` 後**這一頁的操作欄會第一次真的變成 sticky**，外觀與其他 8 頁不同。

**斷點用 1400px 而不是 1200px**：側邊欄收合是 `.page` 上的 runtime class（`--sidebar-width` 300→64px），媒體查詢量的是視窗寬、看不到這 236px 的差，所以同一視窗寬度下無法區分展開與收合。取保守值，配合 `ScrollX`，誤判成單欄也只是要橫捲。刻意不用 `@container`——外層設 `container-type: inline-size` 會建立 containment，AntDesign Table 量 sticky/fixed 欄位時容易出事。

實跑後使用者反映「呈現很好但有點占版面」，以及工具列希望一列排完。

## 四之二、0.4.68 修掉全站的堆疊層級缺陷

使用者回報兩個畫面錯誤：待辦清單的操作欄圖示浮在頁首上、使用者選單的下拉被表頭切掉一半。

### 根因：父層的 z-index 困住了子層

`.top-row`（三個 layout 共用的頁首）是 `position: sticky; z-index: 1`。裡面的使用者選單雖然寫 `z-index: 20`，**但它逃不出頁首建立的那個堆疊脈絡**——整個頁首在頁面層級只有 1。

而 AntDesign 的表格圖層比它高（實際值由 `ant-design-blazor.css` 查出，不是憑印象）：

| AntDesign 元件 | z-index |
| --- | --- |
| `.ant-table-cell-fix-left` / `-right` / `.ant-table-summary` | 2 |
| `th.ant-table-selection-column.ant-table-cell-fix-left` | 3 |
| `.ant-affix` | 10 |
| `.ant-table-resizable .ant-table-resizing` | 99 |
| `.ant-modal-mask` / `.ant-modal-wrap` | 1000 |
| `.ant-message` / `.ant-notification` | 1010 |
| `.ant-dropdown` / `.ant-select-dropdown` / `.ant-picker-dropdown` | 1050 |

所以固定欄（2）蓋過頁首（1）。**這兩個現象的成因是同一個**，只是觸發點不同：

- **下拉被表頭切掉**是既有缺陷，0.4.66 之前就存在（`Fixed="Right"` 的欄位即使沒有 sticky 仍帶 `z-index: 2`）。
- **操作欄浮在頁首上**是 0.4.66 加 `ScrollX` 之後才顯現的——`Fixed` 終於真的生效變成 sticky，於是整欄浮起來蓋住頁首。

### 修法：把外框的層級抽成變數並提高

`app.css` 的 `:root` 新增三個變數，取值要 **> 99**（壓過所有表格內部圖層）且 **< 1000**（對話框、通知、下拉選單仍要蓋在外框之上）：

```css
--z-app-header: 100;          /* .top-row（MainLayout / EmptyLayout / NoFooterLayout） */
--z-app-sidebar-toggle: 101;  /* 側邊欄收合鈕（原本 4） */
--z-app-sidebar: 102;         /* 收合態側邊欄（原本 3） */
```

三個 layout 的 `.top-row` 從 `z-index: 1` 改用 `var(--z-app-header)`。巢狀在裡面的使用者選單（20）與側邊欄彈出選單（40）**不動**——它們只需要贏過各自脈絡內的兄弟，父層修好之後就正確了。

### 全站盤點的結果

掃過所有元件 CSS 的 `z-index` 與 `position: sticky/fixed`，除了上述三處之外沒有第二組問題：

| 位置 | 值 | 判定 |
| --- | --- | --- |
| `.user-menu-dropdown` | 20 | 巢狀在頁首內，父層修好即正確 |
| `NavMenu` 收合態彈出選單 | 40 | 巢狀在側邊欄內，同上 |
| 背景工作進度面板、`#blazor-error-ui` | 1000 | 刻意與 modal 同層，正確 |
| `.login-shell` | 1 | 登入頁自成一頁、沒有表格與下拉，不受影響 |

規則與 AntDesign 的實際數值已寫進 [開發慣例與限制速查](../architecture/開發慣例與限制速查.md) §6.4，連同「`Fixed` 欄位要配 `ScrollX` 才生效」這條——後者是這次會踩到雷的原因。


### 修正過程中自己造成的兩個問題

**收合鈕被側邊欄蓋掉左半邊**：抽變數時把順序寫反了（收合鈕 101 < 側邊欄 102）。收合鈕是用 `transform: translate(-50%, -50%)` 騎在側邊欄右邊界上的，有一半壓在側邊欄上，**必須比側邊欄高**——原本的 3 < 4 就是這個關係。已改回 `--z-app-sidebar: 101` / `--z-app-sidebar-toggle: 102`，並在變數旁註明理由。這類抽變數的重構要特別檢查**相對順序**有沒有被保留，絕對值對了不代表關係對了。

**搜尋框寬度從來沒生效**：工具列改一列後搜尋框仍佔滿整行，把搜尋鈕擠到第三行。原因不是數字設錯，而是

```razor
<Input class="todo-view-search-input" ... />
```

裡的 `class` 是傳給 **AntDesign 元件**的，而 Blazor 的 CSS isolation 只會把 scope 屬性加在 `.razor` 裡自己寫的 HTML 元素上。規則被編成 `.todo-view-search-input[b-dn08df98a0]`（已從 `obj/.../MeetingRecord.Web.styles.css` 確認），渲染出來的 `<input>` 沒有那個屬性 → 永遠選不到，所以它一直是 `.ant-input` 預設的 `width: 100%`。改用 `Style="width: 160px;"`（與旁邊兩個 Select 一致），並刪掉那條已證實無效的 CSS。

⚠️ **全站七個清單頁都有同一條死 CSS**（`MyUserView`／`RoleViewView`／`CategoryViewView`／`MeetingViewView`／`PromptTemplateViewView`／`TeamViewView`／`TodoViewView` 的 `.xxx-search-input { width: … }`），所以七頁的搜尋框實際上都是滿寬。本次**只修了待辦事項頁**，其餘六頁維持原狀待另案處理。

### 實作備註

**`sed` 的全域 pattern 在這個 repo 很危險。** 移除 `AutoMapping.cs` 的 Todo 標籤映射時用 `sed -e '/pattern/d'`，結果把 PromptTemplate 與 Meeting 同形的 `ForMember` 也一起刪掉了（連帶吃掉語句結尾的分號，build 直接紅）——那四個實體的標籤映射寫法逐字相同。已 `git checkout` 還原該檔、改以行號精準刪除。刪測試方法則改用「依方法名稱 ＋ 大括號配對」的腳本，避開 0.4.39 記載的行號位移問題。

**移除 entity 欄位但還沒產生 migration 的中間狀態會讓 app 完全起不來**：EF 10 的 `PendingModelChangesWarning` 會讓 `Program.cs` 的 `Migrate()` 直接拋例外，12 筆 `ApiIntegrationTests` 也會一起紅（它們會啟動真實 host）。這不是錯誤，是提醒 migration 還沒補。

**`dotnet ef` 需要建置啟動專案，所以 app 在跑的時候不能產 migration**（`MSB3027`，檔案被 `MeetingRecord.Web` 鎖住）。`BackendDBContext` 雖然有無參數建構式，但 `OnConfiguring` 在未設定時什麼都不做，所以也不能用 `--startup-project MeetingRecord.AccessDatas` 繞過——要繞就得改 `OnConfiguring` 加一個設計時的 fallback provider，那會讓「未設定的 context」從拋例外變成靜默用本機檔，不值得為了工具方便這樣改。
