# 不必先建專案也能產生會議紀錄（0.4.72 → 0.4.73）

使用者提問：「只想產出會議紀錄、沒有所屬專案的人，該怎麼操作比較好？」

## 問題確認

原本的動線是硬性串行、無法繞過專案的：

1. `/meetings` 上傳影音 → 等轉錄完成
2. **這一頁就沒有後續入口了**——「AI 轉會議紀錄」只存在於 `/projects`
3. 切到「專案項目」，而該頁在沒有選定專案時整個面板都不渲染（`ProjectViewView.razor:76-81`）

所以只想要一份會議紀錄的人，被迫先發明一個專案。

## 意外的好消息：底層早就準備好了

實查之後，這次幾乎是純 UI 工程，**不需要 migration**：

| 已經 null-safe，完全沒動 | 證據 |
| --- | --- |
| `Meeting.ProjectId` | 早就是 `int?`，FK 是 `DeleteBehavior.SetNull` |
| 生成流程 | `MeetingDraftJobRunner` 撈常用名詞前就有 `ProjectId is null` 分支 |
| AI 問答 | `BuildMeetingContextAsync` 只吃 `meetingId`，本來就與專案無關 |
| 匯出 PDF | `MeetingDocumentExporter` 專案名為 null 時退回「未指定」 |
| 可選逐字稿清單 | 本來就不依專案過濾 |

真正的硬綁只有兩處：`RequestDraftAsync` 的 `projectId` 參數，以及「六顆按鈕全關在專案頁」。

## 做法

### 一、`RequestDraftAsync` 的 `projectId` 改為選填

`int` → `int?`。四種情形的行為定義如下：

| 會議目前歸屬 | 傳入 | 行為 | 寫入值 |
| --- | --- | --- | --- |
| 未歸屬 | null | 放行，維持未歸屬 | null |
| 未歸屬 | 專案 A | 放行，歸屬到 A | A |
| 已屬 A | null | **放行，保留原歸屬 A** | A |
| 已屬 A | 專案 B | 拒絕 | 不變 |

**`null` 的語意是「不指定」，不是「解除歸屬」。** 解除是破壞性動作，唯一出口是 `DetachFromProjectAsync`（四道關卡＋紅色二次確認）。讓「產生」這顆按鈕順手靜默解除，等於同一個參數兩種語意。

> ⚠️ **這裡有一個會編譯成功但語意相反的寫法。** 原本的檢查是
> `if (meeting.ProjectId is not null && meeting.ProjectId != projectId)`，
> 改成 `int?` 之後，「已屬 A ＋ 傳 null」會因為 `A != null` 為 true 被判成衝突而拒絕，
> **編譯器不會有任何警告**。必須補上 `projectId is not null &&`。
>
> 同理，專案存在性檢查一定要包在 `if (effectiveProjectId is not null)` 裡——
> `x.Id == projectId`（`int` vs `int?`）在 null 時是 lifted comparison、恆為 false，
> 會讓「不指定專案」一律回「找不到指定的專案項目」。

### 二、新增 `AttachToProjectAsync`：事後補歸屬

只寫 `ProjectId`，**不重新生成、不呼叫任何付費 API**：草稿內容、提示詞快照、與會者快照、生成時間全部原封不動。

驗證項目對照 `DetachFromProjectAsync`，但「已歸屬」拆成兩種訊息——前者重新整理就好，後者得先去原專案移除：

- 已在同一專案 →「這筆會議紀錄已經屬於這個專案，請重新整理後再試。」
- 已屬其他專案 →「這筆會議紀錄已歸屬其他專案，請先從該專案移除後再重新歸屬。」

⚠️ **生成中一樣拒絕，但理由和 Detach 不同。** 技術上不必擋：job runner 全程沒碰過 `ProjectId`，EF 對 tracked entity 只送有變更的欄位，並行的歸屬不會被蓋掉。擋的是**品質語意**——runner 在「開始生成」時就用當下的 `ProjectId` 決定要套哪一份常用名詞，中途歸屬過去的草稿其實沒套到，卻會躺在那個專案的清單裡，看起來像套過了。

> ⚠️ Attach 與 Detach **不是可逆的一對**：Detach 會連草稿一起刪，再歸屬回去也救不回來。這點有測試釘住。

### 三、會議紀錄頁補齊整條動線

「所屬專案」併在會議標題底下當第二行，不另開一欄——操作欄最壞會有 11 顆圖示，橫向空間很緊。另新增「會議紀錄」狀態欄（含即時生成百分比）。

操作欄新增七顆：AI 轉會議紀錄、檢視、編修、匯出 PDF、AI 問答、抽出待辦、歸屬到專案。

- 權限鍵一律用 `角色_會議紀錄`，與頁面守門一致（抽出待辦除外，那顆真正做的事是新增待辦，用 `角色_待辦事項` + Create）
- 「歸屬到專案」不掛 `Danger`——歸屬不是破壞性動作，紅色留給專案頁那顆「從專案移除」
- **專案頁的 AI 面板完全不動**，仍是以專案彙整的視圖；兩個入口共用同一支服務

### 四、抽出待辦仍然需要專案

`Todo.ProjectId` 在資料表層級就是必填、且隨專案 Cascade 刪除。改成可空會連鎖到 6 個以上的檔案，並讓「待辦一定隸屬某專案」這個不變量消失——這次不做。

> ⚠️ 未歸屬時按鈕**刻意保持啟用**，點下去才跳訊息說明要先歸屬。原因：`CrudActionButton` 是 `Tooltip` 包 `Button`，而**停用的 button 不觸發滑鼠事件，Tooltip 永遠不會出現**，提示等於不存在。

## 順手修掉兩個既有缺陷

### 清單的「所屬專案」本來一定是空的

`MeetingService.GetAsync(DataRequest)` 沒有 `.Include(x => x.Project)`，也沒走 `MapWithProjectTitle`，所以 `ProjectTitle` 永遠是 null。而 `ProjectId` 是純量欄位、AutoMapper 有對到——**只有顯示名稱是壞的，按鈕的判斷都對**，所以更難察覺。新欄位一上線就會被看到。

### `UpdateAsync` 會靜默清空 `DraftAttendees`（0.4.71 引入）

`MeetingAdapterModel` 上根本沒有 `DraftAttendees` 屬性，Mapper 一定產出 null，而「從資料庫沿用」的清單裡也沒有它——**在畫面上改個標題，與會者快照就被清掉了**。本次讓會議紀錄頁變成主要入口，觸發機率大增。

同一段的 `ProjectId` 也一併沿用。原註解寫「歸屬本來就要能從畫面改」，但那個前提在 0.4.72 的 `DetachFromProjectAsync` 出現後就不成立了，本次再加 `AttachToProjectAsync` 更是徹底過期——歸屬的權威路徑已經是那兩支方法，不是這張表單。

## 周邊調整

- 儀表板的「未歸屬逐字稿」黃色告警收緊為「未歸屬**且尚未產生會議紀錄**」。本功能上線後「未歸屬但草稿已完成」是正常終態，不收緊的話這個指標會一直告警一個不存在的問題。
- 專案頁下拉的歸屬說明補上「未歸屬 · 重新產生將覆蓋既有會議紀錄」，因為現在會出現「未歸屬但已有草稿」的項目。
- Markdown 樣式改放在 `app.css` 的 `.markdown-content`（全域、不必層層 `::deep`）。專案頁與 AI 問答仍是各自的 scoped 複本，日後要收斂改掛這個 class 即可。
- `AiChatModal` 與 `TodoExtractionModal` 都在 `Views.Projects` 命名空間下，會議紀錄頁以 `@using` 引用。搬到共用目錄比較乾淨，但那會動到專案頁，依外科手術原則不動。

## 驗證

測試 **682 → 697 全綠**（+15），且 **0 支既有測試需要修改**——`int` → `int?` 是隱含轉換，既有呼叫端與 8 支既有測試都照舊編譯。

新增測試涵蓋：真值表四種情形（特別是「已屬 A ＋ 傳 null 要保留 A」那支，釘死上面那個編得過卻語意相反的寫法）、專案不存在仍要拒絕、Attach 的七種情境（含**不得重新入列**這條核心承諾）、兩個既有缺陷的回歸測試，以及 Attach 後再 Detach 會清掉草稿的不對稱行為。
