# AI 用量分析：先建用量帳本，再做分析頁（0.4.79 → 0.4.80）

使用者要一個「Token 用量分析」頁面，內容由我提案。

## 這不是「把既有資料畫成圖」——系統原本完全沒有記錄任何用量

盤點確認：

- 全 repo grep `Usage` / `PromptTokens` / `CompletionTokens` / `stream_options` —— **零命中**
- **沒有裝任何 OpenAI SDK**，兩個 provider 都是手寫 `HttpClient` + 手寫 DTO
- 文字生成的請求 DTO **只有 `messages` 與 `stream`**，`Stream = true` 寫死；回應 DTO **只有 `choices`**
- 轉錄用 `response_format=text`，**回純文字不是 JSON**，連 duration 都沒有
- 14 張資料表沒有任何用量欄位；NLog 的 layout 是純 `${message}`（結構化屬性不會變成欄位），而且只留 30 天

所以範圍是：**先讓系統開始記帳，再做分析頁。**

## 這一版推翻了一項書面決策

`docs/prd/會議紀錄產生流程-prd.md` 兩度決議「**不做 token 計量**」（0.4.31、0.4.65 各一次）。
而 `docs/planning/08-MeetingInk-對標項目決策清單.md` 的 **D11「用量帳本 UsageLedger」** 早就寫著：

> **事後補不回來。** 它同時是成本分析、異常偵測與未來計費的唯一依據。

這一版把 D11 落地，PRD 與決策清單**都已同步更新**。
⚠️ **只有「計量」被推翻**——上限與配額仍然不做，這一版純粹呈現，不擋任何呼叫。

## 一、帳本

一張 `AiUsageLog`，**一次 API 呼叫一列**，永久保留，**不回填**。

⚠️ 「一次使用者動作 = 一次呼叫」是錯的：實際會計費的呼叫有 **5 處，其中兩處是迴圈**——
逐字稿每 12000 字切一段各打一次（map）、音檔每 15 分鐘切一段各打一次。
一趟長會議的生成會寫下 N 筆分段摘要 ＋ 1 筆最終整理。

兩種計費單位共用同一張表：文字生成填 token、轉錄填秒數，另一組留 null。
刻意**不另設單位欄位**——單位由功能別唯一決定，兩個並存必然出現互相矛盾的資料；
分成兩張表則會讓每個查詢都變成 UNION。

### 金額：寫入時算好存起來，連當時的單價一起存

因為單價會變，而這頁最主要的用途是「本月 vs 上月」——歷史若被新單價重算，那個比較就失去意義。
把單價也存進列裡，日後真要修正某段期間的定價，也看得出哪些列受影響。

### ⚠️ 單價沒設定時金額是 null，不是 0

**$0 與「真的沒花錢」看起來一模一樣**，會讓總額靜靜地少報。所以：
帳本存 null、明細顯示「—」、分佈圖那一組標成「未設定單價」、頁面頂端列出「有 N 次呼叫未納入統計」。

這是整個功能最容易無聲出錯的地方，也是唯一有四道防線的地方。

## 二、把用量拿到手

### ⚠️ 串流的 usage 原本會被靜默丟棄

Azure 在串流模式下**預設不回 usage**，要送 `stream_options: {"include_usage": true}`。
但光加這個還不夠——實際錄下來的回應是：

```
倒數第二片  {"choices":[], ... "usage":{"prompt_tokens":8,"completion_tokens":4,"total_tokens":12}}
最後       data: [DONE]
```

帶用量的那一片 **`choices` 是空陣列**，而原本的 `ExtractDelta` 只取 `choices[0].delta.content`，
取不到就 `continue`——**用量會被整片吃掉，而且一切照常運作、沒有任何錯誤訊息**。

所以迴圈改成「一個片段只反序列化一次，**先取 usage 再檢查 delta**」。
另外：開了 `include_usage` 之後中間每一片都明確帶 `"usage": null`，
所以不能用「JSON 裡有 usage 這個欄位」當成「這是最後一片」的判斷。

### ⚠️ 音檔時長：`-loglevel error` 讓 stderr 在成功時完全是空的

原本以為 `FfmpegMediaConverter` 已經捕捉了 stderr、直接解析 `Duration:` 即可。
**實測後發現那是錯的**：`BuildSegmentArguments` 送的是 `-loglevel error`，
而 `Duration:` 是 AV_LOG_INFO 等級——成功路徑上那個 StringBuilder 永遠是空字串。

```
-loglevel error            → stderr 完全空白
-loglevel info -nostats    → Duration: 00:00:05.57, bitrate: 705 kb/s
```

改成 `-loglevel info` 並加 `-nostats`（不加的話每 0.5 秒吐一行進度，三小時的檔會累積上百行，
而那些字串在失敗時會被塞進 `Meeting.TranscriptionError` 顯示在畫面上）。
失敗訊息同時改成只取 stderr **尾端 500 字**。

⚠️ 另一個實測發現：**`Duration:` 那一行不保證有 `start:`**。
regex 押到第一個逗號為止，寫成 `Duration: (.+?), start:` 會在所有一般檔案上解析失敗，
然後靜靜走進推估分支。

**完全沒有動轉錄 API 的回應格式**——逐字稿是這套系統最重要的功能，不值得為了記帳去動它。

### 介面改動

`ITextGenerationProvider.GenerateAsync` 從 `Task<string>` 改成 `Task<TextGenerationResult>`。
⚠️ 刻意**不保留舊多載**：兩個並存時新程式碼會隨手挑到丟棄用量的那一個，而需求是涵蓋**全部**付費呼叫。
這裡的編譯錯誤是資產——它正好把 4 個呼叫點逐一指出來。

### 分層：provider 只回用量，呼叫端寫帳本

只有呼叫端知道 user／meeting／project；而且**失敗是 provider 用拋例外表達的**，
失敗也要記帳，那個 `catch` 本來就只能寫在呼叫端。

### ⚠️ 三個 `continue` 都在「已經付錢」之後

- `MeetingDraftJobRunner`：某一段摘要回空白 → `continue`
- `TranscriptionJobRunner`：指令洩漏被丟棄 → `continue`；整段無人說話 → `continue`

那幾次呼叫**照樣花了錢**，記帳必須放在 `continue` **之前**。
這個專案在「進度回報」上已經踩過同一個坑並留了註解，記帳原地重演了一次。

### ⚠️ 記帳的 SaveChanges 會提交呼叫端未完成的變更

Recorder 與 job runner 共用同一個 scoped `BackendDBContext`。
所以記帳必須放在「修改自己的實體**之前**」——放在後面的話，生成失敗時反而會把半成品寫進資料庫。
有一筆測試專門守這件事。

### 失敗的呼叫：照記，但絕不猜用量

串流中斷時 token 已經被消耗，但 usage 那一片永遠不會到（它在最後）。
所以照樣寫一列、`Outcome = Failed`、**token 與金額全部留 null**。
頁尾固定說明：失敗與取消沒有用量資料，供應商仍可能計費，因此本頁金額是**下限**。

## 三、使用者歸屬：佇列要帶觸發者

⚠️ 生成與轉錄跑在背景服務自建的 scope 裡，那裡的 `CurrentUserService` 解析出來是一個
**空白的** `CurrentUser`（Id=0、Name=""），**不是 null、也不會拋例外**——
讓 runner 自己去問，結果是所有背景呼叫都被默默記到「空白使用者」，而且完全不報錯。

所以兩個佇列從 `Channel<int>` 改成 `Channel<MeetingJobRequest>`，觸發者在入列那一刻就抓下來。

runner 用**尾端選擇性參數**而不是換成請求物件：既有的 11 處
`RunAsync(meeting.Id, CancellationToken.None)` 測試呼叫因此一行都不用改。
假佇列的 `Enqueued` 也刻意維持 `List<int>`，讓既有的 23 處斷言原樣保留。

## 四、頁面

管理員限定，放在「系統管理」選單底下（id 33，`/ai-usage`）。

- 概況卡片：本月估算金額（含與**上月同期**比較）／本月 token（輸入・輸出分開）／本月轉錄時長／本月呼叫次數
- 每日趨勢：文字生成金額 vs 語音轉錄金額，可切 7／30／90 天
- 分佈：依功能別（圓餅）、依模型、依使用者（長條）
- 最近呼叫明細：可篩功能別，**真的會分頁**

### ⚠️ 「上月同期」不是「上月整月」

每月 3 號拿 3 天比 31 天，卡片上會顯示「-89%」，看起來像系統壞了。
另外 3/31 的上個月是 2 月、沒有 31 號——要夾到最後一天，不能讓 `DateTime` 拋例外或滑到下個月。
上期為 0 時變化率回 null（顯示「上月同期無資料」），不是 0% 也不是無限大。

### ⚠️ 圖表元件的數值是 `int`，而且直接印出來

`BarChart` 與 `PieChart` 把 `Value` 原樣輸出，金額以「分」塞進去會顯示成「1234567」。
所以 `ChartSlice` 尾端加了一個**可選**的 `Display`：`Value` 只負責幾何，文字另外給。
位置在最後且有預設值 → 儀表板既有的所有建構**原樣編譯、行為不變**。

`LineChart` 的圖例原本寫死「新增會議／完成紀錄」，改成參數且**預設值就是現值**，儀表板同樣不用改。

圓餅中央的總計另外加了 `textLength` 壓縮：`USD 0.24627` 這種長字串在 52 單位寬的洞裡
會被 viewBox 切成「D 0.246」（實測看到）。

### ⚠️ `dashboard-cards` 借不到

那條規則在 `DashboardView.razor.css` 裡是 **scoped** 的，在別的元件完全不生效——
卡片會變成一張一列（實測踩到）。scoped CSS 沒有共用元件，照既有現況複製一份。

### 明細表的分頁用對的寫法

全站有七支 service 的 `Take` 被包在 `if (dataRequest.Take != 0)` 裡，而呼叫端一律傳 0，
所以它們**從來沒有真的分頁過**（0.4.64 只修了 `PromptTemplateService`）。
帳本是唯一會持續成長的表，直接寫對的版本，不照抄那七支。

## 五、設定

`appsettings.json` 的 `LlmSettings` 新增：

```json
"Currency": "USD",
"Pricing": {
  "gpt-4o-mini":       { "InputPerMillionTokens": 0.15, "OutputPerMillionTokens": 0.60 },
  "gpt-4o-transcribe": { "AudioPerMinute": 0.006 }
}
```

以 **deployment 名稱**為鍵——`Model`／`TranscriptionModel` 設的就是它，帳本記的也是它，三者對得起來。

⚠️ **實際部署用的 deployment 若不在這張表裡，金額會是空白**（而不是 0），頁面頂端會提示。
換模型時記得補一筆。

⚠️ `Pricing` 字典的 `StringComparer.OrdinalIgnoreCase` 寫在**屬性初始化器**裡（與 `Providers` 同樣的寫法）。
寫成 `= new()` 會變成大小寫敏感，`GPT-4o-mini` 查不到單價而靜靜地不計費。

單價為負數會在啟動時被擋下——負成本在圖表上只是看起來「這個月比較省」，沒有任何跡象。

## 六、驗證

測試 **769 → 843**。

### 確認新測試有牙齒

| 故意改壞 | 變紅的測試 |
|---|---|
| 取用量的程式碼移到 delta 的 `continue` 之後 | `GenerateAsync_ShouldReturnBothContentAndUsage`（值變 null——正是那種靜默失效） |
| `Duration:` 的 regex 押上 `start:` | 3 筆時長解析測試 |
| 分段摘要的記帳移到 `continue` 之後 | `RunAsync_ShouldStillRecord_WhenChunkSummaryComesBackBlank` |
| 記帳前先改 `meeting.DraftContent` | `RunAsync_RecordingShouldNotCommitDraftBeforeItIsReady` |
| 加一個欄位但不產生 migration | `ModelSnapshot_ShouldMatchCurrentModel` |

⚠️ 誠實記錄兩件事：

1. **`GetRecentCalls_ShouldReturnEveryRowExactlyOnceAcrossPages` 抓不到「漏了 `ThenByDescending(Id)`」**——
   SQLite 在排序平手時的順序未定義，實務上多半跟著 rowid，所以拿掉 tie-breaker 那筆測試仍然會過（實測過）。
   那個子句留著是因為它本來就正確，不是因為有測試盯著它。
2. **`ToChartCents` 的溢位測試抓到我自己實作裡的真 bug**：上界原本寫在乘以 100 **之後**，
   很大的 decimal 會在乘法那一步就拋 `OverflowException`，根本輪不到夾住。

### 補上一個既有的測試缺口

全部 fixture 都用 `Database.EnsureCreatedAsync()`（照模型直接建表、**繞過 migration**），
而正式啟動走 `Database.Migrate()`。所以「忘了產 migration」原本會讓整套測試全綠，
直到有人跑 App 才在啟動時被 EF 10 的 `PendingModelChangesWarning` 擋下來。
新增 `MigrationSnapshotTests` 補這個缺口，約 15 行。
