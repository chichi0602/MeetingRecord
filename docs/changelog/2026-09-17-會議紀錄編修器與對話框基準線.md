# 會議紀錄編修器、對話框基準線、逐字稿編修移除（0.4.81 → 0.4.82）

使用者要求兩件事，追問後展開成四件：

> 編輯畫面 左邊修改 右邊顯示檢視畫面並且可以快速搜尋+取代
> 同時檢查每個有 dialog 畫面 盡量滿版外圍不要太多空系 然後畫面不要整個滾動 可以滾動顯示的只有 dialog 裡面內容

1. 會議紀錄的編修改成**左改右看**，附常駐的搜尋／取代列
2. **所有**對話框：外圍留白收斂、整頁不可捲、只有內容區可捲
3. 逐字稿的**預覽與編修全部移除**（逐字稿檔案本身保留）
4. 依「有沒有歸屬專案」決定在哪裡編修與下載 PDF

---

## 一、逐字稿預覽與編修：移除

兩頁的預覽鈕與對話框、`MeetingService.ReadTranscriptAsync(int)`／`UpdateTranscriptAsync`、
`MeetingFileStore.OverwriteTranscriptAsync` 全部刪掉，連同 10 筆測試。

### ⚠️ 逐字稿檔案本身沒有消失

`MeetingFileStore.ReadTranscriptAsync(string?)` **不能刪**——`MeetingDraftJobRunner`（生成會議紀錄）
與 `AiChatService`（AI 問答）都在讀它。移除的只有「人看逐字稿」這條路徑。

### `CanPreviewTranscript` → `HasTranscript`

這個旗標**不能**跟著刪：`CanGenerateDraft` 與「AI 問答」按鈕的顯示條件都吃它
（只有逐字稿、還沒生成會議紀錄的會議也問得到，那正是「先問問看再決定要不要花錢生成」最有用的時機）。
留一個叫 Preview、系統裡卻已經沒有 Preview 的屬性比刪掉更糟，所以改名。

### 這是一次真實的功能退步，不是單純的介面精簡

`UpdateTranscriptAsync` 的註解與舊 PRD 都寫著「這是整條流程唯一的人工介入點」。
移除之後，STT 聽錯人名的補救只剩兩條：專案的**常用名詞名冊** ＋ 重新生成（要再付一次生成費），
或直接改會議紀錄（逐字稿裡的錯字留著，下次重新生成又會錯）。
使用說明已照這個現實改寫，沒有假裝什麼都沒發生。

## 二、對話框基準線

### 問題出在三條從未被覆寫的 AntDesign 預設值

```css
.ant-modal      { top: 100px; padding-bottom: 24px; }
.ant-modal-body { padding: 24px; }          /* ← 外圍留白太多的來源 */
.ant-modal-wrap { overflow: auto; }         /* ← 「整頁在捲」的現場 */
```

0.4.69 建了正確的機制（content 是 flex column、只讓 body 捲），但只套在 9 個**表單**對話框上；
唯讀檢視、清單、chat 那些完全沒有 class，於是那兩個抱怨在它們身上完全沒被修到。

### 改法：把基準線本身改對，分級只負責寬度

`FormModalHelper` 掛在 **MainLayout**，全站都吃得到，所以**不需要幫每個 Modal 各補規則**。

| 級別 | 寬度 | 用途 |
|---|---|---|
| `.form-modal-compact` | 680px | 3～4 個欄位、唯讀短清單 |
| `.form-modal-standard` | 880px | 5～8 個欄位、清單型 |
| `.form-modal-wide`（新）| 1080px | 左右分欄的對話式內容（AI 問答）|
| `.form-modal-large` | 90vw | 欄位多、含矩陣或檔案清單 |
| `.meeting-view-modal` | 96vw | 含影音上傳、左右分欄編輯器 |

### ⚠️ `.ant-modal-wrap` 刻意**不**改成 `overflow: hidden`

它會捲是**果**不是**因**：wrap 會捲，是因為 `.ant-modal` 比視窗高。
把「4vh ＋ 最多 92vh ＝ 96vh，永遠塞得進視窗」做成事實之後，wrap 根本沒有東西可捲。

那為什麼不順手也關掉？因為它是唯一的退路。萬一日後有人給某個 Modal 加上更大的 `max-height`：

| | 壞掉時 |
|---|---|
| `overflow: auto`（現況）| 可以捲到底，難看但救得回來 |
| `overflow: hidden` | 底部連同按鈕被永久裁掉，使用者既操作不到也看不出來 |

正常情況下兩者的行為完全一樣，壞掉時的代價差很多。

### 連帶清掉

- **8 個重複的 `<FormModalHelper />`**——同一段 `<style>` 在 DOM 裡被渲染 9 次。只留 MainLayout 那一個。
- **16 個死 class**（`about-modal`、`meeting-draft-modal`…）全專案沒有任何對應 CSS。
- **掛了尺寸 class 卻還設 `Width`**：尺寸 class 的 `width` 是 author-important，**贏過 `Width` 產生的 inline style**，參數是死的。一併移除。
- **`.ai-chat-log` 的 `height: 52vh`、`.todo-extract-list` 的 `max-height: 52vh`**——猜出來的常數，在 1366×768 上加起來超過視窗高。改成 `flex: 1 1 auto` 吃剩餘空間。
- **`.todo-view-detail-content` 的 `max-height: 60vh`**——與 body 的捲軸疊成兩層，內框捲到底之後還要再捲外框。

## 三、共用編修器 `MarkdownEditorModal`

放在 `Components/Commons`：它不知道「會議」是什麼，存檔與匯出都由呼叫端做，
所以日後拿去編修專案說明或提示詞範本都可以直接用。

```
┌ 搜尋列（常駐）─────────────────────────────────┐
│ [搜尋] 第 3 / 共 12 筆 [↑][↓] [取代為] [取代][全部取代] │
├───────────────────┬───────────────────┤
│ textarea（左）      │ Markdown 預覽（右）  │
└───────────────────┴───────────────────┘
                        [下載 PDF] [取消] [儲存]
```

檢視與編修**共用同一個元件**，差別只在 `CanEdit`：唯讀時只剩右邊的預覽，佔滿整寬。

### 幾個刻意的決定

- **`Content` 是單向的**，只在 `Visible` 由 false→true 的那一次吃進緩衝。會議頁的進度通知器會週期性 `StateHasChanged`，雙向繫結會把使用者打到一半的內容洗掉。
- **繫結不 debounce（0ms），預覽才 debounce（250ms）**。兩者是不同的東西：搜尋／取代／存檔必須讀到當下的文字（0.4.52 在 AI 問答上踩過「讀到舊值」）；預覽是純顯示，`MarkupString` 一變就是整串重送，不 debounce 每秒會往下推 100KB。
- **編修時 `Keyboard="false"`**：一整篇打到一半的會議紀錄，Esc 按錯一次就沒了。改過再按「取消」會先跳確認。
- **只反白當前那一筆**。`<textarea>` 裡唯一能做的反白就是 selection，要同時標記全部 m 筆得做逐像素對齊的 overlay（CodeMirror 那套），中文字型 fallback 一有差異就整段錯位。用「第 n / 共 m 筆」補足資訊，這也是記事本與 VS Code 的行為。
- **不綁 Ctrl+F**。Blazor 的 `@onkeydown:preventDefault` 是編譯期決定的，攔 Ctrl+F 就得對整個容器無條件攔，**連右邊預覽區的瀏覽器原生搜尋都會被吃掉**。搜尋列本來就一直在。

### 搜尋取代的邏輯全在 C#

`Business/Helpers/TextSearchHelper.cs`（純函式，30 筆測試）。放在 JS 裡就永遠測不到——本專案沒有 bUnit。
JS 只做 DOM 才做得到的事：`setSelectionRange`、`focus`、捲動。

⚠️ 兩個容易默默出錯的地方，都有測試釘住：

- **換行正規化**：`<textarea>` 的 value 一律是 LF，而會議紀錄來自 LLM／資料庫可能含 `\r\n`。不正規化的話索引從第一個換行之後就開始偏，而且愈往後偏愈多——只有長文件的後半段才看得出來。
- **比對一律 `OrdinalIgnoreCase`**：保證「比對到的片段長度 == 搜尋字串長度」，`Start + Length` 的算術才成立。culture-sensitive 的比對會做多字元折疊，長度不相等。

## 四、依歸屬決定操作位置

| | 編修會議紀錄 | 下載 PDF |
|---|---|---|
| **已歸屬專案** | 只在專案頁 | 只在專案頁（清單列的按鈕保留，視窗裡也有）|
| **未歸屬專案** | 只在會議紀錄頁 | 只在會議紀錄頁的編修視窗裡 |

已歸屬的會議在會議紀錄頁按「檢視」時，視窗底部有一行指路：
「這份會議紀錄已歸屬『○○』專案，編修與下載 PDF 請到『專案項目』頁。」
沒有這行，使用者只會覺得按鈕莫名其妙消失了。

⚠️ **編修視窗裡的「下載 PDF」拿的是視窗裡當下的內容**，不是資料庫那份。
改了字還沒存就按下載，用舊內容產 PDF 會給出一份與畫面不符的檔案，而且完全沒有徵兆。

## 五、驗證

測試 **843 → 874**（−10 逐字稿測試，＋30 `TextSearchHelper`，＋7 `IsReverseSubmit`，＋3 `ModalSizeClassTests`）。

### 測得到的

`TextSearchHelperTests` 以突變測試確認有牙齒：把 `from = at + term.Length` 改成 `at + 1`、
把 `OrdinalIgnoreCase` 換成 `Ordinal`、把 `ReplaceAll` 改成反覆呼叫 `Replace`——三種都正確變紅。

`ModalSizeClassTests` 掃描所有 `.razor` 的 `<Modal>` 標籤：每個都要剛好一個尺寸 class、
不可以同時留 `Width`。0.4.69 之所以留下 16 個死 class 與 13 個沒 class 的 Modal，
正是因為當時沒有任何東西在看著。同樣以突變測試確認兩條規則都會抓到。

### 只能實跑驗的

以 CDP 驅動瀏覽器，沙箱資料副本、另一個 port，在 **1366×768 與 1280×720** 各量一次
（0.4.69 只驗過 1574×900，而那些 vh 常數正是矮螢幕才會爆）。

**18 個對話框全部通過**：外框不捲、整頁捲不動（`bodyOverflow: hidden`）、標題與按鈕列都看得到、
`body padding` 一律 `16px 20px`。連 `ConfirmAsync` 的確認框（不在原清單裡、但會被基準線波及）也一併量過。

實跑抓到兩個單元測試證明不了的缺陷：

1. **Razor 註解夾在元件屬性之間會變成參數名**
   `@*...*@` 寫在 `<Modal>` 的兩個屬性中間時，Razor 把整段註解當成**屬性名稱**傳給元件，
   執行期丟 `InvalidOperationException`、整頁空白——而且**編譯得過**。
2. **編修視窗的按鈕列被擠出捲動區**
   `.markdown-editor` 原本是 `height: 100%`，佔滿整個 body，把下面的「儲存」推到看不到的地方。
   改成 `flex: 1 1 auto` 並讓 body 成為 flex column。

搜尋取代也實跑驗過：13 筆命中、Enter 跳下一筆、**中文輸入法組字中的 Enter 不跳筆**、
取代一筆（13→12）、全部取代（歸 0）、改過按取消會跳確認。

**本次沒有任何 API 花費。**

## 六、順帶發現的安全問題（本次只改文件，不動程式）

`AiChatService` 全檔 grep **不到** `IsTeamAccessible`／`accessScope`——**它讀逐字稿沒有團隊守門**。

移除 `MeetingService.ReadTranscriptAsync`（那支**有**守門）之後，
**AI 問答成為使用者接觸逐字稿原文的唯一路徑，而那條路徑比被刪掉的預覽路徑更鬆。**

`docs/security/認證授權與權限機制.md` 與 `docs/prd/會議紀錄-prd.md` 原本都宣稱
「逐字稿預覽以 `IsTeamAccessible` 守門」——移除後那兩句會變成描述一條不存在的防線，
這一版已經把文件改成描述現況。**要不要把守門補進 `AiChatService` 是另一個決定**，不在本次範圍。
