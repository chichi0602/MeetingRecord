# 待辦頁列數跟著畫面高度走，右邊面板只捲自己（0.4.85 → 0.4.87）

使用者要求：

> 不要限定5 row好了 自動調整對應螢幕大小 不要讓他過長 導致需要滾動螢幕
> 右邊的工作量一樣 就算內容過多 也是只能滾動內容 不能滾動整個畫面

0.4.85 把每頁筆數寫死成 5，這一版改成量畫面算出來。
**0.4.86 是第一版做法，留白太多被退回；0.4.87 換成回授式控制器。**

---

## 一、0.4.86 的做法為什麼不夠好

第一版是「**預測**」：量出 tbody 頂端到畫面底部還剩多少高度，除以列高得到列數。

實跑量到的結果是：**表格底部永遠離畫面底 76～177px，而右邊面板永遠只差 51px**
——使用者看到的就是「左邊只顯示幾列、底下一大片空白」。兩個原因疊在一起：

1. 列高必須取保守值（見第三節），估出來的列數本來就偏少；
2. 再被無條件捨去吃掉一列。

## 二、0.4.87 改成回授

不預測，改量**表格區塊（含分頁器）底部離畫面底還剩多少**（`leftover`）：

- `leftover` 夠塞下一列 → 補列（用**最高**的列估，寧可少補也不要補到超出讓捲軸閃一下）
- `leftover` 是負數（已經撐出捲軸）→ 縮列（用**最矮**的列估並無條件進位，一次拿夠）
- 剩下的空間連最矮的一列都放不下 → 就是吃滿了，那點留白排不掉

每調整一次就**再量一次**，直到不再變動。這樣天生對「列高不一致」免疫——
不需要猜列高到底是多少，只要看實際排出來還剩多少。

⚠️ **一定要在改完列數之後主動再量一次**（`remeasure`）。JS 端的 `ResizeObserver`
只看寬度，而改列數只會改高度——少了這一步，列數就只會被調整一次，永遠停在第一次估的值。

---

## 三、⭐ 實跑才抓到的：列高不是固定的

0.4.86 第一版量完就除，結果同一個 1600×900 量到 8 列、換個高度再回來變 6 列、再一次又 8 列，
**而且每跳一次都打一輪查詢**。

取證之後原因很單純：**截止日欄會把「逾期 N 天」折到第二行**（0.4.67 刻意的排版），
實測 **63.75px 對 81px**。於是「這一頁剛好有沒有逾期的列」直接決定量到的列高。

0.4.87 的控制器用**上限**解決同一件事：每次撐出捲軸就把「已知放不下的列數」記下來，
之後不再長回去。列數夾在 3～40 之間、上限只會往下壓，所以一定會停。

### ⚠️ 判斷「換了版面」的容差不能用 0

收斂過程中**整頁捲軸會短暫出現**，表格容器寬度跟著差一個捲軸寬（Windows Chrome 約 15px），
被當成「換了版面」而把上限清掉，於是又開始來回跳。

所以 `WidthChangeThreshold = 24`：大於任何常見捲軸寬，又遠小於側邊欄收合的 236px
——真的換版面時仍然會重來（欄寬變了，折不折行也會變）。視窗高度則是一變就重來。

## 四、量測的四個坑

| 量什麼 | 怎麼量 | 為什麼 |
|---|---|---|
| 底部要留的空白 | 外層 `<article>` 的 `padding-bottom` ＋ `margin-bottom` | 版面調整時不用記得同步改常數 |
| 表格區塊底部 | `wrap.getBoundingClientRect().bottom` ＋ `scrollY` | ⚠️ `rect` 是**視窗**座標，不加 `scrollY` 的話，進頁面時剛好捲在半路就會算錯。標題列是 `sticky`（仍佔著流），換算後正好等於「沒捲動時的視窗座標」 |
| 安全邊界 | 再多留 2px | ⚠️ `scrollHeight` 是整數、版面高度是小數，剛好算滿時進位會多出 1px——而 1px 也是一條捲軸 |
| 面板高度上限 | `Math.floor`，不要 `Math.round` | 同上，進位上去那 1px 也是捲軸 |

**算術一律不在 JS 裡**（`TodoAutoFit.Decide`）——本專案沒有 bUnit，
放進 JS 的判斷就永遠測不到，與 `text-editor.js` 同一條界線。

---

## 五、右邊面板

`--todo-view-panel-max` 由 JS 量「面板頂到視窗底」寫在 `<html>` 上，
面板 `max-height` 吃它，小清單 `flex: 1 1 auto; min-height: 0; overflow-y: auto`。
內容再多也是小清單自己捲。

`min-height: 0` 讓小清單成為面板裡**唯一**會被壓縮的區塊：上面的下拉、完成度、膠囊都是
flex 項的 `min-height: auto`（＝內容高，擋住壓縮），只有捲動容器的 `min-height: auto` 依規範解成 0。

⚠️ 變數掛在 `<html>` 而不是面板自己的 inline style：面板是 Blazor 算繪的元素，
把樣式寫在它身上等於跟框架搶同一個位置。

### ⚠️ CSS 原始碼順序踩到一次

單欄（< 1400px）的覆寫原本寫在檔案上方那個 grid 的 media query 裡，
**特異度相同、原始碼順序在基礎規則之前，所以被蓋掉**——實跑量到面板吃了 113px 的上限。
覆寫必須排在 `.todo-view-owner-panel` 與 `.todo-view-owner-list` 的基礎規則**之後**。

## 六、兩個刻意的邊界

| 情況 | 行為 |
|---|---|
| **單欄（< 1400px）** | 面板是疊在表格**下面**的，量「面板頂到視窗底」沒有意義，退回 0.4.66 的固定 420px 上限。整頁仍要捲一段才看得到面板——兩塊都要塞進一個畫面，在這個寬度下本來就辦不到 |
| **使用者自己改每頁筆數** | 從那一刻起不再自動調整。否則他選了 20 筆，下一次量測會立刻蓋回去，看起來就像那個選單壞了。（筆數選單在總筆數 > 50 時才出現）|

## 七、測試（917 → 939）

`TodoAutoFitTests`（22 個）。最有價值的三條：

- ⭐ `Decide_AtCeiling_ShouldNotGrowBackToTheKnownBadSize` —— 收斂的唯一保證。
- ⭐ `Decide_ScrollbarWidthJitter_ShouldKeepTheCeiling` —— 把實跑抓到的捲軸寬度抖動釘住。
- `Decide_BadMeasurement_ShouldNotTouchThePageSize` —— 特別是列高 0（表格還沒有任何列），
  不擋的話會除出 `Infinity`，一路把列數推到上限，等於每次進頁面都先撈 40 筆。

三處突變驗過，各自讓測試變紅：拿掉上限、補列改用最矮的列估、縮列的進位改成捨去。

## 八、實跑驗證

判定一律**等到狀態連續兩次相同**才讀，不用固定 sleep——量測→查詢→重繪會跑好幾輪，
固定等 2.8 秒會抓到過渡態，看起來就像沒收斂（0.4.86 為此繞了兩次冤枉路）。

| 視窗 | 列數 | 整頁超出 | 扣掉結構空白後排不掉的餘量 |
|---|---|---|---|
| 1500×900 | 7 | 0 | 63px |
| 1555×805 | 6 | 0 | 47px |
| 1555×900 | 8 | 0 | 14px |
| 1840×910 | 8 | 0 | 63px |
| 1840×1000 | 10 | 0 | 26px |
| 2210×1100 | 11 | 0 | 62px |
| 2560×1000 | 10 | 0 | 26px |

**餘量一律小於一列**（列高 63.75px），也就是「再多排一列就會撐出捲軸」。
0.4.86 同樣的尺寸餘量是 76～177px，等於白白少排一到兩列。

側邊欄收合／展開不再影響列數；小清單 37 筆時自己可捲而整頁不捲；翻頁正常。

⚠️ CDP 的 `Emulation.setDeviceMetricsOverride` **不會在頁面裡派送 `resize` 事件**
（真實瀏覽器拉視窗一定會派），驗證腳本要自己補一發，否則量到的是「改變大小之前」的版面。

實跑在沙箱資料副本上做，事後已刪除沙箱並確認真實資料庫 md5 未變。**本次沒有任何付費 API 呼叫。**
