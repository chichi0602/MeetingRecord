## 一、「頁面滾動太多」的真正原因不是頁大小

`TodoService.GetAsync` 的 `Take` 被包在 `if (dataRequest.Take != 0)` 裡，
而呼叫端（`TodoViewView.razor.cs`）**一律傳 `Take = 0`** ——所以第 1 頁會列出**全部 44 筆**。

`result.Count` 是在 `Skip`／`Take` 之前算的，**分頁器的總數與頁數一直是對的**，
只有內容沒被切，所以這個缺陷才會一直沒被發現：畫面上有分頁器、看起來很正常，
但不管翻到第幾頁都是一路捲到底。

⚠️ **因此只把每頁筆數改成 5 完全不會有效果**，畫面仍會一次渲染全部列。

這是全站已知缺陷（[開發慣例與限制速查 §6.2](../architecture/開發慣例與限制速查.md)），
八支 `*Service.GetAsync(DataRequest)` 裡先前只有 `PromptTemplateService`（0.4.64）修好。
**本次修了第二支 `TodoService`，其餘六支維持原樣**——使用者明確說其他頁之後再決定，
而每多改一頁就多一頁要實跑驗證的分頁與頁碼夾住。

## 二、分頁（四處，缺一不可）

| 位置 | 改動 |
|---|---|
| `TodoService.cs` | `Take` 從 `if` 裡拉出來，照抄 `PromptTemplateService` 的形狀 |
| `TodoViewView.razor.cs` | `private const int TodoPageSize = 5;` |
| `ReloadAsync` 尾端 | 補頁碼夾住 |
| `OnTableChange` | 補 `_pageSize = args.PageSize;` |

**頁大小刻意不用 `MagicObjectHelper.PageSize`（8）**：那是八個清單頁共用的值，
改它會一次動到七個沒被要求改的頁。寫成 view 內的具名常數並在 XML 註解裡寫明理由，
否則下一個人會順手把它「統一」回共用值。

**頁碼夾住不是順手加的，是分頁修好之後才第一次會出事的**：
`_pageIndex` 從來不會被夾回範圍內，停在末頁把該頁唯一一筆刪掉，
`Skip` 就會跳過全部而顯示**空白表格**。分頁沒作用時永遠只有第 1 頁，所以看不到。

```csharp
if (todoAdapterModels.Count == 0 && _total > 0 && _pageIndex > 1)
{
    _pageIndex = Math.Max(1, (_total + _pageSize - 1) / _pageSize);
    await ReloadAsync();
    return;
}
```

⚠️ `Math.Max(1, ...)` 不可省：AntDesign 1.6.0 在 `PageIndex < 1` 時**不觸發** `OnChange`，
夾出 0 會卡死。遞迴有界：`Count` 與資料列來自同一個 query，`_total > 0` ⇒ 夾到的最後一頁必定非空。

**`OnTableChange` 補 `_pageSize` 也不算改不相關的東西**：分頁本來沒作用過，
「使用者改每頁筆數」以前不可能被觀察到，修好之後它第一次真的會動。
目前唯一讓它能動的是 `@bind-PageSize` 與 AntDesign 內部 callback 的**觸發順序**，
是沒有文件保證的第三方實作細節，一行明確賦值把它釘死。

> 順帶把 `PromptTemplateService.cs` 註解裡的「其餘 7 支」改成 6 支——我們一改它就變成假的。
> 但 `docs/changelog/2026-09-17-AI用量分析.md` 裡「0.4.64 只修了 PromptTemplateService」
> **刻意不動**：那是當時的歷史紀錄。

## 三、膠囊可點篩選

原本四顆膠囊是純 `<span>`、沒有任何 `@onclick`，是乾淨的掛點。
`ownerTodos` 來自 `GetByOwnerAsync`（刻意不分頁，單人量級小），
所以這是**純記憶體的檢視層篩選，服務層完全不動**。

### ⚠️ 絕對不可以做的事

**不要把狀態帶進 `GetOwnerSummariesAsync`。** 那會讓完成度變成「每個人都 100%」
或「都 0%」——**不是空資料，是看起來合理的錯誤數字**。
膠囊自己的數字與完成度進度條一律維持未篩選。程式與 PRD 兩邊都留了註解擋住。

### 型別用 enum 不用 `string?`

「逾期」**不是 `Status` 的值**（`IsOverdue => DueDate.HasValue && !IsCompleted && DueDate < Today`）。
用 `string?` 就得塞一個不在 `StatusOptions` 裡的魔術字串，而 `todo.Status == filter`
會**安靜地**永遠不成立——沒有例外、沒有紅字，只有一個永遠空的清單。

新檔 `Components/Views/Todos/TodoOwnerFilter.cs`：`enum OwnerTodoFilter` ＋ `Apply`／`Clamp`／`CountOf`／`Describe`。
放在 view 旁邊而不是 `Components/Commons/`（只有一個消費者，升格成共用 helper 是假的），
但仍抽成純函式——理由與 `FormKeyboardHelper`／`FormDirtyHelper` 一樣：
**本專案沒有 bUnit，寫進 `.razor.cs` 的判斷就只能靠眼睛驗**。

### 互斥單選，不疊加

理由是資料決定的：逾期 ⊂（待辦 ∪ 進行中），而**逾期 ∩ 已完成恆為空**。
多選一定會產生「已完成 ＋ 逾期」這種**永遠空清單**的組合。
單選也才保得住唯一的賣點：**膠囊上的數字 = 點下去看到的筆數**。

### 三個邊界情況

| 情況 | 處理 |
|---|---|
| **0 筆的膠囊** | 渲染回 `<span>` 而不是 `<button disabled>`——沿用 §6.1 第三類既有的理由（disabled 不可 focus，掛在上面的說明讀不到），也從源頭消滅「點了得到空清單」 |
| **篩逾期後把最後一筆改成已完成** | 膠囊會消失而篩選還在 → 空清單且沒東西可點掉。用不變式守：**作用中的篩選，畫面上一定要有一顆可以點掉它的膠囊**。`Clamp` 在 `ReloadOwnerPanelAsync` 與 `OnOwnerChangedAsync` 尾端各呼叫一次 |
| **換人／換專案** | **不重設，只 clamp**。典型用法是跨人巡同一個狀態（「還有誰有逾期」），每換一人就要重點一次等於把功能做廢一半 |

⚠️ **陷阱**：日後若要改成「換專案要重設」，那一行只能放在 `OnProjectFilterChanged`，
**絕不能放進 `ReloadOwnerPanelAsync`**——後者在每次勾完成／刪除／新增之後都會跑，
放那裡等於使用者每勾一個完成，篩選就被默默清掉。

### 元素與可及性

膠囊改成 `<button type="button">`，樣板是 §6.1 第三類，三點差異：

- **要 `aria-pressed`**（這是 toggle 不是 action）。⚠️ 必須給**字串** `"true"`／`"false"`：
  Blazor 對 `bool` 屬性的規則是「true 只渲染屬性名、false 整個略掉」，給 bool 會渲染成空值而無效。
- **不需要二次確認**。§6.1 第三類原本寫「一定要有二次確認」，那是針對**會寫入資料**的膠囊；
  這裡只改檢視狀態、可逆、不碰資料庫。這是真的偏離 → 已回寫文件把那句限縮，否則下一個人會來「修正」。
- 原生 `<button>` 不繼承字型，`font: inherit` 會把 `font-size` 一起重設 → 要把 `12px` 補回來。

### 讓使用者看得出「現在有篩選」

兩層，缺一不可：選中的膠囊 `box-shadow: inset 0 0 0 2px currentColor` ＋ 粗體，
**其餘膠囊 `opacity: .5`**（只有選中那顆變粗，四顆並排時看不出來）；
小清單上方多一行條件式的篩選列帶「顯示全部」——與本頁既有的「清空搜尋」同一個慣例。

篩選結果用 computed property (`FilteredOwnerTodos`) 而不是另存一份欄位：
`ownerTodos` 是資料來源、`ownerTodoFilter` 是檢視狀態，合併成一份欄位之後
每一條重載路徑（面板重載、換人、勾完成、刪除、Modal 送出）都要記得重套一次，
**漏掉任何一條就會顯示上一次的篩選結果，而且畫面看起來很合理**。
