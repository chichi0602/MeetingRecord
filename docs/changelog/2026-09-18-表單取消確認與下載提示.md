# 表單取消要確認、下載與移除補上右下角提示（0.4.83 → 0.4.84）

使用者要求：

> 且編輯畫面取消要多一個確認取消尚未儲存
> 另外每個下載pdf、把會議記錄移除時都一樣要加入右下角toast提醒

追問後拍板：「移除」指**從專案移除歸屬**（不是刪除會議紀錄）；確認套用到**所有編輯表單**
（外加變更密碼、抽出待辦視窗）；**只有真的改過才跳**。

---

## 一、兩個調查結果改變了原本的假設

**1. 「右下角」不需要新機制——它已經是全站既有的位置。**
`NotificationService` 的每一處呼叫都寫死 `Placement = BottomRight`。真正缺的是
**匯出 PDF 完全沒有成功提示**（成功路徑只有 log），以及「從專案移除」用的是
`messageService`（**頂部置中**），與同檔其他成功提示不一致。

**2. `MarkdownEditorModal` 早就有取消確認了（0.4.82），其餘 12 個表單一個都沒有。**
全部是 `modalVisible = false; return;`。

## 二、dirty 判斷：`Components/Commons/FormDirtyHelper`

開表單時拍一份 JSON 快照，取消時比對。純函式、24 筆單元測試。

**為什麼不用 `EditContext.IsModified()`**：`InputWatcher` 撈到的是**外層 `EditForm`** 的
EditContext，而欄位住在**內層 `AntDesign.Form`** 底下，欄位變更的通知打不到外層，永遠回 false。
（`Validate()` 能用是因為它驗的是同一個 model 實例，不依賴 field-change 通知。）全 repo
`IsModified` 用量本來就是 0。

### 設計原則：所有不確定都往「多問一次」倒

漏問會**靜默吃掉**使用者打好的字；多問只是多按一下。所以：

- `IsDirty(null, ...)` 一律回 true（代表開表單時忘了拍快照，症狀是「每次取消都問」，一試就發現）
- `ReferenceHandler.IgnoreCycles`（日後有人加了回頭參照，寧可少比一個欄位也不要在按取消的當下丟例外）
- 已知且**接受**的誤判：`TodoAdapterModel.OverdueDays` 依賴 `DateTime.Today`（跨午夜）、
  `RolePermissionNode.Actions` 勾了再取消勾會多一個 key。兩者都不值得為它們改既有程式碼。

### ⚠️ 評估後否決的「只序列化有 setter 的屬性」

那能少問幾次，但匿名型別的屬性全是 get-only，日後誰寫
`Capture(list.Select(x => new { x.A }))` 會得到 `[{}]` → **永遠判定沒改過，靜靜吃掉輸入**。
用「多問一次」換掉這個失敗模式。

### `params string?[]` 而不是 `object?[]`

逼呼叫端自己把暫存狀態變成字串。`IBrowserFile` 身上帶著 Stream，直接丟進去序列化的結果
與使用者選了哪個檔案無關——**所有檔案都長得一樣**，於是「換了一個檔案」永遠判不出來。

## 三、三個一定會踩到的坑（都在實作前先驗證過）

**一、`@bind-Visible` 是雙向的。**
AntDesign 在呼叫 `OnCancel` **之前**就把視窗關掉了，`return` 留不住。選「繼續編修」時必須
`modalVisible = true` 開回來，否則整張表單反而消失——正好是我們要修的問題的反面。

⚠️ repo 裡 30 個「重開視窗」的先例**全在 `OnOk` 上，沒有一個在 `OnCancel`**，所以這件事
不能靠推論。**第一步先用 `CategoryViewView` 單頁 pilot 實跑驗證**，確認之後才鋪其餘 9 個。
（`TodoExtractionModal` / `MarkdownEditorModal` 是單向 `Visible=`，那種直接 `return` 就留得住，
**不可以**寫 `Visible = true`。）

**二、Esc 走兩條路。**
AntDesign 的 `Keyboard="true"` 與表單上的 `@onkeydown` 都會呼叫同一個 handler。
0.4.84 之前兩次都只是 `modalVisible = false`，冪等所以沒人發現；加了確認框之後會**疊出兩個**。
每個表單一個 `isDiscardConfirming` 旗標擋重入。

**三、`TodoExtractionModal` 的快照不能拍在開窗時**——那時 `candidates` 還是空的。
要拍在 `ExtractAsync` 結尾，否則「什麼都沒改」也會被判成 dirty。

## 四、涵蓋範圍

**加了確認的 10 個**：會議紀錄維護、專案維護、待辦、提示詞範本、使用者、角色、分類、團隊、
變更密碼、抽出待辦。`MarkdownEditorModal` 改用同一支 helper（文案一字不差，有測試釘住）。

**刻意不加的**：專案附件（**親自確認過是純唯讀清單**，只有下載鈕）、待辦詳情、關於、
AI 轉會議紀錄與歸屬到專案（只有選取沒有輸入，且取消是不花錢方向）、AI 問答的訊息編輯（使用者指定不做）。

抽出待辦的確認多一句警語：**「關閉之後再開啟會重新抽取一次，並且再計費一次。」**

## 五、Toast（5 處）

| 位置 | 改動 |
|---|---|
| 會議紀錄頁 匯出 PDF | 新增成功提示 |
| 專案頁 匯出 PDF | 新增成功提示 |
| AI 問答 匯出 PDF（單則／整段）| 新增成功提示（放在共用的 `ExportAsync` 裡，一處包辦兩個入口）|
| 專案附件 下載 | 新增成功提示 |
| 從專案移除 | `messageService`（頂部置中）→ `NotifySuccess`（右下角），並帶出會議標題 |

### ⚠️ 兩件刻意**不做**的事（都記在這裡，留給下一版）

1. **`NotifySuccess` 用 `NotificationType.Warning`**——全專案 `Warning` 共 **30 處**
   （`Success` 0 處），其中 26 處是各頁 inline 寫死的。只改 4 個 helper 會讓 4 處變綠、
   26 處還是橘，**比現在更不一致**；全部改是 9 個檔案的純視覺改動，與本次需求無關。
2. **「同時跳兩個 toast」**——不是 2 處而是 **8 處**，而且**只在「新增」分支**、8 個檔案一致，
   看起來是當初刻意的樣板不是手滑。修它還會讓部分檔案的 `messageService` 注入變成沒人用。

建議下一版合成一個主題：抽 `ToastNotifier` 把 30 處收成一處，加一支釘住
`Placement == BottomRight` 的測試。

## 六、驗證

測試 **876 → 900**（＋24 筆 `FormDirtyHelperTests`）。

最有價值的一組是**快照穩定性**：`Capture(m)` 與 `Capture(m.Clone())` 必須相等，
`[Theory]` 掃過 8 個實際用到的型別。這是整套設計的地基（專案的編輯隔離慣例是開視窗時
`Clone()`），也是回歸保險——日後誰加了 `public Guid Key => Guid.NewGuid()` 這種
非決定性計算屬性會立刻變紅，否則會靜默劣化成「每次取消都跳確認」。

### 實跑（沙箱資料副本、另一個 port、CDP）

**8 個表單全部通過**（分類、團隊、待辦、提示詞、使用者、角色、會議紀錄、專案）：

```
沒改過按取消      → 直接關、不跳確認
改過按取消        → 跳「放棄編修」，內容以主詞開頭
選「繼續編修」    → 表單還在、欄位內容完整保留
```

pilot 階段另外實測：**Esc 只跳一個確認框**、右上角 X 與點遮罩也都走同一條路。

Toast 實測到的：**專案附件下載**「已下載「…pdf」。」、**從專案移除**「已將「0902」從專案移除。」，
兩者都出現在右下角、文字正確。匯出 PDF 的**失敗**提示也確認會跳。

### ⚠️ 沒有驗到的三項（誠實列出）

1. **匯出 PDF 的成功提示**——這台機器的無頭瀏覽器產不出 PDF（`瀏覽器沒有輸出 PDF 檔`），
   失敗發生在 `RenderAsync`，還沒走到新增的那一行。與本次改動無關（沒碰過 renderer）。
   那一行與**已驗證**的專案附件下載提示同形狀：同一個 `try` 內、`SaveBytesAsync` 之後。
2. **變更密碼的「改過→確認」**——驗證用的是 `support` 帳號，而它只渲染一張
   「系統預設帳號不允許變更密碼」的 Alert、**0 個輸入欄位**，所以「直接關不問」才是對的。
   一般帳號的路徑沒有實跑到。
3. **抽出待辦的「改過→確認」**——觸發它要真的打一次付費 API，依計畫不花錢，所以沒跑。

**本次沒有任何 API 花費。**
