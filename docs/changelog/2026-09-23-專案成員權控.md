# 專案權控：專案成員制，團隊從介面退場（0.4.98 → 0.4.99）

- 文件版本：1.0
- 文件狀態：已實作
- 現行系統版本：0.4.99
- 首次實作版本：0.4.99
- 最後核對日期：2026/09/23

使用者要求：

> 一般使用者要歸類所屬團隊（專案）才能看到她負責的專案
> 專案主負責人要有更高的功能才能開權限給底下協作者
> 團隊應該只顯示在使用者管理那邊，角色管理只要設定可以看甚麼，然後在使用者管理才會去設定每個身分所屬的團隊（下拉是專案項目、可複選）

這是專案權控的**第二階段**；第一階段（0.4.98）把角色收斂成管理者／一般使用者。

已確認的決定：

- 任何人都能建專案，建立者就是負責人。
- 刪除專案、轉移負責人只有管理者。
- 還沒歸屬專案的會議，只有上傳者與管理者看得到。
- 提示詞範本對所有人開放。
- 儀表板維持全公司彙總數字。

---

## 一、資料模型（migration `AddProjectMemberAndMeetingCreator`）

- 新表 `ProjectMember(ProjectId, MyUserId, Role, CreatedAt)`，`Role` 是 `ProjectMemberRole`（負責人／協作者）。`(ProjectId, MyUserId)` 唯一；刪專案或刪帳號時連帶刪除。
- `Meeting.CreatedByUserId`（上傳者）。**刻意不設外鍵**：刪帳號不該被擋，也不該連帶刪會議。

## 二、判斷集中在 `ProjectAccessService`

- `ProjectAccess` 紀錄：`IsAdmin`、`UserId`、成員專案、負責專案。提供 `CanViewProject`、`CanManageProject`、`CanViewMeeting`，以及專案、會議、待辦三種 `IQueryable` 的 `Filter`。
- 會議規則：已歸屬看專案成員；**未歸屬只有上傳者**；上傳者為 null（推不回來的舊會議）時只有管理者看得到。`CanViewMeeting` 與 `Filter(IQueryable<Meeting>)` 是同一條規則的記憶體版與 SQL 版，要一起改。
- 使用者身分沿用 `IRecordAccessScopeProvider`，`RecordAccessScope` 加上 `UserId`。
- ⚠️ 順手修掉：`RecordAccessScopeProvider` 在 API 路徑只認 Cookie 的 `Sid` claim，但 JWT 放的是 `NameIdentifier`，所以 **0.4.98 以前 API 呼叫一律被當成「非管理員、無團隊」**。現在兩個都看。

## 三、套用範圍

| 地方 | 規則 |
|------|------|
| `ProjectService` | 清單、下拉（`GetSelectableAsync`）、單筆、附件下載只回看得到的專案。新增時建立者寫成負責人，`Owner` 姓名取自帳號、不信任表單。修改要負責人或管理者；刪除只有管理者 |
| `MeetingService` | 原本 11 處團隊檢查全部換成專案規則；**補上原本完全沒檢查的 `UpdateAsync`／`DeleteAsync`**。新增時記錄上傳者。歸屬到專案與產生會議紀錄時，目標專案也要看得到 |
| `TodoService` | 清單、負責人面板、單筆、新增、修改、完成、刪除都限於成員專案；修改時原專案與目標專案都要看得到 |
| `TodoExtractionService` | 看不到的會議當成不存在（這支會花錢，也會把會議內容送出去） |
| `AiChatService` | 0.4.98 以前**完全沒有檢查**，知道 Id 就讀得到別人的對話與附件。現在每個公開方法第一行都經 `EnsureAccessAsync` |
| 進度面板 | 通知器的項目改帶 `ProjectId`、`CreatedByUserId`，取代 `Teams`。面板查成員資格時自開 scope，避免和頁面共用 DbContext 撞在一起 |
| Web API | `ProjectRepository`、`MeetingRepository`、`TodoRepository` 套同一套規則，看不到的回 404。另修掉「API 更新會議會把 `ProjectId` 清成 null」的舊問題（DTO 沒這欄，`SetValues` 會蓋掉） |

看不到的一律當成**不存在**（回空模型或「找不到」），不回「沒有權限」，免得透露它存在。

## 四、畫面

- **專案頁**：摘要列「負責人」旁多一個「成員」，開 `ProjectMemberModal`。負責人與管理者可以加減協作者，管理者可以「設為負責人」（原負責人降為協作者）；協作者看到唯讀名單。「編輯專案」只給負責人與管理者，「刪除專案」只給管理者。專案表單拿掉負責人欄位。
- **使用者管理**：「團隊」選單換成「**所屬團隊（專案）**」複選，勾了＝協作者（`ProjectMemberService.SyncUserCollaborationsAsync`，只增刪協作者列）。他擔任負責人的專案標「（負責人）」並鎖住。`MyUserService.AddAsync` 改成回填 `Id`，新增使用者時才能接著存專案。清單的「管理者」是／否欄改成「角色」欄，直接顯示「管理者」或「一般使用者」。
- **角色管理**：拿掉「預設團隊」，只管能用哪些功能。
- **提示詞範本**：拿掉團隊過濾與表單的團隊欄位，所有人都選得到啟用中的範本。
- **團隊清單**：從選單與權限目錄移除，頁面程式碼保留。

`Teams` 欄位、`UserTeam`、`EffectiveTeamResolver` 等資料與程式都保留未刪。

## 五、舊資料回填（`ProjectAccessBackfillService`，每次啟動、冪等）

- **負責人**：還沒有負責人的專案，拿 `Project.Owner` 手打姓名去對 `MyUser.Name`，**剛好對到一個**才算；對不到或同名好幾個都跳過，那個專案只有管理者看得到，由管理者到專案頁「成員」或使用者管理補指派。
- **上傳者**：`CreatedByUserId` 為 null 的會議，取 AI 用量帳本裡這場會議**最早一筆轉錄**的 `UserId`。帳本 0.4.80 才開始記，更早的推不回來。

⚠️ **升級後的影響**：一般使用者會看不到自己不是成員的專案。舊專案的負責人若對不上帳號，要由管理者補指派，否則那個專案一般使用者都看不到。

## 六、測試

- `ProjectAccessTests`（新增 14 筆）：規則純邏輯、成員專案清單、建立者成為負責人、協作者不能改專案、負責人不能刪專案、成員管理、轉移負責人、使用者頁同步不動負責人列、待辦過濾與不能搬家、回填（同名、最早轉錄）。
- `MeetingServiceTests`：原本的團隊可見性測試改寫成專案規則，另加上傳者記錄、非成員不能改與刪。
- `PromptTemplateServiceTests`：團隊過濾測試改成「標了團隊也看得到」。
- 兩個進度通知器測試改驗 `ProjectId`／`CreatedByUserId`。
- `ApiIntegrationTests`：非成員用 API 看不到別人的專案，自己用 API 建的專案看得到而且是負責人。
