# 團隊與分類分工：團隊管誰的資料、分類管什麼資料（0.4.101 → 0.4.102）

- 文件版本：1.0
- 文件狀態：已實作
- 現行系統版本：0.4.102
- 首次實作版本：0.4.102
- 最後核對日期：2026/09/29

0.4.101 把「團隊」改名成「資料群組」，用來決定誰看得到什麼。使用者覺得定義不清楚，也容易和「分類」混在一起，所以重新定義：

> 團隊是「誰的資料」，分類是「什麼資料」（也就是標籤），兩個不要混在一起。

範例：

| 專案 | 主責團隊 | 協作團隊 | 分類 |
|------|----------|----------|------|
| 成大醫療平台 | 研發部 | — | .NET、成大 |
| 新創平台 | 研發部 | — | Java、新創 |
| 成大 EMR | 研發部 | 管理部、業務部 | .NET、成大 |

王小明屬於研發部與管理部：

- 看得到主責是研發部或管理部的專案。
- 看得到主責是業務部、但協作有研發部的專案。
- 看不到只屬於業務部的專案。

已確認的決定：

1. 名稱改回「**團隊**」，也就是部門，例如業務部、管理部、研發部。一個人可以屬於多個團隊。
2. 每個專案有 **1 個主責團隊（必填）**，可以再加 **0～多個協作團隊**。**不再有公開專案**。
3. 一般使用者：主責只能選自己所屬的團隊，協作可以選任何團隊。管理者可以選所有團隊。
4. 分類可以貼在**專案與會議**上，兩邊都能依分類篩選。
5. 分類頁可以記錄「通常由哪些團隊負責」，**只是參考**，不影響專案，也不影響誰看得到。
6. 0.4.101 轉換出來的同名群組保留。之後由管理者建好部門，再手動改主責團隊。

角色維持 0.4.101 的做法：只管能做什麼，可以多角色，權限取聯集；勾了「管理者」就全部放行。

## 一、可見性（`ProjectAccessService`，唯一入口）

| 情況 | 誰看得到 |
|------|----------|
| 專案 | 所屬團隊與專案的**主責＋協作**團隊有交集的人 |
| 沒有任何團隊的專案（舊資料） | 只有管理者 |
| 未歸屬專案的會議 | 上傳者與管理者 |
| 管理者 | 全部 |

- `ProjectAccess(IsAdmin, UserId, TeamIds, ProjectIds)`。`CanViewProject`、`CanViewMeeting` 與三個 `Filter` 的簽章不變，會議、待辦、AI 問答、三個 Repository、進度面板的呼叫端都沒改。
- 拿掉「沒指定＝公開」。
- 儀表板維持全公司彙總的例外；提示詞範本維持對所有人開放。

## 二、專案：主責＋協作團隊

- `ProjectTeam` 加上 `IsPrimary`，每個專案恰好一筆主責，由服務層保證。
- `ProjectAccess.ResolveProjectTeams` 的規則：
  - 主責必填。
  - 非管理者的主責限自己所屬的團隊。**主責沒變時照原樣保留**，所以協作團隊的人改專案內容也能存檔。
  - 協作任何團隊都可以選，主責不會重複列在協作裡。
- `ProjectTeamWriter` 負責檢查團隊存在並寫入，畫面（`ProjectService`）與 API（`ProjectRepository`）共用，兩邊規則不會分岔。
- 專案表單：
  - 「主責團隊」單選。管理者看得到全部，一般使用者只看得到自己的團隊；新增時預帶自己的第一個團隊。
  - 「協作團隊」多選，可選全部團隊。
  - 「分類」多選。
  - 摘要列顯示主責、協作與分類。
- 專案下拉旁多一個「依分類篩選」。
- API：
  - `ProjectCreateUpdateDto`／`ProjectDto` 多了選填的 `primaryTeamId`、`collaboratorTeamIds`、`categories`。
  - 建立時沒給主責，用建立者 Id 最小的團隊；建立者沒有任何團隊時回 400。
  - 修改時沒給就保留原值；團隊選擇不合法時回 400。

## 三、團隊

- 畫面上的「資料群組」全部改回「團隊」。選單 id 52 改回「團隊清單」。
- 權限鍵常數改回 `角色_團隊清單`。啟動時 `RbacBackfillService` 把 0.4.101 的「資料群組」鍵，包括「資料群組:edit」這類動作鍵，就地改回「團隊清單」，已勾的角色不會掉權限。
- **刪除保護**：團隊還是某個專案的主責時不能刪，畫面會列出這些專案的名稱，API 回 409。只當協作的團隊可以刪，因為刪了只會讓看得到的人變少。這也解決了 0.4.101「刪群組會讓專案變公開」的問題。
- 團隊頁的成員管理，以及使用者管理的批次加入／移出，維持 0.4.101 的做法，只是改稱「團隊」。
- 附帶修正：使用者清單的勾選欄改用表格的 `RowKey`，消除過時用法警告。

## 四、分類

- 分類是「什麼資料」：只描述性質，不影響誰看得到。
- **專案**新增 `Categories` 欄位，存法與會議相同：以名稱存成標籤字串。
- **會議頁**放回 0.4.35 拿掉的分類，包括工具列篩選、清單的「分類」欄與編輯表單。團隊沒有放回來，會議的可見性照舊跟著專案走。
- **分類頁**多了「負責團隊（參考）」多選與清單欄位，存在新表 `CategoryTeam`。只是參考資訊，不會帶進專案。
- 已知限制：分類以名稱存在專案與會議上，分類改名後，舊資料上的名稱不會跟著改。

## 五、升級轉換（`TeamConversionService`，原 `DataGroupConversionService`）

每次啟動都跑，重複執行不會有副作用：

1. 舊的 `ProjectMember` 表如果還在，照 0.4.101 的方式轉成同名團隊，並**設為主責**，然後刪表。
2. **補主責**：還沒有主責的專案，取已掛團隊中 Id 最小的一筆設成主責。完全沒掛團隊的專案（0.4.101 的「公開」專案）主責掛「待分配」，重新指定前只有管理者看得到。
3. 會議上傳者的回填保留。

Migration `AddProjectPrimaryTeamAndCategories`：新增 `ProjectTeam.IsPrimary`、`Project.Categories` 與 `CategoryTeam` 表。
