# 角色與資料群組分離：角色管做什麼、資料群組管看什麼（0.4.100 → 0.4.101）

- 文件版本：1.0
- 文件狀態：已實作
- 現行系統版本：0.4.101
- 首次實作版本：0.4.101
- 最後核對日期：2026/09/29

使用者整理出新的權限原則，要求照這個邏輯改：

> 角色＝可以做什麼；資料群組＝可以看到什麼；使用者分別關聯角色與資料群組。

這推翻了 0.4.98～0.4.99 的兩個設計：角色只剩「管理者／一般使用者」、專案靠「成員（負責人／協作者）」控管可見性。已確認的決定：

1. 專案成員制**完全改用資料群組**，拿掉負責人／協作者與成員對話框。
2. **只有專案**指定資料群組，會議、待辦、附件、AI 問答跟著專案走。
3. 未歸屬專案的會議維持**只有上傳者與管理者**看得到。
4. 升級時把舊的專案成員轉成**同名資料群組**；沒有成員的舊專案放進空的「**待分配**」群組。
5. 一般使用者只能從自己所屬的群組裡選，新專案預設全選；不選＝公開。
6. **恢復多角色**，「管理者」勾選維持全部放行。

程式內部沿用 `Team`／`UserTeam`，畫面上叫「資料群組」。

---

## 一、可見性規則（`ProjectAccessService`，唯一入口）

| 情況 | 誰看得到 |
|------|----------|
| 專案**沒有**指定資料群組 | 公開：有專案頁權限的人都看得到 |
| 專案有指定資料群組 | 所屬群組跟專案的群組**有交集**的人 |
| 未歸屬專案的會議 | 上傳者與管理者 |
| 管理者（`IsAdmin`） | 全部 |

- `ProjectAccess(IsAdmin, UserId, GroupIds, ProjectIds)`：`GroupIds` 只取 `UserTeam`，角色不再帶任何群組。
- `CanViewProject`、`CanViewMeeting` 與三個 `Filter` 的簽章不變，會議、待辦、AI 問答、三個 Repository 與進度面板**呼叫端都沒改**。
- 看不到的當成不存在：畫面顯示「找不到」，API 回 404。
- 儀表板維持全公司彙總的例外；提示詞範本維持對所有人開放。

## 二、專案

- 新表 `ProjectTeam(ProjectId, TeamId)`，唯一鍵，專案或群組刪除時連帶刪除。
- 表單多一個「**資料群組**」多選：
  - 管理者可選任何啟用中的群組；一般使用者只看得到自己的群組。
  - 新增時預設帶入自己全部的群組；清空＝公開。
- **非管理者只能增刪自己所屬的群組**：專案原本掛著、但自己不屬於的群組存檔時原樣保留（`ResolveProjectGroups`），避免一存檔就把其他部門踢掉。
- 「負責人」回到表單手打的描述欄位（0.4.99 以前的行為），不再代表權限。
- 改、刪回到角色的動作權限（畫面 `CheckAccessAction`、API `[HasPermission]`），拿掉「只有負責人能改、只有管理者能刪」。
- 摘要列把「成員」換成資料群組名稱；沒指定時顯示「公開」。
- API：建立專案時帶入建立者的所有群組；修改時保留原本的群組（DTO 沒有這個欄位）。
- 刪除 `ProjectMember`、`ProjectMemberRole`、`ProjectMemberService`、`ProjectMemberModal`。

## 三、角色

- 恢復**主要角色＋額外角色**，權限取聯集（`UserRole`）。「管理者」勾選仍然不看角色與資料群組、全部放行。
- `RoleConsolidationService` 改名 `DefaultRoleSeeder`，只負責確保「一般使用者」角色存在：
  - 舊名「預設角色」就地改名，都沒有才新建。
  - 權限**只在建立或改名的當下**設成業務頁那一組，之後以角色管理頁為準。
  - **不再動任何人的角色**（0.4.98～0.4.100 每次啟動都把所有人收斂成一般使用者）。預設帳號 support 只在沒有角色時才掛上。
- 拿掉角色的「預設團隊」：刪除 `RoleView.DefaultTeamsJson` 欄位與 `TeamJsonHelper`；`EffectiveTeamResolver` 只取 `UserTeam`；`RbacBackfillService` 不再從角色回填 `UserTeam`。
- 使用者清單的「角色」欄列出所有角色；管理者顯示成「管理者（…）」。

## 四、資料群組

- 選單 id 52 回到「資料定義」底下，改名「**資料群組**」（`/teams`）。
- 權限鍵常數改成 `MagicObjectHelper.角色_資料群組`＝「資料群組」。
  - 啟動時 `RbacBackfillService` 把既有權限的「團隊清單」（含「團隊清單:edit」這類動作鍵）就地改鍵，連同角色的 `TabViewJson`。已經勾過的角色不會掉權限。
  - 一般使用者的初始權限不含它。
- 資料群組頁：
  - 清單多「成員數」欄。
  - 編輯表單多「成員」多選，列出啟用中的帳號。存檔時增刪 `UserTeam`（`TeamService.SyncMembersAsync`）。
- 使用者管理：
  - 「所屬團隊（專案）」換回「資料群組」多選。
  - **批次**：清單可以勾選多人，選一個群組後按「加入資料群組」或「移出資料群組」。已經在群組裡的人不會重複加入。

## 五、舊資料轉換（`DataGroupConversionService`，取代 `ProjectAccessBackfillService`）

每次啟動都跑，冪等：

1. 只在舊的 `ProjectMember` 表還在時做。migration **刻意不刪這張表**，由這裡用原生 SQL 讀。
2. 有成員的專案：建一個同名資料群組，把成員放進去，專案掛上它，升級前後看得到的人不變。名稱撞到既有群組時加「（專案）」，再撞就加序號。
3. 沒有成員的專案：掛到沒有成員的「待分配」群組，只有管理者看得到。不這樣做的話，它們會因為「沒指定群組＝公開」在升級後突然對所有人公開。
4. 已經有群組的專案不動。
5. 全部成功後 `DROP TABLE ProjectMember`，所以只會轉一次。
6. 會議上傳者的回填保留：從 AI 用量帳本取最早一筆轉錄的使用者。

Migration `AddProjectTeamRemoveDefaultTeams`：新增 `ProjectTeam`、刪除 `RoleView.DefaultTeamsJson`。

## 六、測試

`dotnet test` 全數通過（1112 筆）。

- `ProjectAccessTests` 改寫，涵蓋：
  - 規則：沒群組＝公開、有交集才看得到、管理者全看、未歸屬會議只給上傳者。
  - `ResolveProjectGroups` 保留別人的群組；非管理者只能選自己的群組。
  - 看不到的專案不能改也不能刪。
  - 資料群組成員同步、使用者批次加入與移出。
  - 轉換：同名群組、撞名加尾碼、待分配、刪表後第二次不動作、上傳者回填。
- `RoleConsolidationServiceTests` 改成 `DefaultRoleSeederTests`，新增「不動任何人的角色」。
- `RbacBackfillServiceTests`：新增「團隊清單」改鍵不掉權限；刪掉角色預設團隊的案例。
- `EffectiveTeamResolverTests`：只回傳直接所屬的群組。
- `MeetingServiceTests` 的種子資料從「專案成員」改成「資料群組」。
- `ApiIntegrationTests`：別的群組的專案回 404；自己建立的專案帶自己的群組、看得到，負責人照表單。

## 七、升級後請實測

1. 舊專案變成同名資料群組，看得到的人跟升級前一樣；沒有成員的專案在「待分配」，只有管理者看得到。
2. 在資料群組頁把某人加進群組，他就看得到那個群組的專案。
3. 使用者管理勾選多人，批次加入或移出群組。
4. 多角色的權限取聯集，例如某人只有檢視權限。
5. 沒有指定群組的專案所有人都看得到。
6. 原本勾了「團隊清單」的角色，改名後仍然看得到「資料群組」頁。
