# 首次登入強制改密碼、停用帳號在登入頁擋下、拿掉「設定 API 密碼」選單（0.4.112 → 0.4.113）

使用者照「上架前人工測試清單」實測後，回報三點：

> 1-2：第一次登入，登入後並沒有被導到變更密碼頁。
> 1-4：設定 API 密碼功能是什麼呢？
> 1-5：處理邏輯不夠清楚。點擊登入後跳進系統畫面一秒又跳回登入頁面，請改為直接在登入頁面就阻擋登入，不然會以為只是系統當機。

---

## 一、管理者給的密碼，第一次登入要改

**原因**：原本只有密碼是系統預設值「123456」時才會強制改密碼。管理者建立帳號時如果給了別的密碼，對方就不會被要求改。測試清單的這一項當初寫得不精確。

**使用者決定**：帳號密碼是管理者提供的，使用者第一次登入就要改成自己的。

**修改**：

- `MyUser` 新增 `MustChangePassword` 欄位（migration `AddMustChangePassword`）。既有帳號預設為 false，不受影響。
- 以下情況設為 true：
  - 管理者在使用者管理**新增帳號**。
  - 管理者**替別人重設密碼**。
  - 例外：改自己的帳號不設；`support` 帳號一律不設，因為它被禁止改密碼，設了會卡在改密碼頁出不去。
- 本人透過任何一個改密碼入口改完，就會清掉旗標。三個入口分別是：
  - 強制改密碼頁 `/ChangePassword`
  - 右上選單的「變更密碼」視窗
  - `/Profile`
- 判斷「要先改密碼」的條件變成：旗標為 true，**或**密碼仍是「123456」（舊規則保留）。
- 使用者管理是把畫面上的整筆資料蓋回資料庫，而畫面上沒有這個欄位。所以修改時會先帶回原值，避免單純改名稱就把「要先改密碼」清掉。

## 二、停用帳號在登入頁就擋下

**原因**：登入時沒有檢查帳號是否停用，所以會先登入成功、進到系統，接著才被發現停用而登出，看起來像當機。

**修改**：`MyUserServiceLogin.LoginAsync` 在**密碼驗證成功後**檢查帳號狀態。

- 帳號已停用時，停在登入頁並顯示「此帳號已停用，請聯絡管理者。」，同時寫一筆 `Login.Disabled` 稽核紀錄。
- 密碼錯誤時，一律回「帳號或者密碼不正確」，不讓人藉此試探哪些帳號存在或已停用。
- 網頁登入與 API 登入共用這個方法，兩邊同時生效。
- 輸入正確密碼不算失敗次數。
- 原本「進系統後發現停用就登出」的檢查保留，用來處理登入期間才被停用的情況。

## 三、「設定 API 密碼」從選單移除

**它是什麼**：設定一組密碼，讓外部程式可以透過系統介面登入、取得資料。主要對象是用 Google 單一登入、本來沒有密碼的人。但它寫入的其實就是**同一組網頁登入密碼**，對用帳號密碼登入的人來說等於第二個「變更密碼」，名稱很容易讓人誤會。

**使用者決定**：從右上使用者選單拿掉。

- 頁面程式保留，之後要接外部系統時再開放。
- 目前只能直接輸入網址 `/Profile` 進入。

## 測試

`dotnet test` 全數通過（1133 筆），新增 6 筆：

- `MyUserServicePasswordTests`
  - 新帳號要先改密碼，改完就不再要求。
  - 管理者替別人重設密碼後要改；本人改自己的則不會被要求。
  - 修改其他資料時不會清掉「要先改密碼」。
  - `support` 帳號不設旗標。
- `MyUserServiceLoginTests`
  - 停用帳號輸入正確密碼，回停用訊息。
  - 停用帳號輸入錯誤密碼，仍回一般錯誤訊息。

「上架前人工測試清單」的 1-2、1-4、1-5 已依新行為改寫，並新增 1-8：使用者選單沒有「設定 API 密碼」。
