# 專案負責人改成帳號下拉，負責人才能刪除（1.0.51 → 1.0.52）

- 文件版本：1.0
- 文件狀態：已實作
- 現行系統版本：1.0.52
- 首次實作版本：1.0.52
- 最後核對日期：2026/10/20

使用者要求：

> 專案負責人要是下拉選單，並且要是啟用帳號，身為負責人才可以刪除紀錄

決定：

- **負責人與管理者**可以刪除專案本身，以及專案底下**任何人的**會議、待辦、附件。
- 上傳者仍可刪自己上傳的會議（1.0.47 規則保留）；從專案移除、換影音檔、重新轉錄仍只限上傳者。
- 負責人候選人＝專案**主責＋協作團隊裡啟用中的帳號**，下拉可打姓名或帳號搜尋。
- 升級前手打的負責人自動對到帳號；對不到的不猜，留給人重新選。

---

## 一、原因

- 「負責人」原本是手打文字，打錯沒人提醒，也跟權限無關；刪除只看角色的 `delete` 與主責團隊（1.0.47），專案真正的負責人反而不一定刪得掉。
- 要讓「誰負責這個專案」對到一個真的帳號，並由這個人決定專案底下的資料能不能刪。

## 二、修改

- **資料**：`Project` 新增可空外鍵 `OwnerUserId`（→ `MyUser`，SetNull，導覽屬性 `OwnerUser`）；`Owner` 文字留著當**姓名快照**（存檔時由服務層填，給 API `owner`、清單搜尋與排序用）。
- **規則**（新的 `ProjectOwnerRules`，畫面 `ProjectService` 與 API `ProjectRepository` 共用）：
  - 候選人：主責＋協作團隊裡啟用中的帳號；存檔時驗證，不合格回「負責人必須是專案團隊裡啟用中的帳號，請重新選擇。」，沒選回「請選擇負責人。」。
  - 換負責人：只限主責團隊成員、目前的負責人、管理者（「只有主責團隊的成員或目前的負責人可以變更負責人。」）——不然協作團隊的人可以把自己設成負責人、拿到刪除權。協作團隊的人仍可改其他內容，負責人照原樣保留。
  - 修改時負責人與團隊都沒變就照原樣保留；對不到帳號的舊專案不換負責人就維持未指定，改團隊也不強迫補選；有負責人而團隊改了、他不在新團隊裡，就要重新選。
- **刪除**（`ProjectAccess.IsProjectOwner`／`OwnedProjectIds`，管理者一律放行）：
  - 刪除專案：只限負責人（取代 1.0.47 的主責團隊成員），「只有專案負責人可以刪除專案。」；已完成（封存）的專案非管理者仍要先重新開啟。
  - 刪除會議：上傳者**或**專案負責人，「只有上傳者或專案負責人可以刪除這筆會議紀錄。」。
  - 刪除待辦（畫面與 API）：只限負責人，「只有專案負責人可以刪除待辦。」；主待辦照舊連同子項目一起刪。以前同專案的人只要角色有 `delete` 就能刪。
  - 刪除附件（編輯專案時移除已存的檔案）：只限負責人，「只有專案負責人可以刪除附件。」；上傳不受限。
  - 這些刪除只要該頁的 `edit`，不看角色的 `delete`：當負責人的「一般使用者」能刪，不是負責人的「主管」不能刪。API `DELETE /api/Project/{id}`、`DELETE /api/Todo/{id}` 改要求 `edit`（會議的 DELETE 1.0.47 起已是 `edit`），被規則擋下回 400 `ValidationError`。
- **API 相容**：`ProjectCreateUpdateDto`／`ProjectDto` 多選填的 `ownerUserId`（回應一律帶回）；`owner` 改選填。新增時兩個至少給一個（都沒給回 400「負責人 不可為空白」）；只給 `owner` 時用它在候選人裡比對姓名或帳號，剛好一位才採用，否則存成未指定。修改時不帶 `ownerUserId` 保留原負責人。
- **畫面**：
  - 專案表單「負責人」改成可搜尋的下拉（選項「姓名（帳號）」），主責或協作團隊一改就重新載入，原負責人不在新清單裡就清空；新增時自己是候選人就預設帶自己（編輯不自動帶）；不能換負責人的人看到停用欄位與提示；沒有候選人時顯示「請先選擇主責團隊」；對不到帳號的舊資料提示「原負責人：XXX（找不到對應的帳號，請重新選擇）」。
  - 摘要列顯示負責人姓名，沒有負責人時「未指定」，對不到帳號的舊資料「未指定（原：XXX）」。
  - 「刪除專案」有 `專案項目:edit` 就出現，只有負責人（非管理者還要專案不是已完成）可按。
  - 會議頁「刪除」：上傳者或專案負責人，且有 `會議紀錄:edit`。
  - 待辦頁「刪除」：專案負責人，且有 `待辦事項:edit`、專案不是唯讀。
  - 專案表單已上傳附件的「移除」只有負責人看得到。
- **部署**：migration `AddProjectOwnerUser`（`20261020024620`）新增 `Project.OwnerUserId`、索引與外鍵（SQLite 會重建 `Project` 表），並執行回填 `Migrations/Sql/ProjectOwnerBackfill.cs`：舊的 `Owner` 去頭尾空白後與帳號的姓名或帳號完全相同、而且**剛好只對到一個帳號**才填，其餘留 null（不猜）。回填不看帳號是否啟用、是否在專案團隊裡。升級後請管理者看一下專案頁有沒有「未指定（原：XXX）」的專案，請主責團隊的人重新選負責人——在選好之前，那些專案只有管理者能刪除專案、待辦與附件。

## 三、測試

- 新增 `ProjectOwnerBackfillSqlTests.Backfill_ShouldMatchByNameOrAccount_OnlyWhenExactlyOneUser`（回填只在姓名或帳號剛好對到一位時才填）。
- `ProjectAccessTests` 新增 `OwnerCandidates_OnlyEnabledMembersOfProjectTeams`、`AddProject_OwnerMustBeEnabledTeamMember`、`ChangeOwner_OnlyPrimaryMemberOrCurrentOwner_AndOnlyOwnerRemovesFiles`；`DeleteProject_OnlyPrimaryTeamMemberOrAdmin_AndNotWhenArchived` 改寫為 `DeleteProject_OnlyOwnerOrAdmin_AndNotWhenArchived`。
- `MeetingServiceTests` 新增 `ProjectOwner_CanDeleteOthersMeeting`；`TodoChangeAndNotificationTests` 新增 `DeleteTodo_OnlyProjectOwnerOrAdmin_WebAndApi`。
- 既有測試的專案都補上負責人帳號。全部測試通過（1690 個）。
- 畫面行為靠上架前人工測試清單 13-19～13-31 驗證。
