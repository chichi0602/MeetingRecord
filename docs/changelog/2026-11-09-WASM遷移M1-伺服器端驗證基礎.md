## 一、原因

- WASM 前端會用登入 Cookie 呼叫 Web API，但現有 API 只認 JWT，而且：
  - Cookie 的使用者 Id 放在 `Sid`、`NameIdentifier` 放的是帳號字串；`[HasPermission]` 只讀 `NameIdentifier`，用 Cookie 打 API 一律被當成未登入。
  - Cookie 未登入時 302 到登入頁，前端只會拿到一頁 HTML。
  - 沒有一般的 CSRF 防護（只有上傳端點自己檢查標頭）。
- 登入狀態判斷（刪除、停用、沒有角色、需改密碼）綁在 `AuthenticationStateHelper.Check` 的畫面導向裡，WASM 拿不到。

## 二、修改（畫面完全沒變）

- **開分支** `wasm-migration`，版本 1.0.67 → 1.1.0（分支從 1.1.0 起，main 的 bug 修正仍是 1.0.x）。
- **Policy scheme** `MagicObjectHelper.ApiScheme`：帶 `Authorization: Bearer` 走 JWT，否則走登入 Cookie。6 個 CRUD controller 改用它；外部用戶端的行為不變。
- **`Web/Auth/UserClaims.GetUserId`**：先讀 `Sid`、再讀數字的 `NameIdentifier`；`HasPermissionAttribute` 改用它。
- **Cookie 的 `/api` 挑戰**：未登入回 401、沒權限回 403 的 `ApiResult` JSON，網頁照舊導向登入頁。
- **CSRF**：全域 `Filters/CookieApiCsrfFilter`——以 Cookie 驗證、會改資料的請求必須帶 `X-MeetingRecord-Client: 1`，否則 403；帶 Bearer 的不受影響。上傳分塊端點自己檢查 `X-MeetingRecord-Upload`（缺了回 400，行為不變），標 `[OwnCsrfCheck]` 跳過。
- **`Business/Services/Other/UserSessionService`**：登入狀態判斷抽出來；`AuthenticationStateHelper.Check` 改呼叫它、只負責導向（順序與行為不變）。進頁面的規則抽成純函式 `AuthenticationStateHelper.CanAccessPage`。
- **Session API**（新 `SessionController`，只需登入）：
  - `GET /api/v1/session`：狀態、帳號、是否管理者、是否需改密碼、是否預設維護帳號、有效權限鍵；刪除／停用／沒有角色回 403，`Data.Status` 是登出原因。
  - `GET /api/v1/session/menu`：依權限過濾好的側邊選單（新 `MenuItemDto`），規則與網頁側邊欄同一套（`SidebarMenuService` 新增依權限判斷函式載入的多載）。
  - 兩支列入授權守門掃描的「只需登入」白名單並寫明理由。
- 新 DTO：`Dtos/Sessions/SessionDto`、`MenuItemDto`。
- 文件：[開發慣例與限制速查](../architecture/開發慣例與限制速查.md) §4、[Web API 設計慣例](../architecture/Web%20API%20設計慣例.md)、[認證授權與權限機制](../security/認證授權與權限機制.md)、[09 號遷移評估](../planning/09-Blazor-WASM-遷移評估與測試策略.md) 新增「十、之二 M1 進度」、`CLAUDE.md`。

## 三、測試

- 新增 `CookieApiTests`（用真的網頁登入表單取得 Cookie，不偽造 claims）：Cookie 能打既有 CRUD API；Cookie 寫入沒帶防偽標頭 403、帶了 200；Bearer 寫入不需要標頭；未登入打 API 回 401 JSON 而不是 302；Session 的管理者、權限鍵與 `IPermissionChecker` 一致、需改密碼、登入後被停用回 403 與登出原因；選單依權限過濾（一般使用者看不到使用者管理與只限管理者的項目，管理者看得到）。
- 新增 `UserClaimsTests`（Cookie／JWT／只有帳號／未登入四種）。
- 既有 `AuthenticationStateHelperTests`、上傳端點缺防偽標頭回 400 等全部照過；全套 1,874 則通過，端對端全套照跑。

## 四、已知尚未處理

- 需改密碼的帳號以 Cookie 直接呼叫 CRUD API 目前沒有擋（網頁會先導到改密碼頁；判斷「仍是預設密碼」要驗一次密碼雜湊，放進每次 API 呼叫太慢）。M2 開放更多寫入 API 前補上。
- `GET /api/Auth/me` 維持只給 JWT（它的欄位依 JWT 的 claims 組成）；WASM 前端用 `GET /api/v1/session`。
