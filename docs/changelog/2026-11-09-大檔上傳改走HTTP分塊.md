# 大檔上傳改走 HTTP 分塊（1.0.59 → 1.0.60）

- 文件版本：1.0
- 文件狀態：已實作
- 現行系統版本：1.0.60
- 首次實作版本：1.0.60
- 最後核對日期：2026/11/09

使用者要求（WASM 遷移前置工作 D，見 [09-Blazor-WASM-遷移評估與測試策略](../planning/09-Blazor-WASM-遷移評估與測試策略.md) §4.6）：

> 分塊 HTTP 上傳

決定（與使用者確認）：涵蓋會議影音檔與專案附件；AI 問答附件（最大 20 MB）維持原樣。

---

## 一、原因

- 影音檔與專案附件原本經 Blazor 連線（SignalR）串流上傳。IIS 正式機上傳 127 MB 的 mp4 約 11 秒就逾時，整條連線中斷、頁面空白，DbContext 跟著釋放（[會議上傳進度與連線中斷](2026-10-08-會議上傳進度與連線中斷.md) §4 記的備案就是改走 HTTP）。
- 改成 WASM 時上傳本來就要改走 HTTP，先在 Server 版落地。

## 二、修改

- **瀏覽器端** `wwwroot/js/chunk-upload.js`：直接從 `<input type="file">` 取檔，每塊 8 MB 依序 `PUT`；每塊失敗重試 3 次（1／3／9 秒）；401 視為登入失效、404／409 表示伺服器那頭不要了就安靜收手、400／413 不重試；送不下去時回呼伺服器讓這趟上傳失敗。
- **端點** `Controllers/UploadChunkController.cs`：`PUT /api/v1/uploads/{uploadId}/chunks/{index}`。
  - 走**網頁登入 Cookie**（「API 一律 JWT」的明文例外），授權靠「工作階段擁有者＝目前使用者」，找不到或不是自己的一律 404；
  - 必須帶 `X-MeetingRecord-Upload: 1`（防跨站請求偽造）；
  - 免除全站 "api" 限流（共用桶每分鐘 120 次，1 GB 就要 128 塊）；
  - `[SkipStatusCodePages]`：.NET 10 的 Cookie 驗證對 API 回空白 401，全站狀態碼頁面會把它重跑成 405，瀏覽器就會誤判成網路問題一直重試（實測發現）；
  - 瀏覽器傳到一半斷線或中止時安靜結束，不記成系統例外（實測發現原本會記一筆 `ConnectionResetException`）。
- **工作階段** `Uploads/ChunkedUploadStore.cs`（singleton）：分塊用 `Pipe` 接成一個 `Stream`，讀得慢時下一塊的請求會等（背壓）；依序寫入、重送已收過的塊不重複寫；寫入管線不吃請求的取消權杖（否則被取消時資料已進管線、編號還沒加，重送就會寫兩次）；2 分鐘沒收到下一塊就當成中斷。
- **元件入口** `Uploads/BrowserFileUploader.cs`（scoped）：建工作階段、叫 JS 開始送、回傳串流；釋放時結束工作階段並叫 JS 停止。`FileDropZone` 新增 `InputElement` 給 JS 取檔。
- **會議紀錄頁**與**專案頁附件**：把 `file.OpenReadStream(...)` 換成分塊上傳的串流，**服務層一行都沒改**——驗證、進度（右下角面板與其他視窗）、從列上或面板取消、新增的會議取消時連帶刪除、失敗時刪孤兒檔與面板標失敗，全部沿用。
- 「取消上傳」的說明更新：不再是「經連線傳送、暫停會斷線」，而是 2 分鐘沒收到下一塊就當成中斷。
- 與原規劃的差異：原本打算先把整個檔案暫存到磁碟、再新增「開始／完成」服務方法提交；實作改成把分塊直接接成串流交給既有服務層，少一次 1 GB 的磁碟複製、少一組要重寫的取消與失敗邏輯。
- 文件：[檔案上傳機制](../features/檔案上傳機制.md) §3.0.1、[會議紀錄 PRD](../prd/會議紀錄-prd.md) 已知限制、[開發慣例與限制速查](../architecture/開發慣例與限制速查.md) §4、[Web API 設計慣例](../architecture/Web%20API%20設計慣例.md)、[Web API 端點目錄](../architecture/Web%20API%20端點目錄.md)、[測試指南](../guides/測試指南.md)、09 號評估 §4.6。
- 版本 1.0.59 → 1.0.60。

## 三、測試

- 新增 25 則：`ChunkedUploadStoreTests` 15 則、`ApiIntegrationTests.Upload.cs` 7 則（用 App 自己的 Cookie 票證簽登入 Cookie）、`MeetingServiceTests` 3 則（服務層讀分塊串流：完整存檔、等下一塊時從面板取消會刪掉新增的會議、瀏覽器放棄時走上傳失敗並保留會議）；`ApiAuthorizationConventionTests` 白名單加上這支端點。全套 1,829 則通過。
- 瀏覽器實測（Edge 無頭模式、獨立的測試資料庫）：
  - 專案附件：60 MB＋12 KB 兩個檔案，分 8＋1 塊，1.3 秒傳完，暫存檔 SHA-256 與原檔一致。
  - 會議影音：60 MB 分 8 塊，存檔後排入轉錄，落地檔案 SHA-256 與原檔一致。
  - 取消：600 MB 檔案、上傳頻寬限制 4 MB/s，傳 3 塊後從列上按「取消上傳」→ 伺服器記錄使用者取消、剛新增的會議被刪除、沒有留下檔案，取消之後沒有再送任何分塊，也沒有錯誤紀錄。
- 沒有在 IIS 上實測（本機是 Kestrel）；分塊 8 MB 低於 IIS 預設 30 MB 的請求上限，部署後建議用一個 200 MB 以上的檔案在正式環境試傳一次。
