# 專案附件暫存檔殘留修正（1.0.64 → 1.0.65）

- 文件版本：1.0
- 文件狀態：已實作
- 現行系統版本：1.0.65
- 首次實作版本：1.0.65
- 最後核對日期：2026/11/09

使用者要求：

> 先修暫存檔殘留的問題

---

## 一、原因

- 1.0.64 部署上傳實測時發現：專案頁選附件後按確定存檔，伺服器暫存資料夾 `%TEMP%\MeetingRecord\pending-uploads` 每次都留下一份暫存檔（單檔最大 1 GB），正式機長期會吃滿磁碟。
- `ProjectViewView.SaveModalAsync` 為每個待上傳檔開讀檔串流，**到 `finally` 才關**；存檔成功後卻先呼叫 `ClearPendingFiles()` 刪暫存檔。串流還開著，Windows 上刪不掉，例外被吞成 Warning，清單又已清空，之後再也沒人刪。
- 取消、移除附件、關掉頁面的路徑沒有開串流，都刪得掉；只有「存檔成功」這條漏。
- 另外網站當掉或重啟時正在編輯的暫存檔也沒人清（1.0.59 以前正式機曾整個重啟過）。

## 二、修改

- `ProjectViewView.razor.cs`：關串流抽成區域函式 `DisposeUploadStreams()`，存檔成功時**先關串流再刪暫存檔**；`finally` 照舊再關一次（已關則無事）。存檔失敗時暫存檔照舊保留，讓使用者重送。
- 新增 `Web/Uploads/PendingUploadTempFiles.cs`：暫存資料夾路徑的單一來源（專案頁改用它），以及 `DeleteStale`——刪掉最後寫入時間超過指定時間的 `*.tmp`，個別刪不掉寫 Warning 後繼續。
- `Program.cs`：啟動時清掉 **24 小時以前**的暫存殘檔，有刪才寫 Information（筆數），失敗只寫 Error、不擋啟動。只刪舊的，是因為 IIS 回收時新舊行程會短暫並存，舊行程的使用者可能正開著編輯視窗。正式機現有的殘檔會在部署後第一次啟動時清掉。
- 端對端測試主機把網站的 `TMP`／`TEMP` 指到測試自己的臨時資料夾（`E2EAppFixture.PendingUploadPath`），不再把暫存檔留在本機的 %TEMP%。
- 文件：[檔案上傳機制](../features/檔案上傳機制.md) §3.0.1、[開發慣例與限制速查](../architecture/開發慣例與限制速查.md) §4、§7、[正式部署與安全檢查清單](../operations/正式部署與安全檢查清單.md)（升級一節涵蓋到 1.0.65，加部署後檢查項）、1.0.64 changelog 的已知事項註明已修。
- 版本 1.0.64 → 1.0.65。

## 三、測試

- 端對端 PRJ-07（專案附件上傳並下載）加斷言：存檔後暫存資料夾沒有這一則上傳的檔案。修正前執行失敗（殘檔還在），修正後通過。
- 新增 `PendingUploadTempFilesTests`：24 小時以前的刪掉、以內的保留；非 `.tmp` 不動；資料夾不存在回 0。
- 手動：在暫存資料夾放一個改成 2 天前的檔與一個新檔，啟動網站後只剩新檔，日誌有 `Count=1`。
- 全套測試與端對端全套照跑。
