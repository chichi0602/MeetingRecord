# 日期欄 Enter 送出與重複新增修正（1.0.61 → 1.0.62）

- 文件版本：1.0
- 文件狀態：已實作
- 現行系統版本：1.0.62
- 首次實作版本：1.0.62
- 最後核對日期：2026/11/09

使用者要求：

> 修正截止日 Enter 送出和重複新增的問題

決定（與使用者確認）：同一個寫法的八個 CRUD 表單一起修。

---

## 一、原因（M0 基準端對端測試發現，見 [M0 基準測試報告](../testing/2026-11-09-M0-基準測試報告-1.0.61.md) 附註）

1. **日期欄按 Enter 直接送出表單**：表單的 `EditForm` 接 Enter 當送出；日期欄、下拉的搜尋框按 Enter 本來是「套用日期／選這一項」，但事件冒泡上去被當成送出，打的值還沒套用就存檔。開發慣例寫「下拉、日期…欄位外層有 `@onkeydown:stopPropagation`」，實際只有專案表單有（而且漏了「狀態」），其他七個都沒有。實測：待辦截止日打完日期按 Enter，存成沒有期限。
2. **重複新增**：八個表單按 Enter 都是「先 `Task.Delay(200)` 等繫結回寫、再進存檔防護」，等候的 200ms 不受防護。這段時間按「確定」或長按 Enter，第一次存完、防護解除後，延遲的那一次又存一次。待辦、會議、專案有 `isSaving` 但擋不到這個窗口；分類、團隊、提示詞、使用者、角色五個表單完全沒有防護（靠名稱不可重複擋，第二次跳「名稱已存在」）。實測：待辦 Enter 後立刻按確定，新增兩筆。

## 二、修改

- **新增 `Components/Commons/FormSubmitGate.cs`**：表單送出閘門，旗標在等候**之前**就立起來；「確定」與 Enter 共用，送出中（含等候回寫）再送一律忽略，存完或失敗後復原。
- **八個 CRUD 表單**（待辦、會議、專案、分類、團隊、提示詞、使用者、角色）：
  - `OnModalOKHandleAsync` 改為 `submitGate.RunAsync(...)`；原本把存檔邏輯寫在 `OnModalOKHandleAsync` 裡的五個表單，原樣搬成 `SaveModalAsync`（邏輯不變）。
  - Enter 改為 `submitGate.RunAsync(SaveModalAsync, FormSubmitGate.EnterSettleDelay)`，不再自己 `Task.Delay(200)`。
  - 待辦、會議、專案保留 `isSaving` 名稱，改成讀 `submitGate.IsBusy` 的唯讀屬性，其餘用到它的地方（`ConfirmLoading`、背景事件延後重新載入、存檔中不能關窗）不必改。
  - 專案表單：存檔前「附件讀取中」檢查與存檔後補做的重新載入一起放進閘門；補做重新載入改成迴圈，重新載入期間又來的要求也會處理到，不會留一筆沒人處理。
- **下拉與日期欄外層包 `<div @onkeydown:stopPropagation="true">`**（14 個欄位）：待辦（所屬專案、屬於、截止日、優先度、狀態）、會議（會議日期、分類）、專案（狀態）、分類（負責團隊）、團隊（成員）、提示詞（分類）、使用者（角色、額外角色、團隊）。
- **另修一個測試主機偶發啟動失敗**（測試時發現）：`Program.cs` 先檢查 `LogManager.Configuration` 不是 null、再讀一次去設定變數；兩次之間另一台主機關閉把全域 NLog 設定清成 null，就丟 `NullReferenceException`（API 整合測試偶發一則失敗）。改成只讀一次存進區域變數。
- 文件：[開發慣例與限制速查](../architecture/開發慣例與限制速查.md)（表單 Enter 送出一節）、[對話窗 UI 設計規範](../architecture/對話窗%20UI%20設計規範.md)、[畫面與欄位字典](../guides/畫面與欄位字典.md) §0.5、[建立一個新 CRUD 操作網頁說明](../guides/建立一個新%20CRUD%20操作網頁說明.md)、[測試指南](../guides/測試指南.md)。
- 版本 1.0.61 → 1.0.62。
