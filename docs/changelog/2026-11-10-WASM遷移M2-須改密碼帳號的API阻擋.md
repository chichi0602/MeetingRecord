# WASM 遷移 M2：須改密碼帳號的 API 阻擋（1.1.3 → 1.1.4）

- 文件版本：1.0
- 文件狀態：已實作
- 現行系統版本：1.1.4
- 首次實作版本：1.1.4
- 最後核對日期：2026/11/10

使用者要求：

> 開始 M2（第一項：補上「須改密碼」帳號以 Cookie 直接呼叫 API 的缺口；做法選「登入時記下來，API 只看標記」）

---

## 一、原因

- 網頁（Blazor Server）靠 `AuthenticationStateHelper.Check` 把須改密碼的人導去改密碼頁；但 1.1.0 起 WASM 前端用登入 Cookie 直接打 API，API 沒擋，等於可以繞過「第一次登入先改密碼」。JWT 也有同樣的空窗：權杖發出後管理者才重設密碼，權杖到期前仍可呼叫。
- 判斷「仍是預設密碼」要驗一次密碼雜湊，放進每次 API 呼叫太慢。

## 二、修改

- `MyUserServiceLogin.LoginAsync`：登入成功時若明碼仍是預設密碼，就把 `MustChangePassword` 標記打開（只多一次字串比較；support 帳號例外，它不能在網頁改密碼）。
- 新增全域 `Filters/MustChangePasswordFilter`：已登入、標記打開的帳號，API 一律回 403 `ApiResult`，`Errors["Reason"]` 為 `must-change-password`。只讀一個欄位。Cookie 與 JWT 都擋。
- 例外端點標 `[AllowWhenMustChangePassword]`：目前是 Session API（WASM 前端靠它知道該導去改密碼）。之後的改密碼 API 也會標。
- WASM 端 `ApiClient` 收到這個 403 就整頁導到 `/ChangePassword`。
- 文件：[認證授權與權限機制](../security/認證授權與權限機制.md)、[開發慣例與限制速查](../architecture/開發慣例與限制速查.md) §4、09 號新增「十、之三 M2 進度」。
- 版本 1.1.3 → 1.1.4。

## 三、測試

- `MyUserServiceLoginTests`：預設密碼登入後打開標記；support 用預設密碼不標記；用自己的密碼不標記。
- `MustChangePasswordApiTests`：標記打開的 Cookie 帳號打 CRUD API 得 403（帶原因）、打 Session 得 200；JWT 帳號在權杖發出後被打開標記即受擋，標記清掉後恢復。
- 抓錯檢查：拿掉 filter 註冊、拿掉登入時打標記 → 上述三則失敗。驗完已還原。
- 全套單元／API 與端對端照跑。

## 四、已知限制

- 升級前就用預設密碼登入、還沒重新登入的人，要等下次登入才會被標記；這段期間網頁照舊會把他導去改密碼頁。
