## 一、原因

- 專案頁是 M3 最後一個核心頁，也是最大的一頁（畫面約 2600 行）。
- 先開 API，頁面才能搬到 WASM。
- 依賴盤點後拆成三版：
  - **（一）1.1.24**：專案本身——清單、表單、附件、團隊、負責人；
  - **（二）1.1.25**：專案底下的會議、會議紀錄與 PDF、待辦抽取；
  - **1.1.26**：頁面搬過去。
- M3 報告順延到 1.1.27。

## 二、修改

### 2.1 既有五支改走 `ProjectService`

- `ProjectRepository` 刪除。這是最後一個 Repository，`Business/Repositories` 整個資料夾移除。
- 規則與 Server 頁同一份：團隊、負責人、封存、資料範圍、稽核。
- 原本只有 API 才有的相容規則照舊：
  - 新增沒帶主責團隊時，用自己 Id 最小的團隊；
  - 只帶負責人姓名時，在團隊裡找同名帳號，剛好一位才採用；
  - 修改時沒帶的團隊、負責人保留；名詞、名冊、分類沒帶或空的也保留。
- 「只帶姓名、對不到帳號仍照舊建立並留下姓名」的規則搬進服務層，成為只給 API 用的參數 `legacyOwnerName`，畫面不傳。
- 對外的搜尋邏輯搬成 `ProjectService.SearchFlatAsync`，行為不變。
- `ProjectDto` 只加欄位：
  - `primaryTeamName`、`collaboratorTeamNames`、`isArchived`；
  - `files`（只有單筆帶）；
  - 呼叫者的旗標 `isProjectOwner`、`canManageTeams`、`canChangeOwner`。
- 服務的新增、修改加 `via` 參數，API 寫 `via=Api`。附件下載的稽核由 API 呼叫時多帶 `via=Api`。

### 2.2 畫面用的新端點（都標 `[HasPermission(專案項目, …)]`）

| 端點 | 權限 | 說明 |
|---|---|---|
| `GET selectable?includeArchived=` | 檢視 | 專案選擇器 |
| `GET last-selected`、`PUT last-selected` | 檢視 | 上次選的專案，記在帳號上 |
| `GET teams/primary`、`GET teams/collaborator?include=` | 新增或修改 | 團隊選項 |
| `GET owner-candidates?primaryTeamId=&collaboratorTeamIds=` | 新增或修改 | 負責人候選人 |
| `POST form`、`PUT {id}/form` | 新增／修改 | 見下方說明 |
| `GET files/{fileId}` | 檢視 | 附件下載，伺服器寫稽核 |

表單存檔（`POST form`、`PUT {id}/form`）：

- 整筆覆寫：名單傳空就清空、日期可留空；
- 可帶 `uploadIds`（新附件）與 `removedFileIds`（移除附件）；
- 驗證與 Server 頁的表單同一份；
- 新增時專案已建立、但附件存不進去：回 400 也帶 `projectId`，畫面可切成修改模式重送。

### 2.3 專案附件上傳

- 新端點 `POST api/v1/uploads/project-attachments`（專案項目新增或修改任一）：
  - 比照 Server 頁，選好檔案就開始傳、先落到暫存檔（`ProjectAttachmentUploads`）；
  - 存專案時帶上傳編號；
  - 存檔成功才刪暫存檔，失敗留著可直接重送。
- 查狀態、取消、回報失敗沿用 `api/v1/uploads/{id}` 那三支，兩種上傳都認，只認擁有者。

### 2.4 孤兒清理

`ProjectRepository`、`CombinedSearchHelper`、`ReplaceExpressionVisitor`，以及 AutoMapping 的 `Project ↔ ProjectDto／ProjectCreateUpdateDto` 四組對應都只剩舊的 Repository 在用，一併刪除。

### 2.5 文件與版本

- 文件：
  - Web API 端點目錄、認證授權、權限與資料可見範圍總覽；
  - 專案項目 PRD、架構總覽、系統功能總覽、開發慣例與限制速查、檔案上傳機制；
  - 09 號「十、之四」。
- 版本 1.1.23 → 1.1.24。

## 三、外部可見的行為變更

| 項目 | 以前 | 現在 |
|---|---|---|
| `POST`／`PUT api/v1/Project` 名稱與看得到的專案重複 | 409 | 允許（與畫面一致，名稱不唯一） |
| `GET api/v1/Project/{id}` | 只有專案欄位與團隊 Id | 多帶團隊名稱、封存、附件、呼叫者的權限旗標 |
| `POST api/v1/Project/search` | 同上 | 多帶團隊名稱、封存、權限旗標（不帶附件） |
| 新增、修改的稽核 | 由 Repository 寫 | 由服務層寫，摘要照舊 `via=Api` |
| 新端點 | — | 見「二、修改」2.2、2.3 |

## 四、測試

- **既有的 API 相容測試照過**（`ApiIntegrationTests` 的專案案例）：
  - 沒指定主責時用建立者的團隊；
  - 只帶姓名時留下姓名；
  - 不含名單的修改不會清掉名詞表；
  - 稽核 `via=Api`；
  - 看不到的專案回 404。
- 第一次跑抓到「只帶姓名、對不到帳號」會被服務層的「請選擇負責人」擋下，因此補了 `legacyOwnerName`。
- 授權矩陣：
  - 加進專案的既有五支與五支新端點，驗 401、只缺那個動作時 403 並留稽核、只有那個動作時成功；
  - 「新增或修改任一」的四支（團隊選項兩支、負責人候選人、附件上傳）另驗只有檢視時 403、只有新增或只有修改都成功。
- L2 `ProjectApiTests`：
  - 同名允許；
  - 表單帶附件新增，下載內容正確、稽核 `via=Api`、暫存檔已刪；
  - 表單整筆覆寫會清空名單，對外 PUT 照舊保留；
  - 非負責人移除附件被擋；
  - 拿別人的上傳編號被擋；
  - 附件太大回 400，取消後不留暫存檔；
  - 選擇器依封存篩選、上次選的專案存取。
- 抓錯檢查（驗完都已還原）：

  | 暫時改壞 | 結果 |
  |---|---|
  | 對外 PUT 不再保留空名單 | 相容測試與 `ProjectApiTests` 失敗 |
  | 存檔後不刪暫存檔 | 附件案例失敗 |
  | 附件上傳不檢查擁有者 | 「別人的上傳」案例失敗 |

- 另記一件事：這版途中 Razor 編譯伺服器的狀態壞掉，沒改過的檔案也報語法錯誤；`dotnet build-server shutdown` 後恢復，與程式無關。
- 全套單元／API 與端對端照跑；專案頁仍是 Server 頁，PRJ 系列照過。
