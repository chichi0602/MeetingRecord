## 文件目的

說明專案附件與會議影音檔如何上傳、儲存、刪除，以及實體檔案的目錄組織策略。

> 0.4.24 起舊的「工作項目」與「會議記錄」附件機制（`MyTasFile` / `MeetingFile`）已下架。
> 0.4.27 新增「會議紀錄」的影音檔與逐字稿，採**內嵌欄位**而非附件子表——因為一筆會議只搭配一個影音檔。

## 1. 檔案對照

| 主表 | 檔案來源 | 設定檔欄位（`SystemSettings.ExternalFileSystem`） |
|------|----------|----------------------------------------------------|
| `Project` | 附件子表 `ProjectFile`（一對多） | `ProjectFilePath` |
| `Meeting` | 主表內嵌欄位 `MediaRelativePath`（一對一） | `MeetingMediaPath` |
| `Meeting` | 主表內嵌欄位 `TranscriptRelativePath`（轉錄產物） | `MeetingTranscriptPath` |
| （無主表）| AI 問答對話，路徑由「範圍＋對象 Id」算出（0.4.60）| `AiChatPath` |

預設值（`appsettings.json`）：

```json
"ProjectFilePath":           "C:\\temp\\MeetingRecord\\ProjectFile",
"MeetingMediaPath":          "C:\\temp\\MeetingRecord\\MeetingMedia",
"MeetingTranscriptPath":     "C:\\temp\\MeetingRecord\\MeetingTranscript",
"AiChatPath":                "C:\\temp\\MeetingRecord\\AiChat"
```

啟動時 `Program.cs` 會呼叫 `EnsureDirectoryExists(...)` 自動建立缺少的目錄。

## 2. 目錄組織策略

每筆紀錄的附件依「主表的建立時間」決定目錄分層：

```
{各模組根目錄}/
└── {年}/                ← 主表 CreatedAt.Year
    └── {月}/             ← 主表 CreatedAt.Month（補零兩碼）
        ├── 檔案 A
        ├── 檔案 B
        └── ...
```

例：2026 年 5 月新增的專案，其檔案會落在 `C:\temp\MeetingRecord\ProjectFile\2026\05\` 下。
會議影音檔與逐字稿採同一策略，分別落在 `MeetingMedia\2026\08\` 與 `MeetingTranscript\2026\08\`。

## 3. 上傳行為

### 3.1 專案附件

- 一筆紀錄可上傳多個檔案。
- 單檔最大 1GB（前端與後端皆需驗證）。
- 在「新增模式」下，使用者上傳的檔案會先暫留於 UI；按下「儲存」後，Service 才將實體檔案落地到對應年月目錄，並建立資料庫紀錄。
- 在「修改模式」下：
  - 既有檔案會列在清單中，可手動移除（標記為待刪除）。
  - 可繼續加入新檔案，落地行為同新增模式。
  - 按下「儲存」後：被標記為待刪除的紀錄連同實體檔案一併移除；新檔案則寫入目錄並登入資料庫。

### 3.2 會議影音檔

- 一筆會議只搭配**一個**影音檔，重新選檔即取代（連同舊逐字稿一起清掉）。
- 允收政策集中在 `MeetingMediaPolicy`（`MeetingRecord.Business/Helpers/`），**前端與服務層共用同一份判斷**：單檔上限 1GB，副檔名白名單涵蓋常見音訊與視訊格式（`.mp3`、`.wma`、`.wav`、`.m4a`、`.mp4`、`.mkv`…）。
- 白名單只需涵蓋「FFmpeg 讀得懂」的格式——所有檔案在送交語音轉錄前都會先轉成 mp3，不受轉錄 API 的格式限制約束。
- 主資料必須先存檔（拿到 `Id`）才會上傳檔案；上傳失敗時 Modal 不關閉，讓使用者直接重試。
- **上傳進度**：`MeetingFileStore.SaveMediaAsync` 以 80KB 緩衝區逐段複製，每當百分比變動就回報一次 `IProgress<int>`，畫面以 AntDesign `Progress` 顯示。
- 落檔成功後狀態設為「待處理」並排入背景轉錄佇列，逐字稿完成後寫入 `MeetingTranscriptPath`（**UTF-8 含 BOM**，避免記事本開啟亂碼）。
- 完整流程見 [會議紀錄 PRD](../prd/會議紀錄-prd.md)。

## 4. 刪除行為

### 4.1 專案附件（子表 + Cascade）

當使用者刪除主表紀錄（例如刪除一筆專案）：

1. EF Core 因 `DeleteBehavior.Cascade`（見 `BackendDBContext.OnModelCreating`）會自動刪除附件資料表的 row。
2. **實體檔案**仍須由 Service 層在刪除前蒐集 `StoredPath`、刪除主表後再呼叫 `File.Delete(...)`。
3. 若實體檔案刪除失敗（例如已被外部移動），Service 應寫入 `Warning` 等級日誌，但不阻斷主表刪除流程。

### 4.2 會議影音檔（內嵌欄位，無 Cascade 可依賴）

刪除 `Meeting` 時**沒有子表**，因此沒有 Cascade 可以倚靠：Service（`MeetingService.DeleteAsync`）與 API（`MeetingController.Delete`）都必須在刪除資料列後，各自呼叫 `MeetingFileStore.TryDeleteMedia` / `TryDeleteTranscript` 清掉影音檔與逐字稿。刪檔失敗一樣只寫 `Warning`。

**AI 問答對話（0.4.60）**：一段對話一個 `.jsonl`，路徑由「範圍＋對象 Id」直接算出來
（`AiChat\project\3.jsonl`、`AiChat\meeting\12.jsonl`），**不依年／月分層，資料庫也不存路徑**
——這是它與影音檔／逐字稿最大的不同，也是 `AiChatMessage` 資料表能整個移除的原因。
格式為 JSONL（一行一則訊息），新增一輪對話只 append 兩行。編碼 UTF-8 含 BOM，
**讀取時第一行要去掉 BOM**，否則第一則訊息會被當成壞行而默默消失。

同樣沒有 Cascade 可以倚靠：`MeetingService.DeleteAsync` 與 `ProjectService.DeleteAsync`
各自呼叫 `AiChatStore.TryDelete`，漏掉就會留下孤兒檔案。

## 5. 對應 DTO 與設定強型別

`SystemSettings.ExternalFileSystem` 透過 `IOptions<SystemSettings>` 注入到 Service：

```csharp
public class FooService(IOptions<SystemSettings> options, ILogger<FooService> logger)
{
    private readonly ExternalFileSystem fileSystem = options.Value.ExternalFileSystem;
    // ...
}
```

於 Service 內統一使用 `fileSystem.ProjectFilePath` 等屬性，**禁止**直接從 `IConfiguration` 讀字串。

會議檔案的路徑解析、落檔、讀取與刪除集中在 `MeetingFileStore`（`MeetingRecord.Business/Services/Other/`），`MeetingService`、`TranscriptionJobRunner` 與 `MeetingController` 都透過它操作實體檔案，不各自組路徑。

## 6. `/UploadFiles` 靜態資源對應

`Program.cs:319-325`：

```csharp
app.UseStaticFiles(new StaticFileOptions
{
    FileProvider = new PhysicalFileProvider(systemSettings.ExternalFileSystem.DownloadPath),
    RequestPath = "/UploadFiles"
});
```

- `DownloadPath` 是「公開可下載」目錄；任何放在這裡的檔案都會被 `/UploadFiles/...` 對外服務。
- 附件目錄（`ProjectFilePath`）**不**直接對應 `/UploadFiles`；下載這些附件需透過 Controller 端點，由 Service 驗證權限後再回傳檔案串流。
- 會議目錄（`MeetingMediaPath`、`MeetingTranscriptPath`）同樣**不**對外服務。逐字稿為高敏感內容，**刻意沒有任何下載端點**：預覽走 Blazor 服務層（Cookie 驗證 + 團隊守門）讀檔後直接顯示在 Modal，少一個 HTTP 檔案輸出面就少一處要顧的授權。

## 7. 實作檢查清單

新增「檔案功能」時請確認：

- [ ] 一對多附件：Entity 已新增 `XxxFile` 子表，並在 `BackendDBContext.OnModelCreating` 設定 `Cascade`。
      一對一檔案：欄位內嵌於主表，**並記得沒有 Cascade 可依賴**，刪除時要自行清實體檔案。
- [ ] `appsettings.json` 已新增對應根目錄欄位，並在 `SystemSettings.ExternalFileSystem` 模型中對映。
- [ ] `Program.cs` 已呼叫 `EnsureDirectoryExists` 包含新目錄。
- [ ] Service 對外提供 `Add` / `Update` / `Delete` 時皆同步處理實體檔案。
- [ ] 有允收政策（格式白名單、大小上限）時，前端與服務層共用同一份判斷，兩邊都要擋。
- [ ] 對外下載端點需做角色檢查與檔名清洗，避免路徑跳脫攻擊；沒有必要就不要開端點。
