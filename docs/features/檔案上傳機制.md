# 檔案上傳機制

- 文件版本：1.9
- 文件狀態：已實作
- 現行系統版本：1.0.67
- 首次實作版本：0.1.61

## 文件目的

說明專案附件與會議影音檔如何上傳、儲存、刪除，以及實體檔案的目錄組織策略。

> 0.4.24 起舊的「工作項目」與「會議記錄」附件機制（`MyTasFile` / `MeetingFile`）已下架。
> 0.4.27 新增「會議紀錄」的影音檔與逐字稿，採**內嵌欄位**而非附件子表——因為一筆會議只搭配一個影音檔。

## 1. 檔案對照

| 主表 | 檔案來源 | 設定檔欄位（`SystemSettings.ExternalFileSystem`） |
|------|----------|----------------------------------------------------|
| `Project` | 附件子表 `ProjectFile`（一對多） | `ProjectFilePath` |
| `Meeting` | 主表內嵌欄位 `MediaRelativePath`（一對一） | `MeetingMediaPath` |
| `Meeting` | 主表內嵌欄位 `TranscriptRelativePath`（轉錄產物） | `MeetingTranscriptPath` |
| （無主表）| AI 問答對話，路徑由「範圍＋對象 Id」算出（0.4.60）| `AiChatPath` |

預設值（`appsettings.json`）：

```json
"ProjectFilePath":           "C:\\temp\\MeetingRecord\\ProjectFile",
"MeetingMediaPath":          "C:\\temp\\MeetingRecord\\MeetingMedia",
"MeetingTranscriptPath":     "C:\\temp\\MeetingRecord\\MeetingTranscript",
"AiChatPath":                "C:\\temp\\MeetingRecord\\AiChat"
```

啟動時 `Program.cs` 會呼叫 `EnsureDirectoryExists(...)` 自動建立缺少的目錄。

## 2. 目錄組織策略

每筆紀錄的附件依「主表的建立時間」決定目錄分層：

```
{各模組根目錄}/
└── {年}/                ← 主表 CreatedAt.Year
    └── {月}/             ← 主表 CreatedAt.Month（補零兩碼）
        ├── 檔案 A
        ├── 檔案 B
        └── ...
```

例：2026 年 5 月新增的專案，其檔案會落在 `C:\temp\MeetingRecord\ProjectFile\2026\05\` 下。
會議影音檔與逐字稿採同一策略，分別落在 `MeetingMedia\2026\08\` 與 `MeetingTranscript\2026\08\`。

## 3. 上傳行為

### 3.0 上傳 UI：共用的 `FileDropZone`（0.4.77 起）

兩個上傳入口（專案附件、會議影音檔）都改用 `Components/Commons/FileDropZone`，
可以**拖拉或點擊**。先前兩處各寫各的裸 `<InputFile>`。

實作是**零 JS**：把檔案放到 `<input type="file">` 上時瀏覽器會自己設定 `files` 並觸發 `change`，
所以那個 input 只要以 `opacity:0` 蓋滿整個拖放區即可。服務層與兩個上傳 DTO 完全沒動。

四個踩過的坑（詳見 [拖拉上傳與 Enter 送出](../changelog/2026-09-16-拖拉上傳與Enter送出.md)）：

- ⚠️ CSS 必須用 `::deep`——`class` 傳給 `<InputFile>` 這個元件時拿不到 scope 屬性
- ⚠️ `dragleave` 要用計數器配對，否則外框會閃爍
- ⚠️ 每次選完要換 `@key` 重建 input，否則**重選同一個檔案不會觸發 `change`**
- ⚠️ 單檔模式拖入多個檔案，Chrome 會**整個靜默拒絕**，所以提示要寫明「一次一個」

⚠️ **`accept` 對「拖入」不可信**（瀏覽器只在檔案挑選對話框套用它，各家對 drop 的處理並不一致），
所以服務層的白名單是唯一可信的守門員——見第 7 節的檢查清單。

### 3.0.1 檔案位元組改走 HTTP 分塊上傳（1.0.59 實作，1.0.60 起）

會議影音檔與專案附件的檔案內容**不再經 Blazor 連線（SignalR）傳送**。原本 `IBrowserFile.OpenReadStream()` 經連線串流，IIS 上 127 MB 的 mp4 約 11 秒就逾時並拖垮整條連線（見 [會議上傳進度與連線中斷](../changelog/2026-10-08-會議上傳進度與連線中斷.md)）。AI 問答附件（最大 20 MB）維持原樣。

| 環節 | 位置 | 說明 |
|------|------|------|
| 瀏覽器端 | `wwwroot/js/chunk-upload.js` | 直接從 `<input type="file">` 取檔，每塊 8 MB 依序 `PUT`；每塊失敗重試 3 次（1／3／9 秒）；401 視為登入失效、404／409 表示伺服器那頭不要了（安靜收手）、400／413 不重試 |
| 端點 | `Controllers/UploadChunkController.cs` | `PUT /api/v1/uploads/{uploadId}/chunks/{index}`，原始 body。走**網頁登入 Cookie**（「API 一律 JWT」的明文例外），授權靠「工作階段擁有者＝目前使用者」（找不到或不是自己的一律 404）；必須帶 `X-MeetingRecord-Upload: 1` 防 CSRF；免除全站 "api" 限流（1 GB＝128 塊）；`[SkipStatusCodePages]`，否則空白 401 會被重跑成 405 |
| 工作階段 | `Uploads/ChunkedUploadStore.cs` | singleton。每趟上傳一個 `ChunkedUploadSession`，分塊用 `Pipe` 接成一個 `Stream`（背壓：讀得慢時下一塊的請求會等，每趟最多約一兩塊在記憶體）；依序寫入、重送已收過的塊不重複寫；2 分鐘沒收到下一塊就當成中斷 |
| 元件入口 | `Uploads/BrowserFileUploader.cs` | scoped。`OpenAsync(input, fileIndex, fileName, fileSize)` 建工作階段並叫 JS 開始送，回傳的 `Stream` 直接交給服務層；釋放時結束工作階段並叫 JS 停止 |

**只有「傳位元組」改走 HTTP**：元件只是把 `file.OpenReadStream(...)` 換成 `BrowserFileUploader` 的串流，服務層一行都沒改——驗證、進度（右下角面板與其他視窗）、從列上或面板取消、新增的會議取消時連帶刪除、失敗時刪孤兒檔與面板標失敗，全部沿用。

- 瀏覽器放棄（重試用完、登入失效）→ 工作階段 `Fail` → 服務層讀到 `UploadInterruptedException`（`Share/Helpers`，是一種 `IOException`），走既有「上傳失敗」流程；1.0.67 起**原因會帶到畫面與右下角面板**（例如「影音檔上傳失敗：登入已失效，請重新登入後再上傳。」、專案附件「{檔名} 上傳失敗：…」）。其他例外的訊息是內部細節，仍只顯示一般的失敗訊息。
- 使用者關掉分頁 → 2 分鐘沒有分塊 → 同上。
- 服務層讀完、拒絕或被取消 → 釋放工作階段 → 瀏覽器下一塊拿到 409 而停止。
- ⚠️ 寫入管線**不吃請求的取消權杖**：被取消時資料可能已進管線而編號還沒加，重送就會寫兩次。
- ⚠️ 讀完之前**不可重建 input**（`FileDropZone.Reset`），JS 要從它取檔；`FileDropZone.InputElement` 提供元素參考。
- 專案附件仍先落到 `%TEMP%/MeetingRecord/pending-uploads` 暫存檔（`fileIndex` 對應 `input.files` 的順序），存檔流程不變。
- ⚠️ 存檔成功後**先關讀檔串流、再刪暫存檔**（1.0.65）：1.0.64 以前順序相反，Windows 上刪不掉，每存一次留一份。網站啟動時另由 `PendingUploadTempFiles.DeleteStale` 清掉 24 小時以前的殘檔（當掉／重啟時編輯中的暫存檔）；只刪舊的，是因為 IIS 回收時新舊行程會短暫並存。

### 3.1 專案附件

- 一筆紀錄可上傳多個檔案。
- 單檔最大 1GB（前端與後端皆需驗證）。
- 在「新增模式」下，使用者上傳的檔案會先暫留於 UI；按下「儲存」後，Service 才將實體檔案落地到對應年月目錄，並建立資料庫紀錄。
- 在「修改模式」下：
  - 既有檔案會列在清單中，可手動移除（標記為待刪除）。
  - 可繼續加入新檔案，落地行為同新增模式。
  - 按下「儲存」後：被標記為待刪除的紀錄連同實體檔案一併移除；新檔案則寫入目錄並登入資料庫。

### 3.2 會議影音檔

- 一筆會議只搭配**一個**影音檔，重新選檔即取代（連同舊逐字稿一起清掉）。
- 允收政策集中在 `MeetingMediaPolicy`（`MeetingRecord.Business/Helpers/`），**前端與服務層共用同一份判斷**：單檔上限 1GB，副檔名白名單涵蓋常見音訊與視訊格式（`.mp3`、`.wma`、`.wav`、`.m4a`、`.mp4`、`.mkv`…）。
- 白名單只需涵蓋「FFmpeg 讀得懂」的格式——所有檔案在送交語音轉錄前都會先轉成 mp3，不受轉錄 API 的格式限制約束。
- 主資料必須先存檔（拿到 `Id`）才會上傳檔案；上傳失敗時 Modal 不關閉，讓使用者直接重試。
- **上傳進度**：`MeetingFileStore.SaveMediaAsync` 以 80KB 緩衝區逐段複製（1.0.60 起讀的是分塊上傳的串流，進度跟著分塊到達而前進），每當百分比變動就回報一次 `IProgress<int>`，畫面以 AntDesign `Progress` 顯示。
- 落檔成功後狀態設為「待處理」並排入背景轉錄佇列，逐字稿完成後寫入 `MeetingTranscriptPath`（**UTF-8 含 BOM**，避免記事本開啟亂碼）。
- 完整流程見 [會議紀錄 PRD](../prd/會議紀錄-prd.md)。

## 4. 刪除行為

### 4.1 專案附件（子表 + Cascade）

當使用者刪除主表紀錄（例如刪除一筆專案）：

1. EF Core 因 `DeleteBehavior.Cascade`（見 `BackendDBContext.OnModelCreating`）會自動刪除附件資料表的 row。
2. **實體檔案**仍須由 Service 層在刪除前蒐集 `StoredPath`、刪除主表後再呼叫 `File.Delete(...)`。
3. 若實體檔案刪除失敗（例如已被外部移動），Service 應寫入 `Warning` 等級日誌，但不阻斷主表刪除流程。

### 4.2 會議影音檔（內嵌欄位，無 Cascade 可依賴）

刪除 `Meeting` 時**沒有子表**，因此沒有 Cascade 可以倚靠：Service（`MeetingService.DeleteAsync`）與 API（`MeetingController.Delete`）都必須在刪除資料列後，各自呼叫 `MeetingFileStore.TryDeleteMedia` / `TryDeleteTranscript` 清掉影音檔與逐字稿。刪檔失敗一樣只寫 `Warning`。

**AI 問答對話（0.4.60，0.4.79 改為一個對象多段）**：一段對話一個 `.jsonl`，路徑由
「範圍＋對象 Id＋對話 Id」直接算出來（`AiChat\project\3\<對話 Id>.jsonl`、
`AiChat\meeting\12\<對話 Id>.jsonl`），**不依年／月分層，資料庫也不存路徑**
——這是它與影音檔／逐字稿最大的不同，也是 `AiChatMessage` 資料表能整個移除的原因。
格式為 JSONL（一行一則訊息），新增一輪對話只 append 兩行。編碼 UTF-8 含 BOM，
**讀取時第一行要去掉 BOM**，否則第一則訊息會被當成壞行而默默消失。

對話 Id 前段是 `yyyyMMddHHmmssfff`，**檔名本身就帶時間**，列清單不必開檔就能排序。
檔案的**第一行**是一則 `role: "meta"` 的紀錄（標題、建立者、建立時間），刻意不另開 meta 檔
——那會讓「一段對話」變成兩個檔案要同步。⚠️ **meta 行不是訊息**，`ReadHistoryAsync` 與
索引映射都要排除它；少排除一邊，畫面上會冒出一則空白的「AI 助理」，或編輯時改到隔壁那一則。

0.4.79 之前的單檔（`AiChat\project\3.jsonl`）會在**第一次列出該對象的對話清單時自動搬進新結構**，
搬移是「先寫新檔、成功後才刪舊檔」，中途失敗寧可留兩份也不要兩邊都沒有；資料夾已存在就跳過（冪等）。

**AI 問答附件（0.4.95）**：存在對話檔旁邊的 `<對話 Id>.files/`（例如 `AiChat\project\3\<對話 Id>.files\`），磁碟檔名是隨機的 GUID ＋原副檔名；原始檔名、種類與大小記在對話檔那一則提問的 `attachments` 欄位。列清單只列 `*.jsonl`，附件資料夾不會被誤認成對話。刪除一段對話時 `TryDeleteConversation` 會連附件資料夾一起刪；提問失敗時剛存的附件也會刪掉，不留孤兒。讀附件一律只取 `storedName` 的檔名部分——對話檔可以手動編輯，不能被拿來做路徑跳脫。

同樣沒有 Cascade 可以倚靠：`MeetingService.DeleteAsync` 與 `ProjectService.DeleteAsync`
各自呼叫 `AiChatStore.TryDelete`，漏掉就會留下孤兒檔案。
⚠️ 0.4.79 起 `TryDelete` 刪的是**整個對象資料夾**（並順手清掉還沒轉檔的舊單檔）；
只刪一個檔的話，該對象底下其他幾段對話會永遠留在硬碟上。

## 5. 對應 DTO 與設定強型別

`SystemSettings.ExternalFileSystem` 透過 `IOptions<SystemSettings>` 注入到 Service：

```csharp
public class FooService(IOptions<SystemSettings> options, ILogger<FooService> logger)
{
    private readonly ExternalFileSystem fileSystem = options.Value.ExternalFileSystem;
    // ...
}
```

於 Service 內統一使用 `fileSystem.ProjectFilePath` 等屬性，**禁止**直接從 `IConfiguration` 讀字串。

會議檔案的路徑解析、落檔、讀取與刪除集中在 `MeetingFileStore`（`MeetingRecord.Business/Services/Other/`），`MeetingService`、`TranscriptionJobRunner` 與 `MeetingController` 都透過它操作實體檔案，不各自組路徑。

## 6. `/UploadFiles` 靜態資源對應

`Extensions/ApplicationBuilderExtensions.cs` 的 `UseConfiguredDownloadStaticFiles()`（`Program.cs` 於 `#region 綁定靜態資源` 呼叫；`DownloadPath` 為空白時不掛載）：

```csharp
app.UseStaticFiles(new StaticFileOptions
{
    FileProvider = new PhysicalFileProvider(systemSettings.ExternalFileSystem.DownloadPath),
    RequestPath = "/UploadFiles"
});
```

- `DownloadPath` 是「公開可下載」目錄；任何放在這裡的檔案都會被 `/UploadFiles/...` 對外服務。
- 附件目錄（`ProjectFilePath`）**不**直接對應 `/UploadFiles`；下載這些附件需透過 Controller 端點，由 Service 驗證權限後再回傳檔案串流。
- 會議目錄（`MeetingMediaPath`、`MeetingTranscriptPath`）同樣**不**對外服務。逐字稿為高敏感內容，**刻意沒有任何下載端點**：預覽走 Blazor 服務層（Cookie 驗證 + 團隊守門）讀檔後直接顯示在 Modal，少一個 HTTP 檔案輸出面就少一處要顧的授權。

## 7. 實作檢查清單

新增「檔案功能」時請確認：

- [ ] 一對多附件：Entity 已新增 `XxxFile` 子表，並在 `BackendDBContext.OnModelCreating` 設定 `Cascade`。
      一對一檔案：欄位內嵌於主表，**並記得沒有 Cascade 可依賴**，刪除時要自行清實體檔案。
- [ ] `appsettings.json` 已新增對應根目錄欄位，並在 `SystemSettings.ExternalFileSystem` 模型中對映。
- [ ] `Program.cs` 已呼叫 `EnsureDirectoryExists` 包含新目錄。
- [ ] Service 對外提供 `Add` / `Update` / `Delete` 時皆同步處理實體檔案。
- [ ] 有允收政策（格式白名單、大小上限）時，前端與服務層共用同一份判斷，兩邊都要擋。
- [ ] 對外下載端點需做角色檢查與檔名清洗，避免路徑跳脫攻擊；沒有必要就不要開端點。
