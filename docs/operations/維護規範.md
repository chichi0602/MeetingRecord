## 文件目的

定義本專案在「每次提交異動」時必須遵循的最低規範，包含版本遞增、文件同步、檔案編碼，以及 commit 前的自我檢查清單。

> 任何 PR 或 commit 在進入主線前，請先逐項對照本文件確認。

## 1. 規範一：每次更新必須 bump 版本

唯一版本來源是：

```
src/MeetingRecord/MeetingRecord.Web/appsettings.json
└─ SystemSettings.SystemInformation.SystemVersion
```

### 1.1 版號格式

顯示格式維持三碼加日期：

```
Major.Minor.Patch (YYYY/MM/DD)
```

例：`0.4.1 (2026/06/22)`

### 1.2 遞增規則

**每次提交異動一律將最後一碼（`Patch`）+1**，不依異動性質區分：

- 不論是 bug 修正、文件更新、新增功能、新 API、新 Entity 或架構調整，都只把 `Patch` +1。
- **不進位**：`0.4.9 → 0.4.10`（最後一碼是獨立遞增的整數，不會進位到 `Minor`）。
- `Major`、`Minor` 不會自動變動；僅在明確決定「里程碑版本」時才由人工調整（一般開發流程不會用到）。
- 範例：`0.4.0 → 0.4.1 → 0.4.2 → …`

### 1.3 日期同步

括號內日期必須更新為 commit 當天日期，格式 `YYYY/MM/DD`，與 `Asia/Taipei` 時區的當天一致。

### 1.4 檢查方式

```powershell
Select-String -Path "src/MeetingRecord/MeetingRecord.Web/appsettings.json" -Pattern "SystemVersion"
```

## 3. 規範三：UTF-8 編碼

### 3.1 適用範圍

- 所有 `.md`、`.razor`、`.cs`、`.json`、`.css` 文件。

### 3.2 編碼規定

- **`docs/` 下所有 `.md` 一律使用「UTF-8 含 BOM」**：CI 的 [`scripts/Test-DocsEncoding.ps1`](../../scripts/Test-DocsEncoding.ps1) 會遞迴檢查，缺少 BOM 或含取代字元（`U+FFFD`）即失敗。
- 其餘原始碼（`.razor`、`.cs`、`.json`、`.css`）採 UTF-8 即可。
- 編輯後請確認繁體中文未出現 `?`、亂碼方塊或其他不可讀字元。

### 3.3 PowerShell 自我驗證

```powershell
Get-ChildItem -Path docs,readme.md -Recurse -Include *.md | ForEach-Object {
    $bytes = [IO.File]::ReadAllBytes($_.FullName)
    $hasBom = $bytes.Length -ge 3 -and $bytes[0] -eq 0xEF -and $bytes[1] -eq 0xBB -and $bytes[2] -eq 0xBF
    "{0,-50}  bytes={1,-8} bom={2}" -f $_.Name, $bytes.Length, $hasBom
}
```

> ⚠️ 對於 PowerShell 自身建立的檔案（例如 `Out-File`、`Set-Content`），請一律使用 **`-Encoding utf8BOM`**。
>
> **不要寫 `-Encoding utf8`**：在 Windows PowerShell 5.1 它含 BOM，但在 **pwsh 7 它是「UTF-8 無 BOM」**，
> 會直接被 `scripts/Test-DocsEncoding.ps1` 判定失敗。寫 `utf8BOM` 在 pwsh 7 下行為明確。

## 4. Commit 前自我檢查清單

請於 commit 前逐項確認（建議貼到 PR 描述中）：

- [ ] `appsettings.json` 的 `SystemVersion` 已遞增（含日期）。
- [ ] 本次異動所影響的 docs 文件已同步更新（對照第 2 節）。
- [ ] 所有新增 / 修改檔案皆採 UTF-8（無亂碼）。
- [ ] 新 / 改 API：已寫 `Debug` 進站、`Information` 成功、`Warning` 失敗、`Error` 例外四類日誌。
- [ ] 新 / 改 Entity：已在 `MeetingRecord.AccessDatas/Migrations/` 產生 migration（系統啟動時會自動 `Migrate()`，不需手動 `Update-Database`），`MigrationSnapshotTests` 通過。
- [ ] 新 / 改頁面或權限鍵：`Menu.json` / `MenuPermissionMap` / `MagicObjectHelper` / 頁面 `CheckAccessPage` 已同步，並已驗證 Sidebar 權限項目。
- [ ] 終端使用者看得到的操作有變：[`系統使用說明.md`](../guides/系統使用說明.md) 已同步，`HelpManualTests` 通過。
- [ ] 本機 `dotnet build src/MeetingRecord/MeetingRecord.Web/MeetingRecord.Web.csproj` 成功。
- [ ] 文件相對連結可正確開啟（`docs/` 內互引、與 `readme.md` 之間皆通）。

## 6. 文件表頭與封存規則

### 6.1 表頭五行

`docs/` 下每份文件（含 changelog）在 H1 下方都固定有五行表頭：

```
- 文件版本：x.y
- 文件狀態：已實作｜維護中｜已封存（…不再維護）
- 現行系統版本：0.4.118
- 首次實作版本：0.4.xxx
- 最後核對日期：2026/10/08
```

### 6.2 表頭更新規則

- **只有逐句對過程式碼的文件**，才把「現行系統版本／最後核對日期」改成當次版本與當天日期 —— 這兩欄的意思是「在這個版本、這一天，內容和程式一致」。
- 只改了局部內容、沒有整份重核的文件，**只把「文件版本」+0.1**，不動另外兩欄。
- 程式參照一律寫錨點（檔案＋類別／方法／區塊名稱），**不要寫 `檔案:行號`** —— 行號一改程式就漂移，錨點才找得到。

### 6.3 封存規則

規劃快照、樣板時期遺留的文件不刪除，改為封存：

- `文件狀態` 改為 `已封存（…不再維護）`；表頭其餘四行**凍結**，不隨系統版本推進。
- 表頭下方加註：📌 這是快照、⚠️ 表頭刻意凍結，以及「📌 現況差異（YYYY/MM/DD 核對 0.4.xxx）」列出與現況不同之處；內文維持原貌。
- 所屬子目錄的 `README.md` 把封存文件與活文件分區列出（例：[`planning/README.md`](../planning/README.md)）。
- superpowers 設計規格是「實作前的設計定案」，事後不改寫內文；與現況不同處同樣以「📌 現況差異」註記。
