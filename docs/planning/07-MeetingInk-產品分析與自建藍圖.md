## 二、Meeting Ink 產品全貌

### 2.1 定位

以生成式 AI 從 Zoom／Google Meet／Teams／Webex 等會議自動產生**逐字稿 + 智慧摘要**，同時支援線上、實體與混合會議。差異化訴求是「深耕在地與亞洲語言」——支援台語、客語、粵語這類多數國際競品略過的語言。

### 2.2 四種輸入通道（產品的真正骨幹）

| 通道 | 運作方式 | 工程難度〔推論〕 |
| --- | --- | --- |
| 瀏覽器分頁錄製 | 免安裝，登入後錄本機／分頁音訊，錄製中可開即時字幕與翻譯 | 中：`getDisplayMedia` + `getUserMedia` 混音、串流上傳、瀏覽器相容性 |
| 手機 App | iOS／Android 原生錄音，內容與桌機同步 | 中：離線錄音、斷點續傳、背景錄音權限 |
| 線上會議機器人 | 機器人自動加入會議並全程錄製，會後自動推送逐字稿與摘要 | **高**：無頭瀏覽器叢集、各平台入會流程與反自動化機制、行事曆排程 |
| 檔案上傳 | 上傳 mp3／wav／m4a（≤2GB），亦支援 YouTube 與 Podcast 連結 | 低：本專案 0.4.27 已具備同型能力 |

行事曆整合（Google Calendar、Outlook Calendar）是機器人通道的前置條件：先讀到會議時間與連結，才談得上「自動出席」。

**機器人的公開運作細節**（自建時的關鍵規格參考）：會議開始前約 1 分鐘加入；20 分鐘內未被接受即自動離開；Google Meet 需開啟「任何擁有連結的人都可申請加入」。這三條說明機器人是以**外部訪客身分**入會，而不是靠官方 API 側錄——這是自建時最容易低估的部分。

### 2.3 AI 能力層

| 能力 | 對外規格 |
| --- | --- |
| 語音轉文字 | 28+ 語言（含台語、客語、粵語）；FAQ 另提「繁中／英／日等 13 種」，推測為**主力調校語言**與「可辨識語言」的差異 |
| 語者辨識與分段 | 全方案提供；建議 11 人以內，超過準確率遞減 |
| 專業術語 | 自建術語清單，支援新增／編輯／**同義詞**，於逐字稿與摘要自動套用；企業版可 CSV 批次匯入 |
| AI 摘要 | 20 種預設模板（通用會議、業務檢視、教育、醫療等）；區塊可增刪、拖拉排序、一鍵開關；企業版可由管理員建立共用模板 |
| 翻譯 | 逐字稿翻譯、會議中即時翻譯、混語會議多語轉錄 |
| 即時字幕 | Pro 以上方案；企業版另有「即時雙向翻譯」 |
| MCP | 把會議紀錄變成 AI 可查詢的知識庫 |

### 2.4 MCP：值得特別留意的設計

Meeting Ink 提供 MCP Server，讓 Claude Desktop／Claude Code、ChatGPT 開發者模式、Cursor、Codex CLI、Gemini CLI 等以自然語言查詢會議庫。公開的設計約束很值得參考：

- **唯讀**（「只能讀、不能寫」）——把 AI Agent 的爆炸半徑限制在讀取。
- 兩種授權：OAuth 瀏覽器授權（一般工具）／API Key（Cursor、Claude Code）。
- 工具面：依名稱／狀態／日期瀏覽會議、取得含語者標記的逐字稿、取得 Markdown 摘要、查詢多語內容、查詢時數與配額用量。
- 不吃錄製與轉錄配額；API Key 不記錄於日誌；下載內容有大小上限；只能存取自己帳號或被分享的會議。

**這是一個「不必自建 AI 對話介面」的策略**：把資料開放給使用者既有的 AI 工具，成本遠低於自建 RAG 聊天室，卻能宣稱「AI 知識庫」。自建時建議照抄這個順序——先做唯讀 MCP／API，再考慮自建對話。

### 2.5 方案分級（配額設計的參考）

| 項目 | Basic | Pro | Pro+ | Enterprise |
| --- | --- | --- | --- | --- |
| 價格 | 免費 | 約 US$9.99／月（官網年繳 NTD$2,790） | 約 US$18.99／月（年繳 NTD$5,490） | 客製 |
| 月錄製時數 | 3 小時 | 20 小時 | 40 小時 | 團隊共享 |
| 單檔／單次時長 | 30 分鐘 | 2 小時 | 3 小時 | 4 小時 |
| 自訂術語 | 3 | 5 | 20 | 200+ |
| AI 摘要版本數 | 2 | 2 | 3 | 5 |
| 自訂摘要模板 | 1 | 2 | 3 | 20+ |
| 即時字幕與翻譯 | ✗ | ✓ | ✓ | ✓ |
| 即時雙向翻譯 | ✗ | ✗ | ✗ | ✓ |
| MCP 串接 | ✓ | ✓ | ✓ | ✓ |
| 企業後台／SAML SSO | ✗ | ✗ | ✗ | ✓ |

**可讀出的分級邏輯**：

1. **時數是主計價單位**，因為它直接對應 STT 的變動成本；「月時數」擋總量、「單次時長」擋長尾昂貴請求。
2. **即時字幕放在付費門檻**——即時串流的成本與工程複雜度都遠高於批次轉錄。
3. **術語數／模板數／摘要版本數**是零邊際成本的軟性差異化，用來拉開層級而不增加成本。
4. **SSO 與管理後台**留給企業版，這是 B2B 的標準切法。

### 2.6 平台與夥伴

支援網頁、iOS／Android、Windows、Mac、Chrome 擴充（Kuro）。網站標示的技術夥伴為 Microsoft Azure（雲端與儲存）、AWS（全球架構）、OpenAI（NLP）、NVIDIA（AI 加速）。FAQ 另述音檔存放於 Azure 伺服器、會議資料**不用於 AI 訓練**、信用卡資訊由第三方支付處理。登入支援 Google／Microsoft／Apple ID／Passkey（最多 5 組）／密碼／企業 SAML SSO。

## 四、系統架構藍圖〔建議〕

### 4.1 元件視圖

```
[瀏覽器錄音]  [行動 App]  [檔案上傳]  [會議機器人叢集]  [行事曆同步]
      \            |           |              /              /
       \___________|___________|_____________/______________/
                              |
                     [API Gateway / Web]
                              |
              +---------------+----------------+
              |               |                |
        [媒體儲存]      [作業佇列]        [中繼資料庫]
      物件儲存／檔案     queue + worker      關聯式 DB
                              |
        +-------------+-------+-------+--------------+
        |             |               |              |
  [前處理 Worker] [STT Worker]  [摘要 Worker]  [翻譯 Worker]
      FFmpeg         STT API        LLM API       LLM／MT API
        +-------------+-------+-------+--------------+
                              |
                   [搜尋索引／向量庫（選配）]
                              |
              +---------------+---------------+
        [Web UI／即時進度]            [開放介面：REST + MCP]
```

### 4.2 一場會議的狀態機

單一狀態欄位驅動整條流水線，是可靠性的關鍵。建議狀態集：

```
Created ─► MediaUploaded ─► Preprocessing ─► Transcribing ─► Transcribed
                                                                 │
                                    ┌────────────────────────────┤
                                    ▼                            ▼
                             Summarizing ─► Summarized    Translating ─► Translated
                                    │
                                    ▼
                                 Failed（可從最後一個成功階段重跑）
```

設計要點：

1. **每個階段的產物落地後才推進狀態**，讓任一段失敗都能從上一段的產物續跑，不必重付 STT 費用。
2. **冪等**：每段音訊以 `(meetingId, segmentIndex, mediaHash)` 當鍵，重跑不重複計費、不重複寫入。
3. **重試策略分級**：429／5xx 指數退避重試；4xx 參數錯誤直接失敗並記錄可讀原因給使用者。
4. **進度可觀測**：以「已完成分段數／總分段數」回報百分比，不要只給轉圈圈。
5. **成本閘門**：進佇列前先估算成本（時長 × 單價），超過剩餘配額就擋在門口，不要做到一半才失敗。

### 4.3 為什麼一定要分段

長音檔分段（本專案現行為 15 分鐘）同時解決四件事：繞過供應商單檔上限、讓進度可回報、讓失敗只需重跑一段、讓多段可並行。代價是**跨段語境斷裂**——分段邊界要用重疊窗（例如前後各 5～10 秒）並在拼接時去重，否則邊界處會漏字或重複。

**兩個非顯而易見的決定**：

- `TranscriptSegment` 進**資料庫**而非只存檔案。本專案 0.4.27 是把逐字稿整份存 `.txt`，這對「唯讀預覽」夠用；但一旦要做語者標記、時間碼跳播、片段編輯、關鍵字定位、引用回溯，就必須有可查詢的段落表。這是升級成產品時第一個要改的資料決策。

## 七、AI 管線的工程細節（最容易做壞的地方）

1. **術語注入有三個時機**，成本與效果差很多：
   - **STT 熱詞參數**（若供應商支援）：效果最好，但受數量上限限制——這正是產品把術語數做成方案配額的原因。
   - **逐字稿後處理取代**：便宜、可控，但同音異義會誤傷，必須有同義詞表與大小寫／邊界規則。
   - **摘要提示詞夾帶**：只修正摘要不修正逐字稿，成本最低。

   建議三者並用，並在設計文件裡明確寫下各自負責哪一類錯誤。
2. **長逐字稿超出上下文窗**：採 map-reduce——分段各自摘要 → 合併 → 依模板區塊重寫。要保留中間產物，否則除錯無門。
3. **模板即提示詞組裝器**：模板不是一段固定提示詞，而是「區塊清單」。每個區塊帶自己的指令，執行時依啟用狀態與順序組裝。這樣「拖拉排序、一鍵開關」才是資料驅動而非改程式。
4. **幻覺控管**：要求摘要中的每個決議／待辦附上來源時間碼，UI 可點擊跳回逐字稿。這既是可信度，也是產品差異化。
5. **品質量測**：STT 用 WER（自建 20～50 段標註語料，涵蓋主力語言與口音）；摘要用人工抽檢評分表（涵蓋完整性、正確性、可執行性）。**沒有量測就無法換模型**——換供應商時只能靠感覺，這是長期最貴的技術債。
6. **供應商抽象化**：`ITranscriptionProvider`／`ISummarizationProvider`／`ITranslationProvider` 三個介面。本專案 0.4.27 已對轉錄做到這件事，方向正確，摘要與翻譯照做。

## 九、與本專案（MeetingRecord 0.4.27）的落差

| 能力 | Meeting Ink | 本專案現況 | 落差評估 |
| --- | --- | --- | --- |
| 檔案上傳轉錄 | 有（≤2GB） | **已具備**（≤1GB、FFmpeg、15 分鐘分段、Azure OpenAI STT） | 幾乎對齊 |
| 非同步與進度 | 有 | **已具備**（行程內 `Channel<int>` + 單一 worker、進度列、重新轉錄） | 單機單 worker，尚不可水平擴充 |
| 供應商抽象 | 不明 | **已具備** `ITranscriptionProvider` | 方向正確，摘要／翻譯待比照 |
| 提示詞維護 | 模板化（20 種內建、區塊拖拉） | **已具備**提示詞主資料 CRUD，但**從未送進模型** | 需補：變數代入 + LLM 呼叫 + 區塊化模板 |
| 摘要生成 | 核心能力 | **未實作** | 最大落差，也是最高投報 |
| 語者辨識 | 有 | 未實作（PRD 明列為非範圍） | 需先決定自建 diarization 或改用支援的供應商 |
| 逐字稿結構化 | 含語者與時間碼 | 整份 `.txt`，唯讀預覽 | 需改為段落表才能往上長 |
| 翻譯 | 有 | 未實作（PRD 明列為非範圍） | 批次翻譯成本低，可快速補 |
| 即時字幕 | Pro 以上 | 未實作（PRD 明列為非範圍） | 架構影響大，建議最後做 |
| 瀏覽器／App／機器人擷取 | 四通道 | 僅檔案上傳 | 機器人為獨立子專案等級 |
| MCP／開放 API | 有（唯讀） | 僅中繼資料 CRUD API | 投報率高，建議提前 |
| 配額與計費 | 完整分級 | 無 | 內部系統可延後；對外服務必做 |
| 租戶與分享 | 工作區 + SSO | 已有 RBAC + 團隊權控 | 基礎不錯，需補分享連結 |

**一句話**：本專案已經走完最枯燥的那一段（上傳、前處理、分段、非同步轉錄），缺的是**逐字稿之後的一切**。

## 十、分階段路線圖〔建議〕

| 階段 | 目標 | 交付 | 完成定義 |
| --- | --- | --- | --- |
| **M0**（已達成） | 音檔進得來、逐字稿出得去 | 上傳、前處理、STT、進度、重跑 | 對應 0.4.27 |
| **M1** | 逐字稿 → 會議紀錄草稿 | 提示詞變數代入、LLM 呼叫、摘要落地與人工編修 | 上傳一場 60 分鐘會議可得到可編修草稿；[會議紀錄產生流程 PRD](../prd/會議紀錄產生流程-prd.md) 後半段標記為已實作 |
| **M2** | 讓紀錄變成資產 | 逐字稿段落表（語者 + 時間碼）、批次翻譯、唯讀 REST + MCP、用量帳本 | 可用 Claude Code 查詢自己的會議庫 |
| **M3** | 擴大擷取通道 | 瀏覽器分頁錄音、行事曆同步；機器人視資源評估 | 免上傳即可錄一場線上會議 |

M1 是投報率最高的一步：它把現有系統從「轉錄工具」變成「會議紀錄系統」，且**不需要任何新基礎設施**——佇列、狀態、儲存、提示詞主資料都已就緒。

## 十一、風險登記簿

| 風險 | 影響 | 緩解 |
| --- | --- | --- |
| AI 成本失控 | 一場長會議可能吃掉整月預算 | 進佇列前估算成本並閘門化；`UsageLedger` 從第一天就寫；設每日花費告警 |
| 供應商變更定價或下架模型 | 服務中斷 | 三個 Provider 介面 + 設定檔切換；保留評估語料以便快速比較替代品 |
| 錄音法遵（單方／全體同意） | 法律責任 | 明確的告知同意流程；機器人入會時宣告；保留政策文件化 |
| 資料被拿去訓練 | 客戶信任崩塌 | 選用明確承諾不訓練的供應商方案；寫入第三方資料處理聲明並對外揭露 |
| 摘要幻覺 | 產出錯誤決議 | 引用時間碼、人工編修為必經步驟、UI 明示「AI 生成草稿」 |
| 語者辨識準確率隨人數下降 | 使用者體驗落差 | 對外明說建議人數上限（對標產品直接寫進 FAQ）；提供人工重新指派語者 |
| 單機單 worker 成為瓶頸 | 併發上不去 | M2～M3 前把佇列外部化（DB queue 或訊息中介） |
| 分段邊界漏字 | 逐字稿品質 | 重疊窗 + 拼接去重 + 邊界抽檢納入品質計畫 |

## 十二、成本模型（自建時先算這個）

端到端單場成本約為：

```
成本 = 儲存(GB·月)
     + 前處理 CPU 時間
     + STT 單價 × 音訊分鐘數
     + 摘要 LLM（輸入 token × 單價in + 輸出 token × 單價out）× 摘要版本數
     + 翻譯 token 成本 × 目標語言數
```

**經驗法則**：STT 通常是主要變動成本，摘要次之。逐字稿 token 量約為「音訊分鐘數 × 每分鐘字數 × 語言係數」——中文 1 字約 1～2 token，一小時會議的逐字稿常落在 1.5 萬～3 萬 token，摘要一次的輸入成本即由此決定；做 map-reduce 會讓輸入 token 再乘上約 1.2～1.5 倍。**先用一場真實會議實測一次，再回頭訂配額**——用推估訂價幾乎必錯。
