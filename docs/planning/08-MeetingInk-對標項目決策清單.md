## 怎麼用這份文件

1. 先看 **第一節決策摘要表**，那是全貌。
2. 對每一項，讀第二節的說明，在 `決定` 欄填入 **要做 / 不做 / 延後 / 待決**，並填決定日期與一句理由。
3. **「不做」也要寫理由**。半年後最貴的不是做錯決定，是想不起來當初為什麼不做，然後重新討論一遍。
4. 決定完的項目不要刪，留在文件裡。這份文件的價值在於**決策軌跡**，不是待辦清單。
5. 第五節列出**決策相依**——有些項目先決定會鎖死其他項目的選項，照那個順序決定比較省事。

> 所有工作量皆為**單人粗估人天**，只用來比較項目之間的相對大小，不是承諾。相依欄的代號指向本文件其他決策點。

## 二、功能決策點逐項說明

每一項的格式：**是什麼** → **為什麼值得做** → **不做會怎樣** → **風險／前提** → **建議**。

### D01　摘要生成（提示詞代入 + LLM 呼叫）

- **是什麼**：把已有的逐字稿套用已有的提示詞範本，呼叫 LLM 產生可編修的會議紀錄草稿。即 [會議紀錄產生流程 PRD](../prd/會議紀錄產生流程-prd.md) 未實作的後半段。
- **為什麼值得做**：這是整個系統從「轉錄工具」變成「會議紀錄系統」的那一步。基礎設施（佇列、狀態、儲存、提示詞主資料）全部就緒，不需要任何新元件。目前 `PromptTemplate` 的資料躺在資料庫裡從未被送進任何模型——這是最刺眼的半成品。
- **不做會怎樣**：使用者拿到一份幾萬字的逐字稿，還是得自己讀完手寫紀錄。0.4.26 與 0.4.27 兩個版本的投資無法變現。
- **風險／前提**：長逐字稿會超出上下文窗，需要 map-reduce；輸出品質需要人工編修流程配套（見 D09、D10）。
- **建議**：**要做，且優先於其他所有項目。**

### D02　逐字稿段落表（時間碼結構化）

- **是什麼**：把逐字稿從「整份 `.txt`」改為 `TranscriptSegment` 資料表（`Index`／`StartMs`／`EndMs`／`SpeakerId`／`Text`／`Confidence`）。
- **為什麼值得做**：它是四個後續能力的**共同前提**——語者標記（D03）、時間碼跳播與引用回溯（D09）、片段層級翻譯（D04）、關鍵字定位搜尋（D05）。現在改是 3–5 天，等三個功能都疊上去再改就是重寫。
- **不做會怎樣**：逐字稿永遠停留在唯讀預覽。上面那四項全部做不了，或是各自用醜陋的方式硬幹。
- **風險／前提**：需要 migration 與既有逐字稿的一次性轉換（或接受舊資料只有 `.txt`）。要決定 `.txt` 是否保留為備援。
- **建議**：**要做。** 這是本清單裡「現在不做、以後更貴」最明顯的一項。

### D03　語者辨識（diarization）

- **是什麼**：判斷逐字稿的每一段是誰說的，標成 Speaker 1／2／3，並允許人工改名。
- **為什麼值得做**：對標產品全方案都給。多人會議的逐字稿沒有語者標記，可讀性差很多。
- **不做會怎樣**：逐字稿是一整片沒有分角色的文字牆；摘要裡的「誰負責什麼」品質會下降。
- **風險／前提**：工作量落差極大（5–15 天）——**取決於選用的 STT 供應商是否原生支援**。目前用的 Azure OpenAI `gpt-4o-transcribe` 需先確認；若不支援，就要外掛獨立的 diarization 模型，成本與複雜度整個跳級。對標產品自己也承認 11 人以上準確率遞減。
- **建議**：**延後**，但**現在就花半天查清楚供應商支援度**——這個答案會決定它是 5 天還是 15 天，也可能反過來影響 STT 供應商的選擇。

### D04　批次翻譯

- **是什麼**：把逐字稿或摘要整份翻成指定語言（非即時）。
- **為什麼值得做**：技術上很便宜——就是再呼叫一次 LLM。有跨國會議需求時價值很高。
- **不做會怎樣**：沒有跨語言需求的話，完全沒差。
- **風險／前提**：純需求問題，不是技術問題。**先確認實際上有沒有人要用**，不要因為對標產品有就做。
- **建議**：**延後**，等有具體使用者提出來再做。屆時 2–3 天就能上。

### D05　唯讀開放 REST API

- **是什麼**：對外開放讀取會議清單、逐字稿、摘要、用量的 API，以 API Key 授權。
- **為什麼值得做**：它是 D06（MCP）的地基，也讓其他系統能撈會議資料。目前的 Web API 只開放中繼資料 CRUD，逐字稿與摘要讀不到。
- **不做會怎樣**：資料被鎖在 UI 裡。MCP 做不了，也無法跟其他內部系統串。
- **風險／前提**：要設計 API Key 的儲存（雜湊）、scope 與限流；跨工作區隔離必須確實，這是資料外洩的主要風險面。
- **建議**：**要做**，與 D06 視為同一批工作。

### D06　MCP Server（唯讀）

- **是什麼**：提供 `list_meetings`／`get_transcript`／`get_summary`／`search_meetings`／`get_usage` 五個唯讀工具，讓 Claude Code、Cursor 等 AI 工具直接查詢會議庫。
- **為什麼值得做**：這是報告裡投報率最高的發現——**用 3–5 天換到「AI 知識庫」能力，而不必自建 RAG 聊天介面**。使用者拿自己已經在用的 AI 工具來問。對標產品就是這樣做的。
- **不做會怎樣**：想做「問我的會議庫」就得自建對話 UI + 向量檢索，成本至少高一個數量級。
- **風險／前提**：**寫入操作一律不開放**，這條要寫進設計文件而非口頭約定。API Key 不得寫進日誌。
- **建議**：**要做**，緊接在 D05 之後。

### D07　摘要模板區塊化

- **是什麼**：把摘要模板從「一段固定提示詞」改成「可增刪、可拖拉排序、可一鍵開關的區塊清單」，執行時依啟用狀態組裝提示詞。
- **為什麼值得做**：這是對標產品摘要功能的真正形狀（20 種內建模板 + 區塊操作）。做成資料驅動之後，新增模板不必改程式。
- **不做會怎樣**：每種會議類型的摘要格式都要開發者改提示詞，使用者自己動不了。
- **風險／前提**：可以分兩階段——**階段一**沿用現有的單一提示詞範本讓 D01 先上線；**階段二**再改成區塊結構。不要為了等 D07 而卡住 D01。
- **建議**：**要做，但排在 D01 之後**，且明確分兩階段。

### D08　術語表與校正

- **是什麼**：維護專有名詞／公司內部用語／專案代號清單（含同義詞），在逐字稿與摘要中自動套用。
- **為什麼值得做**：專有名詞辨識錯誤是逐字稿最惱人的問題，而且是**使用者最有感的品質提升**。
- **不做會怎樣**：公司名、產品名、人名持續被轉成同音錯字，每份逐字稿都要手動改。
- **風險／前提**：三種注入時機成本差很多——STT 熱詞參數（效果最好，但要供應商支援且有數量上限）、逐字稿後處理取代（便宜可控，但同音異義會誤傷）、摘要提示詞夾帶（最便宜，只修摘要）。
- **建議**：**要做，先做後處理取代版（2–3 天）**，之後再視 STT 供應商能力補熱詞注入。

### D09　引用時間碼／可追溯性

- **是什麼**：摘要裡的每個決議與待辦附上來源時間碼，UI 可點擊跳回逐字稿對應位置。
- **為什麼值得做**：這是**幻覺控管的主要手段**，也是產品差異化。使用者能一秒驗證「AI 說的這句是不是真的有人講過」。
- **不做會怎樣**：使用者無法驗證摘要，要嘛盲信、要嘛整份重讀——後者等於摘要沒用。
- **風險／前提**：依賴 D02 的段落表。要在提示詞裡要求模型輸出來源標記，並處理模型標錯的情況。
- **建議**：**要做**，緊接在 D01 + D02 之後。

### D10　AI 品質評估機制

- **是什麼**：建立 20–50 段標註語料量測 STT 的 WER；建立摘要人工抽檢評分表（完整性、正確性、可執行性）。
- **為什麼值得做**：**沒有量測就無法換模型。** 供應商改價、下架模型、或出了更便宜的選項時，你只能靠感覺判斷「好像變差了」。這是本清單裡最容易被跳過、也最貴的一項技術債。
- **不做會怎樣**：被鎖死在現有供應商，或每次換模型都是賭博。也無法回答「這次調提示詞到底有沒有變好」。
- **風險／前提**：建語料需要人工標註，這是主要成本。可以從很小開始——20 段真實會議就足以偵測明顯退化。
- **建議**：**要做小規模版本**，在 D01 上線的同時建立，不要等到「有空再說」。

### D13　瀏覽器分頁錄音

- **是什麼**：`getDisplayMedia` + `getUserMedia` 在瀏覽器內直接錄會議音訊，免上傳檔案。
- **為什麼值得做**：省掉「開會 → 找錄音檔 → 上傳」這段摩擦，是使用體驗的明顯躍升。
- **不做會怎樣**：使用者得自己想辦法產生錄音檔再上傳。對重度使用者是每次都要做的苦工。
- **風險／前提**：瀏覽器相容性、分頁音訊與麥克風混音、長時間錄製的串流上傳與斷線續傳，都比看起來麻煩。8–15 天的區間反映的就是這些坑。
- **建議**：**延後**。等 D01 上線、確認摘要品質站得住之後再談擷取體驗。品質不夠好的時候，降低上傳摩擦沒有意義。

### D14　行動 App（iOS／Android）

- **是什麼**：原生 App 錄音，與桌機同步。
- **為什麼值得做**：客戶訪談、外出開會等沒有電腦的場景。

- **建議**：**不做。** 若真有行動需求，先做手機瀏覽器可用的網頁錄音（D13 的延伸），成本差一個數量級。

### D15　會議機器人 + 行事曆整合

- **是什麼**：讀行事曆，派無頭瀏覽器機器人自動加入 Google Meet／Teams／Zoom 錄製，會後推送逐字稿與摘要。
- **為什麼值得做**：這是對標產品最有魔力的功能——完全不用動手。
- **不做會怎樣**：線上會議仍需手動錄製或上傳。
- **風險／前提**：**這是獨立子專案等級的工作。** 無頭瀏覽器叢集要維運；各會議平台的入會流程與反自動化機制會變（對標產品自己就要求 Google Meet 開啟「任何擁有連結的人都可申請加入」）；機器人 20 分鐘沒被接受就得自己離開。平台一改版就可能全掛。
- **建議**：**不做。** 如果哪天真的需要，優先評估外購現成的 meeting bot API 而非自建。

### D16　即時字幕（串流 STT）

- **是什麼**：會議進行中即時顯示字幕與翻譯。
- **為什麼值得做**：對標產品把它放在付費門檻上，顯然使用者買單。
- **不做會怎樣**：只能會後才看到內容。
- **風險／前提**：**架構影響最大的一項。** 需要串流 STT（與現在的批次 API 是不同產品）、WebSocket 通道、背壓處理，成本與延遲都是新戰場。對標產品把它擋在付費牆後正是因為成本高。
- **建議**：**不做。** 它應該是整條路線圖的最後一站，不是候選項目。

| 決定 | 決定日期 | 理由 |
| --- | --- | --- |
| 待決 | | |

### D17　佇列外部化／水平擴充

- **是什麼**：把行程內 `Channel<int>` + 單一 worker 換成 DB queue 或訊息中介，讓多個 worker 並行。
- **為什麼值得做**：目前單機單 worker，同時上傳多場長會議會排隊；重啟會遺失佇列中的工作。
- **不做會怎樣**：併發量上不去。使用者少的時候完全不是問題。
- **風險／前提**：**先量測再決定。** 現在的瓶頸可能根本不在這裡——STT API 本身也有速率限制。沒有實測數據就改架構是最典型的過早最佳化。
- **建議**：**延後**，等 D11 的用量資料顯示排隊真的在發生。

| 決定 | 決定日期 | 理由 |
| --- | --- | --- |
| 待決 | | |

### D18　分享連結

- **是什麼**：產生有期限的連結，讓非系統使用者也能看某一場會議紀錄。
- **為什麼值得做**：會議紀錄的自然用途就是給別人看。目前只能靠既有的 RBAC + 團隊權控，外部人士看不到。
- **不做會怎樣**：分享只能靠複製貼上或匯出檔案。
- **風險／前提**：便宜（2–3 天），但**連結外洩就是資料外洩**。要有期限、可撤銷、可稽核。
- **建議**：**延後**，等 D01 產出的摘要品質確認可以見人之後再開放對外分享。

| --- | --- | --- |
| 待決 | | |

### D19　SSO／Passkey 擴充

- **是什麼**：在既有的 Google OAuth 之外，補 Microsoft／Apple 登入、Passkey、企業 SAML SSO。
- **為什麼值得做**：對標產品六種登入方式並列，企業版靠 SAML SSO 拉開層級。
- **不做會怎樣**：現有的 Cookie + Google OAuth 對內部系統已經夠用。
- **風險／前提**：純粹看使用族群。內部系統做 SAML 是浪費。
- **建議**：**延後**，等有明確的企業客戶需求再說。

| --- | --- | --- |

### D20　成本閘門（進佇列前估算）

- **是什麼**：工作進佇列前先算預估成本（時長 × 單價），超過門檻就擋下或要求確認。
- **為什麼值得做**：1–2 天，防的是「有人不小心傳了一個 8 小時的檔案，跑到一半才失敗，錢已經花掉」。也避免做到一半才發現額度不夠。
- **不做會怎樣**：成本失控只能事後從帳單發現。
- **風險／前提**：需要 D11 的單價設定。門檻值要可調，不然會擋到正常的長會議。
- **建議**：**要做**，與 D11 同批，投入極小。

### D21　`Microsoft.OpenApi` 弱點處理

- **是什麼**：`Microsoft.OpenApi` 2.4.1 有 NU1903 高嚴重性弱點警告（[GHSA-v5pm-xwqc-g5wc](https://github.com/advisories/GHSA-v5pm-xwqc-g5wc)）。升版或依既有慣例加抑制並記錄理由。
- **為什麼值得做**：CI 有弱點掃描，遲早會擋。專案先前處理 SQLite CVE-2025-6965 已有現成做法可循（見 [changelog](../changelog/2026-06-22-抑制SQLite-CVE-2025-6965.md)）。
- **不做會怎樣**：建置警告持續累積，真正重要的警告被淹沒。
- **風險／前提**：升版可能牽動 Swagger 相依。若無安全版本可用，就走抑制 + 文件記錄。
- **建議**：**要做**，0.5–1 天，與其他工作無關可獨立進行。

## 四、如果只做三件事

如果資源只夠做三件事，做這三件：

1. **D01 摘要生成** —— 讓兩個版本的投資變現。
2. **D02 逐字稿段落表** —— 現在 3–5 天，以後是重寫。
3. **D11 用量帳本 + D20 成本閘門** —— 合計 3–5 天，防的是唯一會讓專案被叫停的事：帳單失控。

加起來約 11–18 天，系統就從「能轉錄」變成「能用、能量測、不會爆預算」。

## 五、決策相依

有些決定會鎖死其他決定的選項，照這個順序決定比較省事：

```
先決定：
  W18 資料保留政策 ──► 影響 D02 的資料表設計（軟刪／實刪、保留期欄位）
  D03 的前置調查（STT 供應商是否支援 diarization）
        └─► 影響 D03 的工作量，也可能反過來影響 STT 供應商選擇
  D12 商業化與否 ──► 決定 D12、D19、W06 整組要不要做

再決定：
  D02 段落表 ──► 是 D03 / D04 / D09 的共同前提
  D01 摘要生成 ──► 是 D05 / D07 / D08 / D09 / D10 的前提
  D11 用量帳本 ──► 是 D20 / D12 / D17 判斷依據的前提

最後決定（都需要前面的實測數據）：
  D17 佇列外部化（等 D11 顯示排隊真的發生）
  D13 / D16 擷取與即時（等 D01 品質站得住）
```

**兩個「現在就該花半天查清楚」的問題**（不是決策，是調查）：

1. 目前的 Azure OpenAI 轉錄模型**是否原生支援語者分離與熱詞參數**？答案直接決定 D03 與 D08 的做法與工作量。
2. 拿**一場真實的 60 分鐘會議**實測一次端到端成本（STT + 摘要）。報告第十二節的公式只能給量級，真實數字才能拿來訂 D20 的門檻，也才知道 D12 有沒有必要。
