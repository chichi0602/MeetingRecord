## 一、目標與範圍

提供「待辦事項（Todo）」的建立、查詢、修改、刪除與完成狀態管理。待辦一定隸屬於一個專案項目，並可回溯到產生它的來源會議紀錄。

- 範圍：清單查詢（關鍵字搜尋、專案／狀態過濾、排序、分頁）、單筆維護（含表單驗證）、清單上直接勾選完成、右側各負責人工作量面板、動作級授權。**0.4.66 起沒有列級可見範圍控管**（分類與團隊欄位已徹底移除）。
- 非範圍：看板版面與拖拉排序、子任務與相依關係、工時統計、提醒通知。
- **AI 從會議紀錄抽出待辦已於 0.4.61 實作**（入口在專案項目頁的「歷史會議紀錄」，不在本頁）。抽出來的候選一律經確認視窗由人勾選與修改才寫入，`MeetingId` 填來源會議，清單的「來源」欄因此會顯示會議標題而不是「— 手動新增」。規則見 [專案項目 PRD](專案項目-prd.md)。

## 三、畫面與欄位

- 工具列（**0.4.67 改為一列排完；0.4.75 左右對調**）：左側新增、重新整理；右側專案過濾（150px）、狀態過濾（110px）、關鍵字輸入（160px）、搜尋、清空搜尋（僅在有關鍵字時出現）。欄寬刻意壓窄，讓整列在雙欄版面下仍塞得進一行。Icon 一律 Material Icons Outlined。（分類過濾與團隊過濾已於 0.4.66 移除）

  0.4.75 之前本頁是**全站唯一**把新增／重新整理擺在右邊的清單頁，與使用者、角色、分類、會議紀錄、提示詞範本、團隊六頁相反，已對調過來。⚠️ **「搜尋」與「清空搜尋」的前後順序刻意保持與其他頁不同**：清空鈕是條件顯示的，排在搜尋之前會讓「搜尋」在使用者打字時往右跳一格。見 [待辦工具列左右對齊](../changelog/2026-09-16-待辦工具列左右對齊.md)。
- 清單欄位：完成勾選、待辦事項（**單行省略，旁邊有資訊 icon 開唯讀對話框看完整描述**）、所屬專案、來源會議紀錄、負責人、截止日、優先度、狀態、操作。表格設 `ScrollX="1020px"`，窄容器下橫向捲動而不是把欄位擠爛（全站唯一一頁這樣設，因為右側多了面板）。（分類與團隊兩欄已於 0.4.66 移除）
- **每頁筆數跟著畫面高度走（0.4.86 起，0.4.87 改成回授式）**，不是固定值。
  JS 量「表格區塊（含分頁器）底部離畫面底還剩多少」，夠塞一列就補、超出就縮，每調整一次再量一次，
  直到剩餘空間連最矮的一列都放不下（決策在 `TodoAutoFit.Decide`，不在 JS 裡——本專案沒有 bUnit）。
  量不到時退回 6 筆。實測 1555×805 → 6 列、1555×900 → 8 列、1840×1000 → 10 列、2210×1100 → 11 列，
  **各尺寸排不掉的餘量一律小於一列**。
  ⚠️ 0.4.86 曾經用「可用高度 ÷ 列高」**預測**，實測表格底永遠離畫面底 76～177px（等於白白少排一到兩列），
  0.4.87 換成回授才解決。⚠️ 使用者自己在分頁器上改過每頁筆數之後就**停止自動調整**，
  否則他選了 20 筆會立刻被蓋回去。詳見 [列數自動吃滿畫面](../changelog/2026-09-18-待辦列數自動吃滿畫面.md)。
  ⚠️ **0.4.85 之前這一頁的分頁器只有總數與頁數是對的，內容從來沒被切過**：
  `TodoService.GetAsync` 的 `Take` 被包在 `if (dataRequest.Take != 0)` 裡，而呼叫端一律傳 0，
  所以第 1 頁會列出全部資料。`Count` 是在 `Skip`／`Take` 之前算的，分頁器因此看起來一直很正常。
  0.4.85 同時補上**頁碼夾住**（末頁刪到空會退回前一頁，而不是留下空白表格）與
  `OnTableChange` 的 `_pageSize` 賦值。詳見 [開發慣例與限制速查 §6.2](../architecture/開發慣例與限制速查.md)。
- **整頁不捲（0.4.86）**：雙欄版面下表格與右邊面板各自被畫面高度約束，內容再多也是各自區塊內捲。
  ⚠️ **單欄（< 1400px）例外**——面板是疊在表格下面的，兩塊都要塞進一個畫面在這個寬度下辦不到，
  面板退回 0.4.66 的固定 420px 上限，整頁仍要捲一段才看得到它。
- 逾期的截止日以紅色粗體顯示並附「逾期 N 天」；已完成的標題加刪除線。
- 沒有任何可存取的專案時，清單上方顯示提示並停用「新增」——待辦必須隸屬專案。
- 預設排序：有截止日的優先、越早到期越前面，未指定截止日者墊底。
- 編輯表單欄位：待辦標題（必填）、描述、所屬專案（必填）、來源會議紀錄（唯讀，僅在有值時顯示）、負責人、截止日、優先度（必填）、狀態（必填）。（分類與團隊已於 0.4.66 移除）


### 右側各負責人工作量面板（0.4.66，0.4.67 加收合）

版面改為雙欄：左邊是原本的工具列與清單，右邊是固定 320px 的面板（`@media (max-width: 1400px)` 降為單欄）。**斷點刻意用 1400px 而不是 1200px**：側邊欄收合是 `.page` 上的 runtime class（`--sidebar-width` 300→64px），媒體查詢量的是視窗寬、看不到這 236px 的差，所以同一視窗寬度下無法區分展開與收合。取保守值並配合表格的 `ScrollX`，誤判成單欄也只是要橫向捲動。

面板標題列右邊有**收合鈕**（0.4.67）。收合後外層 grid 退回單欄、表格拿回整個寬度，面板縮成一條只有標題與一行摘要（「範圍 · N 位負責人」）的橫條，並用 CSS 的 `order: -1` **移到表格上方**——單欄之下它原本會落在表格後面，長表格會把展開鈕推到要捲很久才看得到的地方。收合狀態刻意不持久化：這是檢視偏好，重新整理回到展開是可預期的。

面板內容：負責人下拉（選項後面帶該人的待辦筆數）→ 完成度進度條（`已完成 N / 共 N`）→ 三個狀態的筆數膠囊（逾期 > 0 時多一個紅色膠囊，**0.4.85 起四顆都可點來篩下面的小清單**）→ 該人的待辦清單（標題單行省略、狀態膠囊、截止日，逾期紅字）。

服務層是兩支方法：`TodoService.GetOwnerSummariesAsync(projectFilter)` 只投影 `Owner`／`Status`／`DueDate` 三個純量欄位算統計，**不撈實體也不映射 AdapterModel**；選中某人之後才用 `GetByOwnerAsync(owner, projectFilter)` 撈他那一份。合成一支會為了顯示一個人而把全表撈出來映射一遍，比左邊的清單本身更貴。

| 議題 | 結論 |
| --- | --- |
| 完成度怎麼算 | **已完成筆數 ÷ 總筆數**，整數截斷。系統沒有「完成度」欄位（`Status` 是唯一的完成依據，見上表），所以只能這樣算。**刻意不四捨五入**：199/200 四捨五入會顯示 100%，看起來像全做完了，是假資訊 |
| 面板跟哪些過濾連動 | **只跟專案過濾**，不跟狀態過濾、關鍵字、排序與分頁。面板顯示的就是狀態分布與完成度，套上「狀態＝已完成」會讓每個人都 100%、套「待辦」都 0%——那不是空資料，是**看起來合理的錯誤數字**。關鍵字也不行：`GetAsync` 的搜尋會比對 `Owner` 欄位本身，搜一個人名會讓那個人的完成度變成 100%。這也延用了本頁既有的分界——`OnAddAsync` 新增時預設帶入專案過濾，但完全不管狀態過濾。面板標題旁會顯示目前範圍（專案名或「全部專案」），免得使用者以為數字沒跟著過濾器動是 bug。⚠️ 0.4.85 加的膠囊篩選**不牴觸這一格**：它篩的是膠囊底下那份小清單，**膠囊自己的數字與完成度進度條一律維持未篩選** |
| 人名從哪裡來 | **現有待辦的 `Owner` distinct 值**，不是使用者帳號清單。`Owner` 是自由文字（`string?`，50 字），與 `MyUser` 沒有任何關聯，用帳號清單會得到「每個人都 0 筆、真正有待辦的人不在清單上」 |
| 分組鍵怎麼正規化 | **一律 `Trim()` 後在記憶體分組**。交給 SQLite 的 `GROUP BY x.Owner` 會把「陳大文」與「陳大文 」算成兩個人，`null` 與空字串也會變成兩組。空白或 null 一律歸到 `TodoService.UnassignedOwner`（「未指定」），與清單「負責人」欄的顯示文字一致 |
| 面板什麼時候重載 | 掛在 `ReloadAsync()` 尾端，與清單**同進同出**。所有變更資料的路徑（勾選完成、刪除、Modal 送出）都只呼叫 `ReloadAsync`，掛在這裡才不會出現「勾了完成、左邊變了、右邊完成度不動」 |
| 切換專案後選中的人不見了 | **自動退回第一位**，不留空面板。人名下拉的選項也跟著專案過濾縮，否則會選到在該專案 0 筆的人 |

### 狀態膠囊可點篩選（0.4.85）

面板裡的四顆狀態膠囊（待辦／進行中／已完成／逾期）從純顯示改成可點的 `<button>`，
點下去把**下面的小清單**篩成「這個人 ＋ 這個狀態」。左邊的主清單、膠囊自己的數字與完成度進度條都不動。

實作是純記憶體的檢視層篩選（`Components/Views/Todos/TodoOwnerFilter.cs`），**服務層完全不動**：
`GetByOwnerAsync` 本來就刻意不分頁（單人量級小），所以在記憶體篩的成本可忽略。

| 議題 | 結論 |
| --- | --- |
| 篩選狀態用什麼型別 | **`enum OwnerTodoFilter`，不是 `string?`**。「逾期」不是 `Status` 的值，它是 `DueDate` 加上「未完成」算出來的衍生條件。用字串就得塞一個不在 `StatusOptions` 裡的魔術字串，而 `todo.Status == filter` 會**安靜地**永遠不成立——沒有例外、沒有紅字，只有一個永遠空的清單 |
| 可不可以多選 | **互斥單選，再點一次回到全部**。理由是資料決定的：逾期 ⊂（待辦 ∪ 進行中），而**逾期 ∩ 已完成恆為空**，多選一定會產生「已完成 ＋ 逾期」這種永遠空清單的組合。單選也才保得住唯一的賣點：**膠囊上的數字 = 點下去看到的筆數** |
| 0 筆的膠囊 | **渲染回 `<span>` 而不是 `<button disabled>`**，與 [§6.1 第三類](../architecture/開發慣例與限制速查.md) 同一條理由（disabled 不可 focus，掛在上面的說明讀不到），另外也從源頭消滅「點了得到空清單」 |
| 篩了逾期，然後把最後一筆逾期的改成已完成 | 膠囊會消失而篩選還在 → 空清單且沒東西可點掉。用不變式守：**作用中的篩選，畫面上一定要有一顆可以點掉它的膠囊**。`TodoOwnerFilter.Clamp` 在 `ReloadOwnerPanelAsync` 與 `OnOwnerChangedAsync` 尾端各呼叫一次 |
| 換人／換專案要不要重設篩選 | **不重設，只 clamp**。典型用法是跨人巡同一個狀態（「還有誰有逾期」），每換一人就要重點一次等於把功能做廢一半；而「保留一個對新的人沒意義的篩選」已經被 clamp 吃掉。⚠️ 日後若要改成「換專案要重設」，那一行**只能**放在 `OnProjectFilterChanged`，**絕不能放進 `ReloadOwnerPanelAsync`**——後者在每次勾完成／刪除／新增之後都會跑，放那裡等於使用者每勾一個完成，篩選就被默默清掉 |
| 怎麼讓人看得出「現在有篩選」 | **兩層，缺一不可**：選中的膠囊加內框與粗體，**其餘膠囊 `opacity: .5`**（只有選中那顆變粗，四顆並排時看不出來）；小清單上方多一行條件式的篩選列帶「顯示全部」，與本頁既有的「清空搜尋」同一個慣例 |
| 篩過的清單存哪裡 | **computed property，不另存一份欄位**。`ownerTodos` 是資料來源、`ownerTodoFilter` 是檢視狀態，合成一份欄位之後每一條重載路徑（面板重載、換人、勾完成、刪除、Modal 送出）都要記得重套一次，**漏掉任何一條就會顯示上一次的篩選結果，而且畫面看起來很合理** |

可及性：膠囊帶 `aria-pressed`（這是 toggle 不是 action）。
⚠️ 必須給**字串** `"true"`／`"false"`——Blazor 對 `bool` 屬性的規則是
「true 只渲染屬性名、false 整個略掉」，給 bool 會渲染成空值而無效。
**這裡刻意不加二次確認**（只改檢視狀態、可逆、不碰資料庫），
§6.1 第三類原本的「一定要有二次確認」已於 0.4.85 限縮成「會寫入資料的膠囊」。

### 待辦內容的檢視（0.4.66）

清單的「待辦事項」欄改為**只顯示標題的單行省略**（`title` 屬性帶完整標題），描述副標移除。描述非空時右邊多一顆資訊 icon（`CrudActionButton`，`Icon="info"`），點開唯讀對話框（`Footer="null"`）看完整描述。

兩個實作細節：對話框**放在元件根層而不是 `<Column>` 裡**（放欄位內會讓每一列都渲染一個視窗）；描述來自 `TextArea`、換行有意義，所以用 `<pre>` 搭配 `white-space: pre-wrap` 保留。另外 `text-overflow: ellipsis` 對純 inline `<span>` 無效，所以標題外面包了一層 flex 容器並讓文字成為 `min-width: 0` 的 flex item。
## 四、設計決策

| 議題 | 結論 |
|------|------|
| 完成狀態 | **只有 `Status` 一個欄位**（待辦／進行中／已完成）。清單上的勾選框是「把 Status 設為已完成」的快捷鍵，**不另存 `IsCompleted` 布林**——兩個欄位並存必然出現「勾了完成但狀態還是進行中」這種互相矛盾的資料 |
| 取消完成後的狀態 | 退回「進行中」而非「待辦」。已經動過的事情退回未開始並不合理 |
| 專案關聯 | `ProjectId` **必填**，`OnDelete(Cascade)`。沒有專案的待辦只會變成沒人管的垃圾資料 |
| 會議紀錄關聯 | `MeetingId` **可空**，`OnDelete(SetNull)`。會議紀錄被刪除時待辦保留，只是失去來源 |
| 團隊權控 | **0.4.66 起完全沒有**。`Categories`／`Teams` 兩欄已隨 migration `RemoveTodoCategoriesTeams` 從資料庫移除，所有待辦對所有使用者可見。與現況一致：待辦必定隸屬於專案，而專案自 0.4.39 起也已退出團隊控管；AI 抽出的待辦從來不填團隊，等於一直是公開的 |
| 專案完成度 | **不連動**。`Project.CompletionPercentage` 維持手動填寫——待辦數量與專案進度未必成正比，自動換算反而變成假資訊 |
| 來源會議紀錄的保護 | `MeetingId` 不開放從畫面或 API 覆寫，`TodoService.UpdateAsync` 與 `TodoRepository.UpdateAsync` 都一律沿用資料庫既有值 |
| 每頁筆數（0.4.86） | **量畫面算出來**，不是固定值（0.4.85 曾經寫死 5 筆）。一樣不動全站共用的 `MagicObjectHelper.PageSize`（8）——改它會一次動到六個沒被要求改的頁 |
| ⭐ 列高不是固定的（0.4.86／0.4.87） | 截止日欄會把「逾期 N 天」折到第二行（0.4.67 刻意的排版），實測 63.75px 對 81px。所以**不能靠估列高**：估保守就少排列（0.4.86 的症狀），估樂觀就撐出捲軸。0.4.87 改成看實際剩餘空間增減，並記下「已知放不下的列數」當上限，之後不再長回去 ⇒ 一定收斂 |
| ⚠️ 寬度變化的容差（0.4.86／0.4.87） | **24px，不能用 0**。收斂過程中整頁捲軸會短暫出現，容器寬度跟著差一個捲軸寬（約 15px），用 0 的話上限會被「自己造成的捲軸」清掉而開始來回跳。24px 又遠小於側邊欄收合的 236px，真的換版面時仍會重來 |
| ⚠️ 調整完要再量一次（0.4.87） | JS 端的 `ResizeObserver` 只看寬度，而改列數只會改高度。少了 C# 主動呼叫的 `remeasure`，列數就只會被調整一次，永遠停在第一次估的值 |
| 膠囊篩選要不要進服務層（0.4.85） | **不要。** 把狀態帶進 `GetOwnerSummariesAsync` 會讓完成度變成「每個人都 100%」或「都 0%」——**不是空資料，是看起來合理的錯誤數字**。程式與本文件兩邊都留了註解擋住 |
| 膠囊數字與清單筆數的一致性（0.4.85） | 兩者是**兩份各自獨立的實作**（數字在查詢端數、清單用 `TodoAdapterModel.IsOverdue` 在記憶體篩），所以由 `TodoServiceTests` 的一條跨來源測試釘住。對不上只會讓人覺得數字有問題，不會丟例外 |

## 五、內部系統運作

- 資料流：`TodoPage.razor` → `TodoViewView` → `TodoService` → `BackendDBContext.Todo`。REST API 走 `TodoController` → `TodoRepository`（兩條路徑並存，皆回 `ApiResult`）。
- 讀取：清單與單筆都 `Include(Project)` 與 `Include(Meeting)` 以取得關聯名稱；`ProjectTitle`／`MeetingTitle` 由 AutoMapper 的 `ForMember` 自導覽屬性帶出。
- 0.4.66 起 `TodoService` 不再注入 `IRecordAccessScopeProvider`——四處列級權控（清單、單筆、勾選完成、修改前置檢查）與 `DashboardService.BuildTodoQuery` 的團隊過濾全部移除。
- 前置檢查：新增與修改都會驗證所屬專案存在（0.4.66 起不再檢查團隊可見範圍）。
- 寫入前後皆 `CleanTrackingHelper.Clean<Todo>(context)`。
- API 新增後會重新載入實體才回傳，否則回應的 `ProjectTitle`／`MeetingTitle` 會是空的。
