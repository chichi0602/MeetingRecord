- 文件版本：1.0

## 目的

本文件針對本腳手架（NET10-Blazor-Starter，定位為**純 SI 通用底座**）的權限控制與授權設計，做一次完整體檢：列出現況、問題與限制、判斷是否符合多數客戶需要，並提出分階段的改善路線與預期效益。作為後續重構的決策依據與追蹤基準。

> 相關文件：[認證授權與權限機制](認證授權與權限機制.md)、[密碼種類與儲存機制](密碼種類與儲存機制.md)、[開發慣例與限制速查](../architecture/開發慣例與限制速查.md)、[資料模型與資料庫](../architecture/資料模型與資料庫.md)。

## 一、現況綜整（以程式碼為依據）

> **現況更新（2026/07/09，重構已落地）**：本節與 §二、§三為**重構前**現況，用以對照改善成效；最新狀態見第八節。已解決：密碼改 PBKDF2（原 SHA256，#6）、帳號鎖定 + 稽核表 `AuditLog`（#8/#7）、多角色 `UserRole` 權限聯集（原一人一角色，#5）、CRUD 動作級分權 `view/create/edit/delete/export`（#3）、選單改宣告式 `id→權限鍵`（原位置索引三處同步，#2）、API 強制動作級授權回 403（原無功能級授權，#1）、團隊直綁使用者 `UserTeam` 且有效團隊為 `UserTeam ∪ 角色 DefaultTeamsJson`（原團隊綁角色）、UI 與 API 共用 `IPermissionChecker` 單一權威來源。**仍暫緩**：Refresh Token 落庫撤銷（#9）。MFA 為 TOTP 骨架（預設關閉，屬 #8）。

### 身分驗證（Authentication）
- UI 用 Cookie 驗證、API 用 JWT Bearer；可選 Google OAuth2 單一登入。
- 密碼儲存：**SHA256 + Salt**（`src/MeetingRecord/MeetingRecord.Business/Helpers/PasswordHelper.cs`）——屬快雜湊，非 bcrypt/PBKDF2/Argon2。
- **無 MFA、無帳號鎖定**（僅登入頁驗證碼防暴力）。
- Refresh Token 為 **stateless JWT，不落庫、無法撤銷**（`src/MeetingRecord/MeetingRecord.Web/Auth/JwtTokenService.cs`）。
- **無資料庫稽核表**，僅 NLog 檔案日誌；權限變更無 who/what 歷史留痕。

### 授權模型（Authorization）
- 角色 `RoleView` 以 `TabViewJson`（JSON 字串）儲存頁面權限；`DefaultTeamsJson` 儲存團隊。
- **一使用者只能綁一個角色**（`MyUser.RoleViewId` → `RoleView`）。
- 權限粒度僅**頁面/功能級**，**無 CRUD（檢視/新增/編輯/刪除）分權**。
- 權限名稱為 **C# 常數硬編碼**（`src/MeetingRecord/MeetingRecord.Share/Helpers/MagicObjectHelper.cs`）。
- 「三處同步」以**位置索引**對齊，缺一不可、順序不可錯：
  - `src/MeetingRecord/MeetingRecord.Web/Datas/Menu.json`
  - `RolePermissionService.GetRoleListPermissionAllName()`
  - `MagicObjectHelper` 權限常數
  - 對應邏輯在 `SidebarMenuService.ApplyPermissionStructure()`（以陣列索引配對）。
- 列級權控（team scoping）：`TagStringHelper` 以團隊標籤字串 + LIKE 過濾，作用於 **Blazor 服務層**（`ProjectService` 的 `GetAsync`），透過 `IRecordAccessScopeProvider` 取得範圍。
- **API 層只驗 JWT 有效性，不做功能級授權**——任何登入者可呼叫任意 CRUD API。
- 使用者團隊來自**角色的 `DefaultTeamsJson`**（非使用者本身）；同角色者資料範圍必然相同。
- 未使用 ASP.NET Core Authorization Policy / Handler；`MyUser.IsAdmin` 直接繞過一切檢查。

## 二、問題與限制（依嚴重度）

| # | 問題 | 影響 | 類別 |
|---|------|------|------|
| 1 | **API 層無功能級授權**，只驗 JWT 有效 | 任何登入者可打任意 CRUD API，UI 的權限形同虛設 | 安全（高） |
| 2 | **位置索引三處同步** | 順序錯位會**靜默改壞授權**；新增頁面易錯、難維護 | 可維護性（高） |
| 3 | **無 CRUD/動作分權** | 無法「可看不可改」「可看不可匯出」，多數客戶基本需求缺失 | 功能（高） |
| 4 | **權限硬編碼於 C# 常數** | 換客戶要改 code、重編、重部署，違背通用底座定位 | 可適應性（高） |
| 5 | **一人一角色 + 團隊綁角色** | 個別使用者無法差異化授權；同角色必同資料範圍 | 彈性（中高） |
| 6 | **SHA256 快雜湊** | 易遭暴力/彩虹表攻擊 | 安全（中高） |
| 7 | **無稽核表** | 合規落差；權限變更無留痕 | 合規（中） |
| 8 | **無帳號鎖定、無 MFA** | 暴力破解與帳號接管風險 | 安全（中） |
| 9 | **Refresh Token 不可撤銷** | 登出後 token 仍可在有效期內換發 | 安全（中） |

> **狀態（2026/07/09）**：#1、#2、#3、#5、#6、#7、#8 已於階段一～四解決（見第八節與 §一 現況更新）；#4（權限鍵仍以宣告式定義於程式）為刻意設計、角色↔權限與使用者↔角色/團隊已資料驅動，非缺陷；**僅 #9（Refresh Token 撤銷）仍暫緩**。

## 三、是否符合多數客戶需要？

以**純 SI 通用底座**（同一套 code、靠設定/資料快速套用到不同客戶）為衡量基準：**目前偏不足**。

- 多數企業客戶必備的 **CRUD 分權**與 **API 端一致授權**缺失（#1、#3）。
- 底座的核心價值「換客戶零改 code」被 **#2、#4、#5** 破壞——每接新客戶幾乎都要動核心程式碼。
- 合規導向客戶（金融/醫療/政府）需要的**稽核**與**強密碼/鎖定/MFA**尚未到位（#6~#8）。

結論：現況足以支撐**單一、簡單、頁面級權限**的小案；一旦客戶需要**動作級分權、個別使用者授權、稽核合規，或以同一底座快速換案**，就會撞牆。

> **現況更新（2026/07/09）**：本節結論係基於 #1~#8 的重構前缺口，**均已於階段一～四解決**（僅 #9 Refresh Token 撤銷暫緩）。底座現已具備：動作級分權（可看不可改）、UI 與 API 一致授權、多角色與團隊直綁的個別使用者差異化授權、稽核 + 強密碼（PBKDF2）+ 帳號鎖定基線。合規導向需求僅 MFA 強制（TOTP 骨架已備、預設關閉）與 Refresh Token 撤銷待補。

## 四、改善方向：路線 A（分階段全面重構）

將底座升級為**資料驅動 RBAC + CRUD 粒度 + UI/API 共用授權 + 後台可管理**。

### 已鎖定的設計決策
- **粒度**：兩層 = 頁面可見 + 動作彈性（預設 CRUD，可依頁面加自訂動作如 export/approve）。
- **指派**：多角色（權限取聯集）+ 團隊**直接綁使用者**。
- **資料驅動分界**：權限鍵在程式碼以**宣告式**定義（屬性/註冊表）；**角色↔權限、使用者↔角色/團隊**全資料驅動、後台可管理。換客戶零改 code；新增功能仍需 code 但改為宣告式、安全不易錯。
- **安全基線**：密碼雜湊升級（含登入時自動遷移）、稽核軌跡表、帳號鎖定 +（選配）MFA。
- **經決定不納入實作範圍**（2026/07/09，刻意不做、非遺漏；日後有需求再另案評估）：Refresh Token 落庫撤銷、MFA 強制（TOTP 骨架已備、預設關閉）、SQL Server 遷移軌道 bootstrap（後者已於 0.4.24 隨 SQL Server 支援一併移除）。詳見 §七。

### 目標架構

**資料模型（新增/調整，需產生 SQLite migration）**
- `Permission`：權限鍵（如 `project`）、動作（如 `read/create/edit/delete/export`）、顯示名稱、群組；以宣告式來源為主，seed 進表。
- `Role`：角色主檔（傾向沿用並擴充現有 `RoleView`，降低衝擊；實作前定案）。
- `RolePermission`（多對多）：角色↔權限映射，取代 `TabViewJson`。
- `UserRole`（多對多）：使用者↔角色，取代 `MyUser.RoleViewId` 單一外鍵。
- `UserTeam`（多對多）：使用者↔團隊，取代 `RoleView.DefaultTeamsJson`。
- 保留 `Project.Teams` 標籤欄位（列級權控資料不變，只改「使用者團隊來源」）。

**統一授權（UI + API 共用一套）**
- 以 ASP.NET Core **policy-based authorization** + 自訂 `AuthorizationHandler` / `IAuthorizationPolicyProvider`，讀取使用者權限（claims 或 DB 查詢）。
- 頁面與 Controller 以**宣告式權限鍵**標註（屬性），取代位置索引。
- **API 端強制功能級授權**（關閉 #1）。
- 選單由權限**動態產生**（取代 `SidebarMenuService` 位置索引對應）。

**列級權控**
- `RecordAccessScopeProvider` 改由**使用者的團隊**（`UserTeam`）取得 scope；`TagStringHelper` 過濾邏輯不變。

## 六、改善後可解決客戶哪些問題 / 適應哪些需求

- **可看不可改／匯出／簽核**等細分權（解 #3）→ 滿足絕大多數企業客戶基本需求。
- **API 與 UI 一致授權**（解 #1）→ 對外開放 API 的客戶不再有越權風險。
- **換客戶零改 code**（解 #2、#4、#5）→ 交付週期縮短、維護成本下降，同一底座承接更多案。
- **個別使用者差異化授權**（解 #5）→ 同職稱不同資料範圍、跨團隊協作等常見場景可支援。
- **稽核 + 強密碼 + 鎖定 + MFA**（解 #6~#8）→ 具備打進金融/醫療/政府等合規導向客戶的門檻。

## 八、實作進度與階段四剩餘 UI 交接

### 已完成（後端全數含測試；UI 完成動態選單與 API 授權）
- 階段 0～3、階段四之一～之三：密碼 PBKDF2、帳號鎖定、稽核表、TOTP 骨架、RBAC 四表 + 回填、雙寫、**多角色權威來源**、**API 動作粒度授權（可看不可改）**、使用者有效團隊、**選單改宣告式 Id→權限鍵**。

### Razor UI（已實作、編譯通過、**執行期已實跑驗收 2026/07/09**）
- ✅ **角色×動作矩陣**：`RoleViewView` 每個權限節點提供「全部」+ view/create/edit/delete/export 勾選；`RolePermissionService` 產出/還原動作鍵。
- ✅ **使用者多角色 + 多團隊**：`MyUserView` 加「額外角色」「團隊」多選；`MyUserService.SyncAssignmentsAsync`/`GetUserAssignmentsAsync` 寫入/回填 `UserRole`/`UserTeam`（有單元測試）。
- ✅ **列表頁按鈕動作化**：Project/MyTask/Meeting 以 `CheckAccessAction` 控制新增/編輯/刪除鈕。

#### 實跑驗收結果（2026/07/09，SQLite/Development，瀏覽器實際點擊 + API curl）
- ✅ **矩陣存回/回填**：建唯讀角色「稽核員」（專案項目只勾「檢視」）→ 存檔後重開，精確回填為僅「檢視」勾選、其餘動作未勾；勾「全部」時 view/create/edit/delete/export 各動作 `Checkbox` 正確變 `Disabled`（互斥）。
- ✅ **多角色 + 多團隊**：使用者指派「主要角色 + 額外角色」與多個團隊 → 重開編輯正確回填，且額外角色清單正確排除主要角色（`GetUserAssignmentsAsync`）。
- ✅ **列表頁按鈕顯隱**：以純唯讀使用者登入，Project/MyTask/Meeting 三頁列表可見，但新增鈕與每列的修改/刪除鈕皆隱藏（管理員登入則全顯示）。
- ✅ **API 動作粒度授權（可看不可改，關鍵驗收）**：唯讀使用者 JWT 打 `/api/Project/search`（View）得 200；`POST /api/Project`（Create）、`PUT`（Edit）、`DELETE`（Delete）皆得 **403**，回應維持 `ApiResult<T>` 格式並精確標示如「目前使用者沒有『專案項目:create』權限。」。此 403（而非 200）反證矩陣確實產出 **動作鍵**（view-only）而非裸頁面鍵；MyTask/Meeting 同樣 create 403、search 200；無 JWT 得 401；管理員得以通過授權（改為 400 驗證層）。
