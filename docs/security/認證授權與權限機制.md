## 目的
本文件說明 MeetingRecord 目前同時支援 Blazor UI Cookie 登入與 Web API JWT Bearer 認證。UI 與 API 使用不同 authentication scheme，避免互相干擾。

## Cookie 認證
Blazor UI 既有登入流程維持 Cookie authentication：
- scheme 使用 `MagicObjectHelper.CookieScheme`。
- Login path 為 `/Auths/Login`。
- Logout path 為 `/Auths/Logout`。
- Access denied path 為 `/Auths/Login`。
- Cookie 名稱為 `MagicObjectHelper.AuthCookieName`（`.MeetingRecord.Auth`，0.4.119）。
- 效期來自 `appsettings.json` 的 `CookieSettings`（0.4.119）：沒勾記住我 `ExpireMinutes`（預設 480＝8 小時，且為 session cookie）、勾了記住我與 Google 登入 `RememberMeDays`（預設 30 天，登入時以 `ExpiresUtc` 明寫）、`SlidingExpiration`（預設 `true`，用掉超過一半效期時的那次 HTTP 請求才續）。

此機制主要服務 Razor/Blazor 頁面與既有後台使用者體驗。

### Data Protection 金鑰（0.4.119）
登入 Cookie 用 Data Protection 金鑰加密。金鑰存到 `SystemSettings:ExternalFileSystem:DataProtectionKeyPath`，應用程式名稱固定為 `MagicObjectHelper.DataProtectionApplicationName`（`ServiceCollectionExtensions.AddConfiguredDataProtection`；路徑空白啟動即失敗）。0.4.118 以前沒設定，IIS 集區回收或重啟就換金鑰，全站被登出。刪除金鑰目錄、改 ApplicationName 或 Cookie 名稱都會讓所有人被登出一次。金鑰檔為明文 XML，部署注意事項見「正式部署與安全檢查清單」。

### Google OAuth2 第三方登入
網頁登入除了帳號密碼外，亦可選用 Google 單一登入（SSO）。Google 驗證完成後同樣以 `MagicObjectHelper.CookieScheme` 完成登入，並串接既有權控（`RoleView`）。首次登入會自動建立停用中的帳號，待管理者啟用；需呼叫 API 者可另行設定 API 密碼。完整設定與流程請見「Google OAuth2 第三方登入」一文。

## UI 登入後檢查
Blazor 元件進入受保護頁面時，會透過 `AuthenticationStateHelper.Check(...)` 做 Cookie 認證後的二次檢查，並回傳 `AuthenticationCheckResult` 讓 Layout、NavMenu 或 Page 判斷是否繼續載入。

目前檢查項目：
- 未登入或 Cookie 無效時，導向 `/Auths/Login`，回傳 `Unauthenticated`。⚠️ 0.4.119 起刻意**不**導向登出頁：登出頁會無條件刪掉 Cookie，而「未認證」也涵蓋 Cookie 一時讀不出來（重啟、金鑰換掉），刪掉會毀掉原本還有效的記住我。真正失效的 Cookie 由 Cookie handler 自己清。
- `ClaimTypes.Sid` 缺失、格式錯誤或不是有效使用者 Id 時，導向 `/Auths/Logout`，回傳 `InvalidUser`。
- 使用者不存在、帳號停用、缺少 `RoleView` 或角色權限 JSON 無法初始化時，導向 `/Auths/Logout`，回傳 `InvalidUser`。
- 使用者仍使用需要強制更換的預設密碼時，導向 `/ChangePassword`，回傳 `RequiresPasswordChange`。
- 檢查成功時，會把使用者與角色權限寫入 `CurrentUserService.CurrentUser`，回傳 `Succeeded`。

`/ChangePassword` 是強制改密碼流程允許進入的例外頁面；使用者在該頁完成密碼更新後，才會回到一般系統頁面。

## JWT Bearer 認證
Web API 使用 JWT Bearer：
- JWT 設定來源為 `appsettings.json` 的 `JwtSettings`。
- `JwtSettings` 會綁定到強型別 `MeetingRecord.Web.Auth.JwtSettings`。
- Access token 用於 API 呼叫授權。
- Refresh token 採 signed JWT，不落庫。

`JwtSettings` 欄位：
- `Issuer`
- `Audience`
- `SigningKey`
- `AccessTokenMinutes`
- `RefreshTokenDays`
- `ClockSkewMinutes`

## Auth API
目前提供三個 API：
- `POST /api/Auth/login`：使用帳號密碼登入，成功回傳 access token 與 refresh token。
- `POST /api/Auth/refresh`：使用 refresh token 換發新 token。
- `GET /api/Auth/me`：使用 Bearer access token 取得目前使用者 DTO。

## API 授權規範
- Project/Category/Team/PromptTemplate CRUD API 預設全部需要 Bearer token。
- 登入與 refresh API 允許匿名。
- API 未授權與禁止存取回應也會包成 `ApiResult`。

### 功能級／動作級授權（關閉 API 越權缺口）
- 除 `[Authorize]`（驗證 token）外，CRUD 控制器**每個動作方法**以 `[HasPermission(頁面, 動作)]`（`MeetingRecord.Web/Filters/HasPermissionAttribute.cs`）強制授權；缺權限回傳 `ApiResult` 403。
- 動作對應：GET/`search`→`view`、POST→`create`、PUT→`edit`、DELETE→`delete`（動作常數見 `MeetingRecord.Share/Helpers/PermissionKeys.cs`）。頁面鍵取自 `MagicObjectHelper`（Project→`專案項目`、Category→`分類清單`、Team→`團隊清單`（0.4.101 曾改名 `資料群組`，0.4.102 起啟動時由 `RbacBackfillService.RenameLegacyPermissionKeysAsync` 就地改回）、PromptTemplate→`提示詞清單`、Meeting→`會議紀錄`）。
- **權限鍵兩型**：裸頁面鍵（如 `專案項目`）＝ 舊制＝該頁全部動作（向後相容）；動作鍵（如 `專案項目:edit`）＝ 特定動作。判定時「擁有動作鍵」或「擁有該頁裸鍵」即通過，故既有角色**零破壞**；「唯讀角色」只給 `專案項目:view`。
- 權限判定由 `IPermissionChecker`（`MeetingRecord.Business/Services/Other/PermissionChecker.cs`）負責：管理員一律通過，否則比對使用者的有效權限鍵。此舉修正先前「API 只驗 token、任何登入者可呼叫任意 CRUD」的越權問題。
- **權限來源已切換為 RBAC 關聯表**：`UserRole → RolePermissionMap → Permission`，多角色取聯集（容錯併入 legacy `RoleViewId`）。角色/使用者編輯時由 `IRbacWriteService` 雙寫保持即時一致。
- **UI 選單顯示與 `AuthenticationStateHelper.CheckAccessPage`／`CheckAccessAction` 已改用 RBAC 權威來源**：登入態初始化（`Check`）時以 `IPermissionChecker.GetEffectivePermissionKeysAsync(userId)` 一次載入有效權限鍵（含多角色聯集）覆寫 `CurrentUser.RoleList`，UI 判定維持同步比對記憶體集合。`CheckAccessPage` 亦補上管理員短路（`GetEffectivePermissionKeysAsync` 不含 admin 隱含全通過）。0.4.109 起 `CheckAccessPage` 認「整頁鍵或 頁面:view」，修正只勾部分動作的角色進不了頁面；分類清單、團隊清單的新增／修改／刪除與 AI 問答的改名、編輯、重新產生、刪除、清空也補上動作權限（測試：`AuthenticationStateHelperTests` 的四個預設角色案例、`ApiIntegrationTests.ProjectApi_ViewerPreset_CanRead_ButCannotCreateEditDelete`）。至此 UI 與 API 共用單一 RBAC 來源、多角色 UI 生效，`TabViewJson` 退居角色編輯畫面回填用的相容欄位。
- **0.4.26 新增頁面權限鍵「提示詞清單」**：宣告式註冊四處必須同步——`Menu.json` 的 `id=53`（掛在「資料定義」群組 `id=5` 之下）、`SidebarMenuService.MenuPermissionMap[53]`、`MagicObjectHelper.角色_提示詞清單`、`RolePermissionService.GetRoleListPermissionAllName()` 的「資料定義」群組。權限目錄（`Permission` 表）由 `RbacBackfillService` 於啟動時冪等回填，不需 SQL 或 migration。**既有自訂角色需由管理員到 `/roleviews` 重新勾選**此新權限；掛「預設角色」者重啟一次即生效。此註冊三件組另有 `MeetingRecord.Tests/PromptTemplateRegistrationTests.cs` 把關。
- **0.4.27 新增群組鍵「會議管理功能」與頁面權限鍵「會議紀錄」**：同樣四處同步——`Menu.json` 的 `id=6`（新群組）與 `id=61`（`url=/meetings`）、`SidebarMenuService.MenuPermissionMap[6]`／`[61]`、`MagicObjectHelper.角色_會議管理`／`角色_會議紀錄`、`RolePermissionService.GetRoleListPermissionAllName()` 的新「會議管理」群組。**影音檔上傳與「重新轉錄」歸在 `會議紀錄:edit`**，不另立動作類型。~~**⚠️ 0.4.82 起逐字稿完全沒有列級守門**~~：0.4.82～0.4.98 讀原文的唯一路徑 AI 問答沒有守門；**0.4.99 起 `AiChatService` 經 `ProjectAccessService` 守門**（見下節）。仍然**沒有任何檔案下載端點**。此註冊三件組由 `MeetingRecord.Tests/MeetingRegistrationTests.cs` 把關；`MenuIconTests.AllowedIcons` 亦須含新 icon `event`／`mic`，否則整套測試失敗。

### 資料可見範圍（主責＋協作團隊，0.4.102）
- **團隊＝誰的資料，分類＝什麼資料，角色＝能做什麼**，三者分開：角色（主要角色＋額外角色）經上述 RBAC 決定功能與動作；團隊（`Team`／`UserTeam`，就是部門，一人可屬多個）決定看得到哪些專案；分類只是描述標籤（`Project.Categories`／`Meeting.Categories`），**不影響可見性**。管理者（`IsAdmin`）不看角色與團隊。角色不帶任何資料範圍（`RoleView.DefaultTeamsJson` 已刪除）。
- 規則由 `ProjectAccessService` 單一權威判定，Blazor 服務層與 API 的 `ProjectRepository`／`MeetingRepository`／`TodoRepository` 共用：每個專案恰好一個主責團隊（`ProjectTeam.IsPrimary`）加 0～多個協作團隊，使用者所屬團隊與其中任一有交集才看得到，**沒有公開專案**；會議、待辦、附件、AI 問答跟著專案；未歸屬專案的會議只有上傳者（`Meeting.CreatedByUserId`）看得到。看不到的一律當成不存在（UI 找不到、API 404），不回 403 以免洩漏存在與否。
- 寫入規則（`ProjectAccess.ResolveProjectTeams`＋`ProjectTeamWriter`，UI 與 API 共用）：主責必填；非管理者的主責只能是自己所屬的團隊，但編輯時主責沒改就原樣保留；協作可選任何團隊。團隊仍是某專案的主責時不能刪（API 回 409）。
- **主責團隊管團隊設定與刪除**（1.0.47，`ProjectAccess.CanManageProject`＋`PrimaryProjectIds`）：修改既有專案時，只有主責團隊的成員（與管理者）能改主責／協作團隊，協作團隊的人改了會被擋（「只有主責團隊的成員可以變更團隊設定。」，API PUT 回 400）；刪除專案也只限主責團隊成員，且已完成（封存）的專案要先重新開啟（`ProjectService.DeleteAsync`，API DELETE 回 400）。協作團隊的人仍可改專案的其他內容。角色的 `專案項目:edit`／`delete` 照樣要有。
- **會議的上傳者專屬動作**（1.0.47，`ProjectAccess.IsMeetingOwner`）：同專案看得到的人都能看、改欄位、編修會議紀錄、重新產生、AI 問答；**刪除、從專案移除、換影音檔、重新轉錄只限上傳者與管理者**（`MeetingService` 服務層把關，訊息「只有上傳者或管理者可以…」）。上傳者為 null 的舊會議只有管理者。上傳者本人的角色只要有 `會議紀錄:edit` 就能刪自己上傳的，所以 API `DELETE /api/Meeting/{id}` 改要求 `會議紀錄:edit`；`主管` 角色從此不能刪別人上傳的會議。
- 例外：儀表板刻意不套（全公司彙總、不放明細；1.0.47 起「各專案會議數」把看不到的專案名稱併成「其他專案」，管理者看全部）；提示詞範本對所有人開放。
- 沿革：0.4.99～0.4.100 以專案成員（負責人／協作者）判定；0.4.101 改成「資料群組」（專案沒掛群組＝公開）；0.4.102 改回「團隊」並取消公開專案。舊成員與 0.4.101 的資料於啟動時由 `TeamConversionService`（原 `DataGroupConversionService`）轉換並補上主責團隊，沒有歸屬的掛「待分配」（只有管理者看得到）。細節見 [開發慣例與限制速查 §4.0](../architecture/開發慣例與限制速查.md) 與 [團隊清單 PRD](../prd/團隊清單-prd.md)。

## 帳號鎖定（防暴力破解）

`MyUserServiceLogin.LoginAsync` 內建連續失敗鎖定：

- 每次密碼錯誤累加 `MyUser.AccessFailedCount`；達 **5 次**即設定 `MyUser.LockoutEndUtc = UtcNow + 15 分鐘`，鎖定期間即使密碼正確也拒絕登入並回傳「帳號已鎖定，請稍後再試。」。
- 成功登入後 `AccessFailedCount` 歸零、`LockoutEndUtc` 清除；鎖定過期後自動恢復可登入。
- 門檻與鎖定時長目前為 `MyUserServiceLogin` 的常數（`MaxFailedAccessAttempts`、`LockoutMinutes`），未來可視需要外部化為設定。
- 相關欄位由 migration `AddAccountLockout` 建立（SQLite）。

## 稽核軌跡（AuditLog）

除 NLog 檔案日誌外，安全關鍵事件另寫入可查詢的資料表 `AuditLog`：

- 實體：`MeetingRecord.AccessDatas/Models/AuditLog.cs`（欄位：`OccurredAt`(UTC)、`ActorUserId`、`ActorAccount`、`Action`、`TargetType`、`TargetId`、`Detail`、`Success`；1.0.32 起加 `ClientIp`）。

- 1.0.33 擴充帳號安全事件：
  - **登入成功改由呼叫端寫**：網頁在 `SignInAsync` 之後、API 在發出權杖之後，摘要 `via=Web`／`via=Api`；失敗類仍由 `LoginAsync` 寫並帶 `via`。API 因必須先改密碼而拒絕時只記 `Login.Failed reason=MustChangePassword`。

  - Google 登入 `Login.GoogleSuccess`／`GoogleFailed`／`GooglePending`，連結既有帳號 `User.GoogleLink`、自動建立 `User.GoogleCreate`；API 權杖更新失敗 `Token.RefreshFailed`。
  - 密碼：`Password.Change`（目前密碼錯誤也記失敗）、`Password.ApiSet`、`Password.Reset`（管理者重設）；使用者啟停用 `User.Enable`／`Disable`；團隊成員 `User.TeamAdd`／`TeamRemove`。
  - **權限拒絕 `Permission.Denied`**：API 由 `HasPermissionAttribute` 在回 403 前寫（目標 `ApiEndpoint#{方法} {路徑}`，寫入失敗照樣回 403；401 不記）；UI 由各頁在拒絕分支呼叫 `AuthenticationStateHelper.RecordPageAccessDeniedAsync(route)`（目標 `Page#{路由}`）。JWT 政策型 403 目前不記。
  - 1.0.34 起資料範圍擋下的**寫入**（修改、刪除、上傳、產生草稿、歸屬專案、AI 問答操作等）也記 `Permission.Denied`，目標是專案／會議／待辦，摘要 `reason=DataScope; op=…`；對使用者仍當成不存在（回 404 或「找不到」），讀取被擋不記。
- 1.0.34 擴充業務資料事件：專案、會議、待辦、團隊、分類、提示詞、AI 問答的異動與流程動作，操作者由 `IAuditActorProvider` 決定（API 請求從 claims 取）。詳見 [稽核紀錄 PRD](../prd/稽核紀錄-prd.md)。
- 已擴充至使用者/角色/權限異動事件（0.4.23）：`User.Create`/`User.Update`/`User.Delete`（`MyUserService`，Detail 含帳號與角色/團隊指派摘要）、`Role.Create`/`Role.Update`/`Role.Delete`（`RoleViewService`，Detail 含角色名稱與權限鍵數）。Actor 取自 `CurrentUserService.CurrentUser`（未登入時 `ActorUserId` 為 null）；僅記錄成功異動。

## 二階段驗證（TOTP，選配骨架）

已建立 TOTP（RFC 6238）基礎設施，**預設關閉、尚未強制於登入**：

- 欄位：`MyUser.TwoFactorEnabled`（預設 `false`）、`MyUser.TwoFactorSecret`（Base32 密鑰，未綁定為 null）。
- 服務：`ITotpService` / `TotpService`（`MeetingRecord.Business/Services/Other/`）——`GenerateSecret`、`GenerateProvisioningUri`（otpauth:// 供驗證器掃碼）、`ComputeCode`、`VerifyCode`。以 HMAC-SHA1、30 秒週期、6 碼實作，並以 RFC 6238 測試向量驗證。
- 資料表欄位由 migration `AddTwoFactor` 建立（SQLite）。
- **MFA 強制經決定不納入目前實作範圍**（2026/07/09，刻意不做、非遺漏）：綁定/停用的使用者介面（QR Code）與登入第二步驗證強制**目前不實作**；TOTP 骨架保留、預設關閉，日後如有實際需求再另案評估。

## Refresh Token 限制
目前 refresh token 不落庫，因此有以下限制：
- 無法可靠撤銷單一 refresh token。
- 使用者登出後，已發出的 refresh token 仍可能在有效期內換發 token。
- 若要強制全部失效，只能輪替 `SigningKey` 或縮短有效期。
- **Refresh Token 落庫撤銷經決定不納入目前實作範圍**（2026/07/09，刻意不做、非遺漏）：目前維持 stateless、不落庫；如日後需要可撤銷、裝置管理或風險控管，再改成 refresh token 落庫並記錄 jti、使用者、過期時間、撤銷時間與裝置資訊。
